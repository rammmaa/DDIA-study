### 인트로

- 데이터를 여러 노드에 똑같이 복사해두는 게 **복제(replication)**다.
- 이걸 왜 하나?
  - 지연 시간 감소: 사용자랑 지리적으로 가까운 곳에 데이터를 둔다.
  - 가용성: 노드 몇 개 죽어도 시스템은 돌아가야 하니까.
  - 읽기 확장: 리더 한 놈이 읽기 요청을 다 감당 못 할 때 팔로워로 분산한다.
- 데이터가 안 변하면 쉽다. 모든 골칫거리는 **데이터 변경(쓰기)**에서 온다.
- 크게 세 가지 알고리즘이 있다: **싱글 리더, 멀티 리더, 리더리스**. 거의 모든 분산 DB는 이 중 하나를 쓴다.

### 리더와 팔로워 (Single-Leader)

- 복제본 중 한 놈만 리더(Master)로 지정한다. 클라이언트는 쓰기 요청을 무조건 리더한테만 보낸다.
- 리더가 자기 로컬에 데이터를 적고, 그 변경 사항을 로그(replication log) 형태로 팔로워들한테 쏜다.
- 팔로워는 리더가 보내준 순서 그대로 자기 데이터를 갱신한다. PostgreSQL, MySQL, MongoDB 등이 다 이 방식이다.

#### 동기 vs 비동기

- **동기식**: 팔로워가 "나도 잘 적었어"라고 응답(ACK)할 때까지 리더가 기다린다.
  - 장점: 리더랑 팔로워 데이터가 항상 똑같다.
  - 단점: 팔로워 하나만 뻗어도 리더의 쓰기 작업이 멈춘다. 사실상 비현실적이다.
- **비동기식**: 리더는 로그 보냈으면 팔로워 응답 안 기다리고 걍 끝낸다.
  - 제일 많이 쓴다. 빠르니까.
  - 근데 리더가 죽으면 팔로워한테 미처 못 간 데이터는 영영 날아간다. 성능과 내구성의 트레이드오프다.

#### 리더가 죽으면? (Failover)

- 팔로워 죽는 건 쉽다. 그냥 나중에 리더한테 "나 죽었을 때 뭐 바뀌었냐" 물어보고 따라잡으면 된다.
- 리더 장애 처리가 진짜 빡세다.
  - 일단 누가 죽었는지 판단해야 한다(보통 타임아웃).
  - 새 리더를 뽑는다(제일 최신 데이터 가진 놈으로).
  - 시스템 설정을 다 바꾼다. "이제부터 얘가 대장이야."
- 이 과정에서 **스플릿 브레인(split-brain)** 문제가 터질 수 있다. 두 노드가 서로 지가 리더라고 우기면 데이터 다 꼬인다.

### 복제 로그 구현 방식

- **구문 기반(Statement-based)**: `INSERT...` 같은 SQL 문을 걍 그대로 보낸다.
  - `NOW()`나 `RAND()` 같은 함수 쓰면 리더랑 팔로워 데이터가 달라진다. 구리다.
- **WAL(Write-Ahead Log) 배송**: DB 엔진이 디스크에 적는 저수준 바이트 열을 그대로 쏜다.
  - 빠르긴 한데 DB 저장소 엔진이랑 너무 꽉 묶여 있다. 버전 조금만 달라도 복제가 안 돼서 업그레이드할 때 피곤하다.
- **논리적(로우 기반) 로그**: 엔진 내부 구현이랑 분리해서 "어떤 로우의 어떤 값이 바뀌었다"는 정보만 보낸다.
  - 버전이 달라도 되고, 외부 앱(CDC 등)에서 데이터를 읽어 가기도 편하다. MySQL binlog가 이 방식이다.
- **트리거 기반**: 애플리케이션 코드 수준에서 복제 로직을 짠다. 오버헤드가 크지만 유연하다.

### 복제 지연 (Replication Lag) 문제

- 비동기 복제에선 팔로워가 리더보다 뒤처지는 게 당연하다. 이걸 **최종적 일관성(eventual consistency)**이라 부른다. "언젠가는 맞춰지겠지"라는 뜻이다.
- 근데 이 지연 시간 때문에 사용자가 이상함을 느끼는 케이스가 있다.

1.  **자신이 쓴 내용 읽기**: 내가 방금 댓글 썼는데 새로고침하니 안 보인다.
    - 해결: 자기가 수정 가능한 데이터는 리더에서 읽게 하거나, 마지막 갱신 후 일정 시간 동안 리더를 강제한다.
2.  **단조 읽기(Monotonic reads)**: 이 팔로워에서 읽었을 땐 데이터가 있었는데, 다음 클릭 때 다른 팔로워로 접속하니 데이터가 없다. 시간이 거꾸로 흐르는 기분이다.
    - 해결: 같은 사용자는 항상 같은 복제본에서 읽게 라우팅한다.
3.  **일관된 순서로 읽기**: 질문보다 답변이 먼저 보이면 안 된다. 인과성이 깨지는 문제다.
    - 해결: 인과 관계가 있는 데이터는 같은 파티션에 몰아넣는다.

### 다중 리더 복제 (Multi-Leader)

- 쓰기를 여러 리더가 받아들인다. 주로 여러 데이터센터에 걸쳐 서비스를 하거나, 오프라인 작업을 해야 하는 모바일 앱에서 쓴다.
- **쓰기 충돌**이 무조건 난다. 웬만하면 특정 레코드는 특정 리더로 가도록 '충돌 회피'를 하는 게 제일 낫다.
- 굳이 충돌을 해결해야 한다면 LWW(Last Write Wins)나 CRDT 같은 기법을 써서 모든 복제본이 하나의 값으로 **수렴**하게 만들어야 한다.

### 리더리스 복제 (Leaderless)

- 리더가 아예 없다. 클라이언트가 여러 노드에 동시에 쓰고 읽는다. (Cassandra, Riak 등)
- **정족수(Quorum)** 개념을 쓴다.
  - $w + r > n$ ($n$: 복제본 수, $w$: 쓰기 성공 노드, $r$: 읽기 노드)
  - 이 식을 만족하면 이론적으로 읽기 때 적어도 한 놈은 최신 데이터를 들고 있게 된다.
- **안티 엔트로피(Anti-entropy)**: 백그라운드에서 노드 간 데이터 차이를 계속 맞춘다.
- **Sloppy Quorum**: 네트워크 장애 시 근처 노드에 대충 적어뒀다가 나중에 돌려주는 방식이다. 가용성은 높지만 일관성은 더 떨어진다.

### 동시 쓰기 감지

- 두 작업이 서로를 모른 채 발생하면 **동시 작업(concurrent)**이다. 물리적 시간과는 상관없다.
- **LWW(Last Write Wins)**: 걍 타임스탬프 찍어서 나중에 들어온 놈이 이기게 한다. 쉽지만 데이터 유실 위험이 크다.
- **인과성 파악**: 클라이언트가 읽을 때 받은 버전 번호를 다시 보냄으로써, 내가 어떤 데이터를 보고 수정했는지를 서버에 알린다.
- **버전 벡터(Version Vector)**: 다중 복제본 환경에선 복제본당 버전 번호를 다 관리해서 충돌을 감지하고 병합(Sibling 병합)해야 한다.

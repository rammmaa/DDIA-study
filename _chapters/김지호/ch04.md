## 📝 상세 정리
- 이번 장에선 JSON, XML, 프로토콜 버퍼, Thrift, Avro를 비롯해서 데이터 부호화를 위한 다양한 형식을 살펴볼 것이다.
	- 특히 어떻게 스키마를 변경하고 예전/새로운 버전의 데이터와 코드가 공존하는 시스템을 지원할지!
- 그리고 REST 원칙과 remote procedure call, actor과 같은 메세지 전달 시스템에서도 어떻게 사용되는지 알아보자.
### 데이터 부호화 형식

#### 언어별 형식
- Java의 `Serializable`이나 Python의 `pickle`처럼 특정 언어에 내장된 부호화 기능이다.
- 타 언어와의 호환성이 낮고 보안 취약점이 존재하며, 데이터의 장기 보관 시 버전 관리 효율이 떨어진다.

#### JSON과 XML, 이진 변형
- 텍스트 기반의 범용 형식으로 사람이 읽기 쉽고 웹 환경에서 널리 쓰이지만, 숫자의 정밀도 문제나 이진 문자열 처리의 비효율성이 존재한다.
- 이를 보완하기 위해 MessagePack, BSON 같은 이진 변형이 등장했으나, 데이터 내부에 필드 이름을 포함하므로 공간 절감 효과가 제한적이다.

#### 이진 부호화
- 스키마를 정의하고 데이터를 이진 형태로 변환하여 저장 공간과 전송량을 최소화하는 방식이다.
- 데이터와 함께 필드 이름 대신 태그 번호를 사용하여 크기를 줄이며, 읽기/쓰기 시 스키마 해석 과정이 필요하다.

#### 스리프트와 프로토콜 버퍼
- IDL(Interface Definition Language)을 통해 스키마를 정의하고 코드를 생성하는 방식이다.
- 각 필드에 고유한 태그 번호를 부여하여 부호화된 데이터 내에서 필드를 식별하며, 전개 성능이 우수하다.

#### 필드 태그와 스키마 발전
- 새로운 필드를 추가하거나 삭제할 때 태그 번호를 유지하여 하위 호환성(Old 코드가 New 데이터 읽기)과 상위 호환성(New 코드가 Old 데이터 읽기)을 보장한다.
- 태그 번호는 변경할 수 없으며, 필수(required) 필드 추가 시 호환성이 깨질 수 있으므로 주의해야 한다.

#### 데이터 타입과 스키마 발전
- 필드의 데이터 타입을 변경하는 것은 데이터가 잘리거나 정밀도를 잃을 위험이 있어 호환성을 깨뜨릴 가능성이 높다.
- Protobuf의 `repeated` 필드처럼 가변 길이 데이터를 처리하는 방식은 호환성을 유지하면서 리스트 형태로 확장이 가능하다.

#### 아브로
- 부호화된 데이터에 필드 태그나 자료형 정보를 포함하지 않아 가장 간결한 이진 형식을 제공한다.
- 데이터를 읽을 때 쓰기 스키마(Writer's Schema)와 읽기 스키마(Reader's Schema)를 비교하여 필드를 매칭하는 스키마 해석 과정을 거친다.

#### 쓰기 스키마와 읽기 스키마
- 데이터를 생성할 때 사용한 스키마와 데이터를 읽는 시점에 사용하는 스키마가 일치하지 않아도 된다.
- 아브로 도서관은 두 스키마 사이의 차이를 해결(Resolution)하여 누락된 필드는 기본값으로 채우고 불필요한 필드는 무시한다.

#### 스키마 발전 규칙
- 아브로에서 호환성을 유지하려면 기본값이 정의된 필드만 추가하거나 삭제해야 한다.
- 필드 이름 변경은 별칭(alias)을 통해 지원하지만, 타입 변경은 호환성 규칙을 엄격히 준수해야 한다.

#### 그러면 쓰기 스키마는 무엇인가?
- 대용량 파일에서는 파일 시작 부분에 한 번 포함하고, 개별 레코드 저장 시에는 스키마 버전 번호만 포함하여 오버헤드를 줄인다.
- 데이터베이스나 네트워크 통신 시에는 별도의 스키마 저장소(Registry)를 두어 버전 번호를 통해 스키마를 조회한다.

#### 동적 생성 스키마
- 데이터베이스 테이블의 덤프를 생성할 때와 같이, 소스 데이터의 구조가 바뀔 때마다 스키마를 즉석에서 생성하기 용이하다.
- 필드 태그를 수동으로 관리할 필요가 없으므로 관계형 스키마와 이진 부호화 사이의 변환이 자동화된다.

#### 코드 생성과 동적 타입 언어
- Thrift나 Protobuf는 정적 타입 언어에서 타입 검사를 위해 코드 생성이 필수적이지만, Avro는 스키마만 있으면 코드를 생성하지 않고도 데이터를 읽을 수 있다.
- 이는 JavaScript나 Python 같은 동적 타입 언어에서 특히 유용하며, 제네릭 데이터 처리 소프트웨어 구현에 적합하다.

#### 스키마의 장점
- 이진 부호화는 JSON 등에 비해 크기가 훨씬 작고, 스키마 자체가 문서화의 역할을 하며 호환성 검증 도구로 활용된다.
- 정적 타입 언어에서는 코드 생성을 통해 컴파일 타임에 타입 체크가 가능하여 런타임 오류를 방지한다.

### 데이터플로 모드
#### 데이터베이스를 통한 데이터플로
- 프로세스가 데이터베이스에 데이터를 기록하고 나중에 다시 읽는 행위는 미래의 자신에게 메시지를 보내는 것과 같다.
- 이전 버전의 코드가 새로운 버전의 코드가 쓴 데이터를 덮어쓸 때, 신규 필드가 유실되지 않도록 주의해야 한다.

#### 다양한 시점에 기록된 다양한 값
- 데이터베이스에는 수년 전의 데이터와 최근의 데이터가 공존하므로, 애플리케이션 코드는 모든 데이터 버전을 지원해야 한다.
- 이를 '데이터가 코드보다 오래 산다(Data outlives code)'고 표현하며, 스키마 발전의 중요성을 시사한다.

#### 보관 저장소
- 백업이나 분석을 위해 데이터를 덤프할 때는 최신 스키마를 사용하여 일괄 부호화하는 것이 관리 측면에서 유리하다.
- Avro 파일 형식처럼 한 파일 내에 하나의 스키마를 포함하는 방식이 보관용으로 적합하다.

#### 서비스를 통한 데이터플로: REST와 RPC
- 네트워크를 통해 클라이언트와 서버가 통신하는 방식으로, REST는 HTTP 원칙을 따르고 RPC는 원격 함수 호출을 로컬처럼 보이게 한다.
- 서비스 업데이트 시 서버가 먼저 업데이트되고 클라이언트가 나중에 업데이트되므로, 양방향 호환성이 필수적이다.

#### 웹 서비스
- HTTP를 전송 프로토콜로 사용하는 서비스로, REST는 리소스 중심이며 JSON을 주로 사용하고 SOAP는 XML 기반의 복잡한 스택을 가진다.
- REST는 단순함과 웹 생태계와의 호환성 덕분에 공개 API에서 사실상의 표준으로 자리 잡았다.

#### 원격 프로시저 호출(RPC) 문제
- 로컬 함수 호출과 달리 네트워크 지연, 타임아웃, 중복 실행 문제 등 예측 불가능한 실패 변수가 많다.
- 네트워크를 통한 데이터 전달은 참조 대신 부호화된 복사본을 보내야 하므로 대용량 객체 전달 시 효율이 떨어진다.

#### RPC의 현재 방향
- 최신 프레임워크(gRPC, Finagle 등)는 네트워크 통신의 비동기성을 명시적으로 드러내어 오류 처리를 강화한다.
- 프로토콜 버퍼나 스리프트를 사용하여 성능을 높이고 언어 간 호환성을 보장하며, 서비스 발견(Service Discovery) 기능을 통합한다.

#### 데이터 부호화와 RPC의 발전
- 서비스 간 결합도를 낮추기 위해 서버와 클라이언트를 독립적으로 변경할 수 있어야 한다.
- RPC 스키마의 전방/후방 호환성을 유지함으로써 전체 시스템의 중단 없이 점진적인 배포가 가능해진다.

#### 메시지 전달 데이터플로
- 메시지 브로커를 통해 비동기적으로 데이터를 전달하는 방식으로, RPC와 데이터베이스의 중간 형태를 띤다.
- 송신자는 수신자의 응답을 기다리지 않으며, 시스템 간 결합도를 낮추고 장애 내성을 높인다.

#### 메시지 브로커
- Kafka, RabbitMQ와 같은 소프트웨어가 메시지를 큐에 저장하고 구독자에게 전달하는 역할을 수행한다.
- 메시지 부호화 시 스키마 호환성을 지키면, 생산자와 소비자의 버전을 독립적으로 관리하며 데이터 파이프라인을 운영할 수 있다.

#### 분산 액터 프레임워크
- 단일 프로세스 내의 동시성 모델을 네트워크로 확장하여, 액터들이 메시지를 주고받으며 상태를 관리하는 방식이다.
- 액터 시스템 업데이트 시에도 이전 버전과의 메시지 부호화 호환성이 유지되어야 전체 시스템이 정상 작동한
    

### 정리
- 애플리케이션의 지속적인 발전을 위해서는 데이터 부호화 형식이 상위/하위 호환성을 반드시 지원해야 한다.
- 스키마 기반 형식은 효율적인 공간 활용과 강력한 타입 보장을 제공하며, 시스템의 복잡도가 높아질수록 그 이점이 극대화된다.

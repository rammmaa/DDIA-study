# Chapter 5 

Replication means keeping a copy of the same data on multiple machines connected via a network. The goals are **High Availability**, **Latency Reduction**, and **Scalability**.

---

## 1. Leaders and Followers
The most common approach to replication is **Leader-based replication** (Master/Slave).

*   **The Leader:** Receives all writes. It writes the data to local storage and sends the data change to all followers.
*   **Followers:** Read-only. They apply the changes sent by the leader in the exact same order.

### Synchronous vs. Asynchronous
*   **Synchronous:** The leader waits for followers to confirm the write before telling the user it's done. 
    *   *Pro:* Data is guaranteed to be up to date. 
    *   *Con:* If one follower fails, the whole write blocks.
*   **Asynchronous:** The leader returns success immediately. 
    *   *Pro:* High performance. 
    *   *Con:* Risk of data loss if the leader crashes before changes propagate.



---

## 2. Handling Node Outages
*   **Follower Failure:** Easy. The follower uses its logs to catch up from where it left off.
*   **Leader Failure (Failover):** Complex. A follower must be promoted to leader. This requires:
    1. Determining the leader is dead (usually via timeout).
    2. Electing a new leader (consensus).
    3. Reconfiguring the system to send writes to the new leader.

---

## 3. Replication Logs
How does data actually move?
*   **Statement-based:** Send every `INSERT` or `UPDATE` SQL string. (Dangerous with non-deterministic functions like `NOW()` or `RAND()`).
*   **Write-Ahead Log (WAL) Shipping:** Sending the low-level disk blocks. (Fast, but ties the follower to the exact software version of the leader).
*   **Logical (Row-based):** Sending a sequence of records describing row changes. (Most flexible and recommended for compatibility).

---

## 4. Problems with Replication Lag
In an asynchronous system, followers may lag behind the leader, causing "read-after-write" issues. Kleppmann highlights three key consistency models to fix this:

1.  **Reading Your Own Writes:** Ensure a user always sees the update they just submitted (e.g., read from the leader for 1 minute after an update).
2.  **Monotonic Reads:** Ensure a user doesn't see time move backward (if they refresh and hit a "slower" follower).
3.  **Consistent Prefix Reads:** Ensure that if a sequence of writes happens in a certain order, everyone reads them in that same order.



---

## 5. Multi-Leader and Leaderless Replication

### Multi-Leader (Master-Master)
Used for multi-datacenter setups or offline-capable apps (like Google Docs).
*   **Conflict Resolution:** The biggest challenge. If two leaders update the same row, how do you decide who wins? (LWW - Last Write Wins, or Causal Ordering).

### Leaderless (Dynamo-style)
Used by Cassandra and Riak. Clients send writes to several nodes in parallel.
*   **Quorums ($w + r > n$):** To ensure a read sees the latest write, the number of nodes written to ($w$) plus the number of nodes read from ($r$) must be greater than the total number of replicas ($n$).
*   **Read Repair:** When a client reads from multiple nodes and notices one is "old," it pushes the new data back to that node.



---

## 6. Key Takeaways
*   **Replication is hard** because of the network's unreliability.
*   **Eventual Consistency** is the baseline for most distributed systems, but "eventual" can be a very long time under heavy load.
*   **Trade-offs:** You must choose between the simplicity of a single leader, the availability of multi-leader, or the robustness of leaderless quorums.

## 1. Partitioning and Replication
Partitioning is almost always used in combination with replication. Each partition has its own leader and multiple followers. A single node may host multiple partitions (some as a leader, others as a follower).



---

## 2. Partitioning Key-Value Data
The main challenge is avoiding **Hot Spots** (nodes with significantly more load than others).

### Partitioning by Key Range
*   **Mechanism:** Assigns a continuous range of keys to each partition (like an encyclopedia).
*   **Pros:** Efficient range scans (e.g., "get all sensor data from 10:00 to 11:00").
*   **Cons:** Certain access patterns lead to hot spots (e.g., if the key is a timestamp, all writes for today go to one partition).

### Partitioning by Hash of Key
*   **Mechanism:** Use a hash function on the key and assign a hash range to each partition.
*   **Pros:** Distributes keys uniformly across partitions, effectively "shuffling" the data to avoid hot spots.
*   **Cons:** You lose the ability to perform efficient range queries; you must search every partition.

---

## 3. Partitioning and Secondary Indexes
Secondary indexes don't usually map neatly to partitions. There are two main approaches:

### Document-based Partitioning (Local Index)
*   Each partition maintains its own secondary index for only the data it stores.
*   **Reads:** Requires "scatter/gather"—you must query every single partition to find all matching records.
*   **Writes:** Very fast, as only one partition needs to be updated.

### Term-based Partitioning (Global Index)
*   The secondary index is itself partitioned across all nodes.
*   **Reads:** More efficient than scatter/gather; you know exactly which partition holds the index entry you need.
*   **Writes:** Slow and complex; a single document write might require updating multiple index partitions across the network.

---

## 4. Rebalancing Partitions
As load increases or nodes fail, partitions must move from one node to another.

*   **How NOT to do it (hash mod N):** If you use `hash(key) % number_of_nodes`, adding one node changes almost every key's location, causing massive data movement.
*   **Fixed Number of Partitions:** Create many more partitions than nodes (e.g., 1000 partitions for 10 nodes). When a node is added, it "steals" a few partitions from existing nodes.
*   **Dynamic Partitioning:** Used in HBase and MongoDB. When a partition grows past a certain size, it splits into two (similar to a B-tree).

---

## 5. Request Routing (Service Discovery)
How does a client know which node to connect to? This is a "service discovery" problem.

1.  **Direct Contact:** Clients can hit any node; if that node doesn't have the data, it forwards the request to the right one.
2.  **Routing Tier:** A load balancer/gateway acts as a partition-aware proxy.
3.  **Client-aware:** The client knows the partitioning scheme and connects directly to the correct node.
    *   *Note:* Systems often use **ZooKeeper** to keep track of which partition lives on which node.

---

## 6. Key Takeaways
*   **Scalability:** Partitioning is essential for datasets too large for a single disk or node.
*   **Skew & Hotspots:** No matter how good your hashing is, highly popular keys (e.g., a celebrity's profile) will always create hot spots that require application-level logic to fix.
*   **The "Scatter/Gather" Problem:** Local secondary indexes can lead to significant tail latency because the slowest partition dictates the speed of the entire query.

# Chapter 3

## 1. The Fundamental Trade-off
A database at its simplest is just a log file where you append data. However, searching a large log is $O(n)$. To speed up reads, we use **Indexes**.
* **The Cost:** Indexes are "side-structures" that speed up reads but slow down writes (because the index must be updated every time data is written).

---

## 2. LSM-Trees (Log-Structured Merge-Trees)
This approach is used in modern "NoSQL" systems like Cassandra, RocksDB, and Bigtable. It relies on sequential writes.

### SSTables (Sorted String Tables)
Instead of just appending, we keep the data **sorted by key**. This allows:
1.  **Efficient Merging:** Merging files is simple (like Merge Sort).
2.  **Sparse Indexes:** You only need to index the start of every few blocks, not every single key.

### The Write Path
1.  Writes go to an in-memory balanced tree called a **Memtable**.
2.  When the memtable gets too big, it is flushed to disk as an **SSTable**.
3.  **Compaction:** Background threads merge SSTables and discard old or deleted values.
4.  **Bloom Filters:** Used to quickly determine if a key exists in an SSTable to avoid unnecessary disk reads.


---

## 3. B-Trees
The most common index type, used in almost all relational databases (PostgreSQL, MySQL).

### Structure
* B-trees break the database into fixed-size **pages** (usually 4KB).
* Pages are arranged in a tree structure. To find a key, you follow pointers from the root page to the leaf pages.
* Unlike LSM-trees, B-trees **overwrite** pages on disk rather than appending.

### Reliability
* Because B-trees overwrite data, they use a **Write-Ahead Log (WAL)**. Every operation is written to this log before the tree is modified so the DB can recover after a crash.



---

## 4. LSM-Trees vs. B-Trees

| Feature | LSM-Trees | B-Trees |
| :--- | :--- | :--- |
| **Write Speed** | Higher (Sequential writes) | Lower (Random writes) |
| **Read Speed** | Lower (Check multiple files) | Higher (Fixed location) |
| **Storage Efficiency** | High (Better compression) | Lower (Fragmentation/Empty space) |
| **Workload** | Write-heavy | Read-heavy |

---

## 5. OLTP vs. OLAP
How you store data depends on how you use it.

### OLTP (Online Transaction Processing)
* **Use Case:** User-facing apps (e.g., "Add item to cart").
* **Pattern:** Small number of records per query, looked up by key.
* **Storage:** Row-oriented.

### OLAP (Online Analytical Processing)
* **Use Case:** Business Intelligence (e.g., "Average revenue per month").
* **Pattern:** Scans millions of rows, but only a few columns.
* **Storage:** Column-oriented.

---

## 6. Column-Oriented Storage
In big data analytics, storing data by column instead of by row is more efficient.

1.  **I/O Efficiency:** If a query only needs 3 columns out of 100, the engine only reads those 3 files from disk.
2.  **Compression:** Values in a column look similar (e.g., many "USD" strings in a currency column). This allows for massive compression using **Bitmap Encoding** or **Delta Encoding**.



---

## 7. Key Terms
* **Compaction:** Merging multiple sorted files into one and removing duplicates.
* **Tombstone:** A marker used in LSM-trees to signify that a record has been deleted.
* **Materialized View:** A pre-computed cache of a query result, physically stored on disk.

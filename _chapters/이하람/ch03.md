저장소 엔진은 크게
- 로그 구조화(log-structured) 계열
- 페이지 지향(page-oriented) 계열  
    로 나뉜다. 대표적으로 전자는 Bitcask, SSTable, LSM 트리, 후자는 B 트리다.

### 01. 가장 단순한 데이터베이스와 색인의 필요성

- 가장 단순한 DB는 append-only 파일이다.    

```bash
#!/bin/bash

db_set() {
  echo "$1,$2" >> database
}

db_get() {
  grep "^$1," database | sed -e "s/^$1,//" | tail -n 1
}
```

- `db_set`은 파일 끝에 계속 추가만 한다.
- `db_get`은 같은 키가 여러 번 들어왔을 때 가장 마지막 값을 찾는다.
    
1) 쓰기가 단순하고 빠르다; 많은 데이터베이스도 내부적으로 append-only 로그를 사용한다.
2) 키를 찾을 때마다 파일 전체를 훑어야 한다. / 검색 비용은 O(n) 이다.
        
- 따라서 빠른 조회를 위해 별도의 데이터 구조, 즉 색인(index) 이 필요해진다.
    
---

### 02. 색인의 일반 개념과 트레이드오프

- 색인은 기본 데이터에서 파생된 부가적 메타데이터 구조다. 하나의 데이터를 여러 방식으로 검색하고 싶다면 여러 종류의 색인이 필요할 수 있다.
    
- 색인의 특징
    1) 데이터 자체를 바꾸지는 않는다.
    2) 주로 질의 성능에 영향을 준다.   
    3) 읽기는 빨라질 수 있다. (빨라질 수도 있고 그렇지 않을 수 있음) 하지만 쓰기를 할 때마다 색인도 함께 갱신해야 하므로 쓰기 속도는 느려진다.
    
* 따라서 어떤 색인을 선택해야 하는지 판단하는 것은 개발자의 몫이다.

### 03. 해시 색인(Hash Index)

- 키-값 저장소는 프로그래밍 언어의 해시 맵(hash map) 과 매우 유사하다. (ok) 키  → 데이터 파일의 바이트 오프셋을 가리키는 인메모리 해시 맵을 유지하는 것.

- 쓰기
    - 로그 파일 끝에 키-값 쌍을 append    
    - 해시 맵에 해당 키의 최신 오프셋 반영
        
- 읽기
    - 해시 맵으로 오프셋 확인    
    - 디스크에서 해당 위치로 바로 가서 값 읽기

#### 해시 색인의 장점

- 구조가 단순하다.
- 모든 키가 메모리에 들어간다는 가정 하에서 매우 빠르다.
- 값은 디스크에 있어도 되고, OS 캐시에 있으면 더 빨라질 수 있다.
- 특히 같은 키가 자주 갱신되는 작업부하에 잘 맞는다.
    - e.g., 동영상 URL -> 재생 횟수
    
#### 로그 세그먼트와 컴팩션

- append-only만 계속하면 디스크 공간이 무한히 늘어난다.
- 해결책
    - 로그를 segment 단위로 나눈다.
    - 오래된 세그먼트들에 대해 compaction(중복된 키를 제거하고 각 키의 최신 값만 남김)을 수행한다.
    - 병합/컴팩션은 보통 백그라운드 스레드에서 수행할 수 있다.
    

#### 실제 구현 시 고려할 점

- CSV보다 바이너리 형식이 더 적합하다.
- 삭제는 툼스톤(tombstone) 레코드로 표현한다.
- 크래시 후 인메모리 해시 맵은 사라지므로 복구가 필요하다.
- 부분 쓰기 손상을 감지하기 위한 체크섬 등이 필요하다.
- 순차 쓰기이므로 보통 하나의 쓰기 스레드만 둬도 구현이 단순하다.
    

#### 해시 색인의 한계

- 모든 키를 메모리에 올려야 한다.
- 범위 질의(range query) 에 비효율적이다.
    - e.g., kitty00000 ~ kitty99999 사이의 키를 쉽게 순차 스캔할 수 없다.

### 04. SSTable과 LSM 트리

- 해시 색인의 한계를 넘기 위해 등장하는 구조가 SSTable(Sorted String Table) 이다.
- 키-값 쌍을 로그에 쓰되, 키 순서대로 정렬해서 저장한다.
#### SSTable의 장점

1. 세그먼트 병합이 쉽다.
    - 정렬된 파일끼리 병합정렬처럼 합칠 수 있다.
    - 같은 키가 여러 세그먼트에 있으면 더 최신 값을 남긴다.
        
2. 모든 키를 메모리에 둘 필요가 없다.
    - 일부 키만 가리키는 희소 색인(sparse index) 만 있어도 된다.
    - 특정 키가 어디쯤 있을지 범위를 좁힌 뒤, 그 구간만 스캔하면 된다.
        
3. 블록 압축이 가능하다.
    - 인접한 키-값들을 블록으로 묶어 압축 저장할 수 있다.
    - 디스크 공간과 I/O 대역폭을 절약한다.

#### 쓰기 문제와 멤테이블(memtable)

- 문제는 실제 쓰기가 임의 순서로 들어온다는 점이다.
- 해결책
    - 메모리 안에서 정렬 구조를 유지한다.    
    - 보통 균형 트리를 사용한다?
    - 이 인메모리 정렬 구조를 멤테이블(memtable) 이라 한다.
        
#### LSM 트리의 동작
- 쓰기가 들어오면 멤테이블에 기록
- 멤테이블이 커지면 디스크에 SSTable 로 flush
- 읽을 때는
    1. 멤테이블 확인
    2. 가장 최신 SSTable 확인
    3. 더 오래된 SSTable 순서대로 확인
        
- 백그라운드에서 세그먼트 병합과 컴팩션 수행

#### 크래시 복구
- 아직 디스크로 flush되지 않은 멤테이블 데이터는 크래시 시 사라질 수 있다.    
- 그래서 별도의 append-only 로그를 둬서, 재시작 후 멤테이블을 복구한다.

#### LSM 트리와 관련 기술
- LevelDB, RocksDB
- Cassandra, HBase
- Lucene도 유사한 원리를 활용한다.
#### 성능 최적화
- 존재하지 않는 키를 찾는 경우 느릴 수 있으므로 Bloom Filter를 사용한다.
- 컴팩션 전략으로는
    - size-tiered compaction
    - leveled compaction  
    - 등이 존재한다.
    
#### LSM 트리의 특징

- 데이터셋이 메모리보다 훨씬 커도 잘 동작한다.
- 키가 정렬돼 있으므로 범위 질의가 가능하다.
- 디스크 쓰기가 순차적이어서 높은 쓰기 처리량을 얻을 수 있다.

### 05. B 트리

- B 트리(B-tree) 는 가장 널리 쓰이는 색인 구조다.
	- 키가 정렬되어 있음 > 검색과 범위 질의에 유리함
	- LSM과 달리 고정 크기 페이지(page) 를 중심으로 동작

#### B 트리의 구조

- 페이지들이 트리 구조를 이룬다.
- 루트에서 시작해,
- 키 범위에 맞는 하위 페이지를 따라 내려가고,
- 마지막 리프 페이지에서 값을 찾는다.
    

#### 삽입과 분할

- 새 키를 넣을 페이지에 여유가 있으면 그대로 삽입
- 공간이 부족하면 페이지 분할(split) 수행
- 상위 페이지도 갱신
- 트리는 균형을 유지하므로 깊이는 O(log n) 이다.
    
#### B 트리의 특징

- 데이터를 제자리 갱신(in-place update) 한다.
- 즉, 기존 페이지를 덮어쓴다.
- 이 점이 append-only 기반 LSM과 가장 큰 차이다.
    

#### 신뢰성 문제와 WAL

- 여러 페이지를 갱신하는 중간에 크래시가 나면 색인이 깨질 수 있다.
- 이를 막기 위해 WAL(write-ahead log) 를 둔다.
- 변경 내용을 먼저 로그에 기록한 뒤 실제 페이지에 반영한다.
    

#### 동시성 제어

- 여러 스레드가 동시에 접근하면 일관성이 깨질 수 있으므로
- 보통 latch 같은 잠금으로 보호한다.
    

#### B 트리 최적화

- copy-on-write 방식
- 키 축약 저장
- 리프 페이지의 연속 배치
- 형제 페이지 포인터
- 프랙탈 트리 등의 변형

- 사실 이부분 뭐라는지 잘 모르겠어요 나중에 다시 또 볼게요

### 06. B 트리와 LSM 트리 비교

- 일반적으로 LSM 트리는 쓰기에 강하고, B 트리는 읽기에 강하다    

#### LSM 트리의 장점

- 순차 쓰기 기반이라 쓰기 처리량이 높다.
- 압축률이 더 좋고 저장 공간 오버헤드가 낮다.
- 파편화가 적다.
- 특히 자기 디스크에서 임의 쓰기보다 순차 쓰기가 훨씬 빠른 점이 중요하다.

#### LSM 트리의 단점

- **컴팩션**이 읽기/쓰기에 영향을 줄 수 있다.
- 상위 백분위 응답 시간이 길어질 수 있다.
- 컴팩션이 유입 쓰기 속도를 못 따라가면 세그먼트 수가 쌓이고 읽기도 느려진다.
- 따라서 명시적인 모니터링이 필요하다.

#### B 트리의 장점

- 각 키가 색인 안의 한 곳에만 정확히 존재한다.
- 강한 트랜잭션 시맨틱과 잘 맞는다.

### 07. 기타 색인 구조

#### 보조 색인(secondary index)

- 기본키 외 다른 칼럼에도 색인을 둘 수 있다.
- 조인 성능에 매우 중요하다.
- 차이점은 기본키와 달리 고유하지 않을 수 있다는 점이다.

#### 색인 안에 값 저장하기

- 색인 값은    
    - 실제 row 자체일 수도 있고
    - 다른 곳에 저장된 row를 가리키는 참조일 수도 있다.
        
- 실제 로우를 저장한 곳을 힙 파일이라 한다.
    
- 변형
    - 클러스터드 색인: 색인 안에 실제 로우 저장    
    - 비클러스터드 색인: 로우 위치만 저장
    - 커버링 색인: 일부 칼럼을 색인 안에 함께 저장
        

#### 다중 칼럼 색인

- 여러 칼럼에 동시에 질의하려면 단일 키 색인만으로는 부족하다.
- 대표적으로
    - 결합 색인(concatenated index)
    - 다차원 색인(multidimensional index) 이 있다.
        

#### 다차원 색인의 예시

```sql
SELECT *
FROM restaurants
WHERE latitude > 51.4946 AND latitude < 51.5079
  AND longitude > -0.1162 AND longitude < -0.1004;
```

- 이런 2차원 범위 질의는 일반 B 트리/LSM만으로는 비효율적일 수 있다.
- > 공간 채움 곡선 / R 트리 같은 전문 공간 색인을 사용한다.
        

#### 전문 검색과 퍼지 색인

- 정확한 키 일치가 아니라 오타 / 유사어 / 형태소 변형 등을 다루려면 별도 기술이 필요
- 루씬은 편집 거리 기반 검색, 오토마톤 등을 사용한다? < 이게 뭔지 모르겠어요

### 08. 인메모리 데이터베이스

- 지금까지의 구조는 대부분 디스크의 한계를 보완하려는 시도였다. 그런데 메모리가 점점 저렴해지면서 전체 데이터를 메모리에 두는 인메모리 DB도 현실적으로 고려되며 인메모리 데이터베이스가 개발되었다. 

#### 특징

- 일부는 캐시 용도로만 사용된다. 예: Memcached
    
- 일부는 지속성을 목표로 한다.
    
    - 디스크 로그
    - 주기적 스냅샷
    - 복제
    - 특수 하드웨어 등으로 지속성을 확보한다.
        

#### 중요한 점

- 인메모리 DB가 빠른 이유는 단순히 디스크를 안 읽어서X
- 디스크 기반 엔진도 OS 캐시 때문에 메모리에서 읽을 수 있다.
- 오히려 디스크용 포맷으로 부호화하는 오버헤드가 줄기 때문에 빠를 수 있다.
    

#### 추가적인 장점

- Redis처럼 우선순위 큐, set 같은 다양한 자료구조를 제공할 수 있다.
- 안티 캐싱처럼 메모리가 부족할 때 일부 데이터를 디스크로 내보내는 방식도 연구된다.

### 09. 트랜잭션 처리(OLTP)와 분석 처리(OLAP)

- **OLTP**
    - 적은 수의 레코드 조회
    - 사용자 입력 기반 삽입/갱신
    - 낮은 지연 시간 중요
    - 현재 상태 중심
    - **디스크 탐색**이 병목이 되기 쉽다.
        
- **OLAP**
    - 많은 수의 레코드 스캔
    - 일부 칼럼만 읽어 집계 수행
    - 비즈니스 분석가/의사결정 지원
    - 이벤트 이력 중심
    - **디스크 대역폭**이 병목이 되기 쉽다.

### 10. 데이터 웨어하우스

- 기업은 보통 여러 개의 OLTP 시스템을 운영한다. 그런데 이 운영 DB에 직접 무거운 분석 질의를 때리면 서비스 성능이 저하될 수 있다. 그래서 분석 전용 DB인 데이터 웨어하우스(data warehouse) 를 별도로 둔다. 데이터 웨어하우스는 여러 OLTP 시스템의 읽기 전용 복사본이다.
    
#### ETL

- OLTP 시스템에서 데이터를    
    - **Extract**
    - **Transform**
    - **Load**  
        하여 데이터 웨어하우스로 옮긴다.

### 11. 분석용 스키마: 별 모양 스키마와 눈꽃송이 스키마

- 분석에서는 보통 **별 모양 스키마(star schema)** 를 많이 쓴다.
- 중심에는 **사실 테이블(fact table)** 이 있다.
    - 각 로우는 하나의 이벤트를 나타낸다.
- 주변에는 **차원 테이블(dimension table)** 이 있다.
    - 제품, 날짜, 매장, 고객, 프로모션 등
    - 즉, 누가/언제/어디서/무엇을/왜 같은 속성 설명

#### 특징

- 사실 테이블은 매우 크다.    
- 차원 테이블은 메타데이터를 풍부하게 담는다.
- 날짜도 차원 테이블로 둬서 공휴일 여부 같은 속성을 함께 저장할 수 있다.

#### 눈꽃송이 스키마

- 차원 테이블을 더 정규화해 세분화한 구조다.
- 하지만 분석가는 보통 별 모양 스키마를 더 다루기 쉽게 여긴다? < 누구맘대로?

### 12. 칼럼 지향 저장소(Column-Oriented Storage)

- 분석 질의는 보통 모든 칼럼을 다 읽지 않는다. 예를 들어 100개 칼럼이 있는 사실 테이블에서 실제 질의는 4~5개 칼럼만 쓸 수 있다. 따라서 로우 지향 저장 방식은 비효율적이다. 한 로우 전체를 읽어오고 필요 없는 칼럼은 버려야 하기 때문이다.

#### 칼럼 저장의 아이디어

- 로우 단위가 아니라 칼럼별로 값들을 모아서 저장한다.
- 그러면 질의에 필요한 칼럼만 읽으면 된다.
- > 디스크에서 읽는 데이터 양이 크게 줄어든다. / 분석 질의에 매우 적합하다.

---

### 13. 칼럼 압축과 비트맵 인코딩

- 칼럼 저장소는 압축과 궁합이 좋다.    
- 같은 칼럼 값들이 반복되는 경우가 많기 때문이다.

#### 비트맵 인코딩

- 각 고유값마다 하나의 비트맵을 둔다. 각 로우가 그 값을 가지면 1, 아니면 0으로 표시한다.

#### 추가 압축

- 대부분 0이 많으면 **런 렝스 인코딩(RLE)** 으로 압축한다. > 필터 조건 계산이 빨라진다. / OR, AND 같은 비트 연산으로 조건 결합 가능
        

---

### 14. 칼럼 저장소에서의 처리 최적화

- 칼럼 저장은 디스크 I/O뿐 아니라 CPU 처리에도 유리하다. 
- 필요한 칼럼만 L1 캐시에 맞는 크기로 가져와 처리할 수 있다. 압축된 블록 위에서 직접 연산하는 벡터화 처리도 가능하다.
    

#### 정렬 순서의 중요성

- 칼럼을 따로따로 정렬하는 것이 아니라,
- 로우 순서를 유지한 채 전체를 어떤 기준으로 정렬한다.
- 자주 쓰는 질의 기준으로 정렬하면 특정 범위 스캔이 쉬워지고 압축률도 높아진다.

---

### 15. 칼럼 저장소의 쓰기 문제

- 칼럼 저장소는 읽기에는 강하지만 쓰기에는 불리하다.
- 압축된 칼럼 파일 중간에 새 값을 끼워 넣거나 제자리 갱신하기 어렵다.
    

#### 해결 방식

- 먼저 인메모리 저장소에 쓰기 모음
- 이후 배치로 디스크 칼럼 파일과 병합
- LSM 트리식으로...
    

---

### 16. 구체화 뷰(materialized view)와 데이터 큐브

- 분석에서 자주 쓰는 집계 결과를 미리 계산해 저장한 것이 구체화 뷰(materialized view) 다. 일반 뷰는 질의 정의만 저장하지만, 구체화 뷰는 실제 결과를 디스크에 저장한다는 점에서 차이가 있다. 
    
#### 데이터 큐브

- 구체화 집계의 특수한 경우 날짜, 제품, 매장 등 여러 차원 기준으로 집계값을 저장한다. 특정 분석 결과를 매우 빠르게 조회할 수 있지만 원시 데이터 질의만큼 유연하지는 않다.

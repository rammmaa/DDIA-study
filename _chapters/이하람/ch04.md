- 4장의 핵심은 데이터가 코드보다 지속성이 크고 시스템에는 예전 코드와 새로운 코드가 동시에 공존할 수 있기 때문에 데이터 부호화 형식이 상위 호환성과 하위 호환성을 지원해야 한다는 것이다. 즉, 단순히 어떻게 저장하느냐의 문제가 아니라, 변경이 계속 일어나는 시스템에서 어떻게 안전하게 발전할 수 있느냐의 문제다.
    

---

### 01. 부호화와 호환성의 기본 개념

- 프로그램은 보통 메모리 안에서는 객체, 구조체, 배열, 해시맵 같은 형태로 데이터를 다룬다.    
- 그런데 파일에 저장하거나 네트워크로 보내려면 데이터를 바이트열로 바꿔야 한다.
    
- **부호화(encoding)**: 메모리 표현 → 바이트열 / 직렬화(serialization), 마샬링(marshalling)
- **복호화(decoding)**: 바이트열 → 메모리 표현 / 역직렬화(deserialization), 언마샬링(unmarshalling)

- 문제는 시스템이 계속 변한다는 점이다. 새로운 기능이 생기면 새로운 필드가 추가될 수 있고, 혹은 기존 필드 의미가 달라지거나 아예 구조가 바뀔 수도 있다. 그런데 현실에서는 코드를 한 번에 다 바꾸지 못하고 서버는 rolling upgrade로 조금씩 배포될 수 있다.
    
- 그래서!! 여기서 중요한 개념이
    
    1. **하위 호환성(backward compatibility)**
        - 새로운 코드가 예전 데이터 형식을 읽을 수 있어야 한다.        
    2. **상위 호환성(forward compatibility)**
        - 예전 코드가 새로운 데이터 형식을 읽을 수 있어야 한다.
            
- 보통 하위 호환성은 새로운 코드가 예전 형식을 알면 되니까 비교적 쉽다. 반면 상위 호환성은 예전 코드가 자신이 모르는 새 필드를 무시할 수 있어야 하므로 더 까다롭다.

### 02. 언어별 형식(language-specific format)

- 많은 프로그래밍 언어는 자체 직렬화 기능을 제공한다.
    
- 예를 들면 Java의 `Serializable`, Ruby의 `Marshal`, Python의 `pickle` 같은 것들이 있다. 이런 방식은 인메모리 객체를 아주 쉽게 저장하고 복원할 수 있어서 편하다.
    
- 하지만 문제점이 많다.
    1. 특정 프로그래밍 언어에 강하게 묶인다.
    2. 다른 언어에서 같은 데이터를 읽기 어렵다.
    3. 복호화 과정에서 보안 문제가 생길 수 있다.
    4. 버전 관리와 상하위 호환성을 제대로 고려하지 않는 경우가 많다.
    5. 성능이나 부호화 결과 크기 면에서도 비효율적일 수 있다.
        
- 즉, 잠깐 쓰는 용도가 아니라 오래 가는 시스템이나 여러 서비스가 얽힌 환경에서는 일반적으로 좋지 못하다...

### 03. JSON, XML, CSV

- JSON, XML, CSV는 대표적인 **텍스트 기반 언어 독립적 형식**이다.
- 사람이 어느 정도 읽을 수 있고, 여러 언어와 도구에서 잘 지원된다는 장점이 있다.
- JSON은 XML보다 덜 장황하고 웹 환경에서 특히 많이 쓰인다.
- CSV도 단순해서 여전히 많이 쓰인다.
    
#### 문제점

- 숫자 표현이 애매한 경우가 있다.
- XML과 CSV는 숫자와 숫자 문자열을 명확히 구분하기 어렵다. JSON은 숫자와 문자열은 구분하지만 정수/부동소수점/정밀도 문제는 남는다. 특히 큰 정수는 자바스크립트 같은 언어에서 정확히 표현되지 않을 수 있다. JSON과 XML은 이진 문자열을 직접 잘 다루지 못한다. 그래서 보통 Base64로 감싸서 보내는데, 그러면 데이터 크기가 약 33% 증가한다.
- XML과 JSON은 스키마를 둘 수는 있다. 하지만 실제로는 스키마를 강제하지 않고 쓰는 경우도 많다. > CSV는 아예 스키마가 없어서 각 칼럼의 의미를 애플리케이션이 직접 해석해야 한다.
- 근데 문제가 너무 많은데요? > 그래도 사람이 읽을 수 있는 건 중요함... 그래서 널리 쓰임...

### 04. 이진 부호화(binary encoding)

- 조직 내부에서만 쓰는 데이터라면 굳이 JSON 같은 최소공통분모 형식을 고집할 필요는 없다. 이 경우 더 작고 빠르게 파싱할 수 있는 이진 형식을 쓸 수 있다.
    
- JSON의 이진 변형들도 있다.(MessagePack, BSON, Smile) 하지만 이런 형식들은 보통 JSON 데이터 모델은 유지한 채 이진화만 한 경우가 많다. 즉, 스키마가 없으면 여전히 필드 이름을 데이터 안에 반복해서 담아야 한다.
- 그래서 단순 이진 JSON은 조금 작아질 수는 있어도, 구조적으로 엄청 큰 이득을 주지는 않는다. 더 큰 이득을 얻으려면 스키마 기반 이진 형식으로 가야 한다.

### 05. 스리프트와 프로토콜 버퍼

- Apache Thrift와 Protocol Buffers는 대표적인 **스키마 기반 이진 부호화 형식**이다. 둘 다 먼저 데이터 구조를 스키마로 정의하고, 그 스키마를 바탕으로 여러 언어용 코드를 생성해 사용한다.
    
- 이 형식들의 핵심은 **필드 이름을 데이터 안에 직접 넣지 않고 숫자 태그(field tag)** 로 대체한다는 점이다. 그래서 JSON처럼 `userName`, `favoriteNumber` 같은 문자열을 반복해서 저장하지 않아도 되어 훨씬 짧게 부호화할 수 있다.
    
- 또 정수는 보통 **가변 길이 정수(variable-length integer)** 로 부호화해서 작은 숫자는 더 적은 바이트를 사용한다. 즉, 단순히 “이진”이라는 점보다도, **스키마를 알고 있기 때문에 불필요한 메타데이터를 줄일 수 있다**는 점이 더 중요하다.
    
- 여기서 중요한 것은 **필드 태그 번호는 바꾸면 안 된다**는 점이다. 필드 이름은 바꿀 수 있어도, 태그 번호를 바꾸면 예전에 저장된 데이터가 어떤 필드를 의미하는지 해석할 수 없게 된다.
    
- 새로운 필드를 추가할 때는 새로운 태그 번호를 부여하면 된다. 그러면 예전 코드는 자신이 모르는 필드를 그냥 무시할 수 있고, 새로운 코드는 예전 필드를 여전히 이해할 수 있으므로 상위 호환성과 하위 호환성을 유지할 수 있다.
    
- 다만 새 필드를 `required`로 추가하면 예전 데이터에는 그 값이 없어서 문제가 생긴다. 그래서 하위 호환성을 유지하려면 **새로 추가하는 필드는 optional이거나 기본값이 있어야 한다**고 이해하면 된다.
    
- 필드를 삭제할 때도 비슷하다. 보통은 optional 필드만 안전하게 삭제할 수 있고, 한 번 사용한 태그 번호는 다시 재사용하면 안 된다.
    
- 필드의 데이터타입을 바꾸는 것도 아주 불가능한 것은 아니지만, 값이 잘리거나 부정확해질 수 있어서 조심해야 한다. 예를 들어 32비트 정수를 64비트 정수로 바꾸면 새로운 코드는 예전 데이터를 읽기 쉽지만, 예전 코드는 새로운 큰 값을 정확히 담지 못할 수 있다.

### 06. 아브로(Avro)

- Avro도 스키마 기반 이진 형식이지만, Thrift나 Protocol Buffers와는 방식이 조금 다르다. 가장 큰 차이는 **필드 태그 번호가 없다는 점**이다.
    
- Avro는 부호화된 데이터 안에 필드 이름이나 타입 정보를 거의 넣지 않는다. 대신 데이터를 읽는 쪽이 스키마를 알고 있다는 전제하에 동작한다. 그래서 같은 데이터를 더 짧게 저장할 수 있다.
    
- Avro의 핵심 개념은 **쓰기 스키마(writer’s schema)** 와 **읽기 스키마(reader’s schema)** 를 구분한다는 것이다. 데이터를 기록할 때 사용한 스키마와, 데이터를 읽을 때 기대하는 스키마가 완전히 같지 않아도, 서로 호환되기만 하면 읽을 수 있게 한다.
    
- 읽는 과정에서는 Avro 라이브러리가 쓰기 스키마와 읽기 스키마를 함께 보고 차이를 해소한다. 쓰기 스키마에만 있는 필드는 무시하고, 읽기 스키마에는 있는데 쓰기 스키마에는 없는 필드는 기본값으로 채운다.
    
- 그래서 Avro에서는 **기본값이 있는 필드만 안전하게 추가하거나 삭제할 수 있다**고 보면 된다. 기본값 없는 필드를 추가하면 예전 데이터에는 그 값이 없어서 하위 호환성이 깨질 수 있고, 기본값 없는 필드를 삭제하면 예전 코드가 기대하던 값을 못 받아서 상위 호환성이 깨질 수 있다.
    
- Avro는 `optional`, `required` 같은 표시 대신 **유니온 타입과 기본값**을 사용한다. 예를 들어 null을 허용하려면 유니온 타입 안에 null을 명시적으로 넣어야 하므로, 어떤 필드가 널일 수 있는지가 더 분명해진다.
    
- 또 Avro는 태그 번호를 수동으로 관리할 필요가 없어서 **동적으로 생성되는 스키마와 잘 맞는다**. 예를 들어 관계형 데이터베이스 스키마에서 Avro 스키마를 자동 생성해서 데이터 덤프를 만들기 쉽기 때문에, Hadoop 같은 환경에서 특히 잘 쓰인다.
    
- 게다가 코드 생성 없이도 사용할 수 있어서 동적 타입 언어와도 잘 맞는다. 이 점은 정적 타입 언어 중심인 Thrift/Protocol Buffers와 구별되는 장점이다.

### 07. 스키마 기반 이진 형식의 장점

- Thrift, Protocol Buffers, Avro 같은 형식은 **텍스트 형식보다 훨씬 짧게 데이터를 저장할 수 있다**. 필드 이름을 생략하거나 최소화할 수 있기 때문이다.
    
- 또 스키마 자체가 좋은 문서 역할을 한다. 데이터를 읽으려면 결국 스키마가 필요하므로, 실제 구조와 문서가 따로 노는 문제가 줄어든다.
    
- 게다가 스키마 변경 전에 상위 호환성과 하위 호환성을 확인할 수 있다. 즉, 단순히 “빠르고 작다”는 점뿐 아니라 **발전성과 유지보수성까지 챙길 수 있다**는 것이 중요하다.
    
- 정적 타입 언어에서는 코드 생성 기능도 큰 장점이다. 컴파일 시점 타입 검사와 IDE 자동완성 같은 지원을 받기 쉬워지기 때문이다.

### 08. 데이터플로 모드

- 이 장은 부호화 형식 자체만 다루는 것이 아니라, 데이터가 시스템 안에서 **어떻게 흐르는가**도 함께 본다. 대표적인 방식은 1) 데이터베이스를 통한 데이터플로, 2) 서비스를 통한 데이터플로, 3) 비동기 메시지 전달을 통한 데이터플로다.
    
- 결국 중요한 것은 “누가 데이터를 부호화하고, 누가 그것을 복호화하는가”이다. 그리고 이때 서로 다른 버전의 코드가 만나더라도 문제가 생기지 않도록 호환성을 유지해야 한다.

### 09. 데이터베이스를 통한 데이터플로

- 데이터베이스에서는 **기록하는 프로세스가 데이터를 부호화하고, 읽는 프로세스가 데이터를 복호화한다**고 볼 수 있다. 이 경우 데이터베이스에 값을 저장하는 일은 일종의 “미래의 자신에게 메시지를 보내는 것”처럼 생각할 수도 있다.
    
- 당연히 하위 호환성은 필요하다. 그렇지 않으면 예전에 저장한 데이터를 나중의 코드가 읽을 수 없기 때문이다. 그런데 현실에서는 여러 버전의 애플리케이션 인스턴스가 동시에 DB를 읽고 쓸 수 있으므로 상위 호환성도 함께 필요하다.
    
- 여기서 추가 문제는 **새로운 필드를 예전 코드가 날려버릴 수 있다는 점**이다. 예를 들어 새로운 버전의 코드가 DB에 새 필드를 저장했는데, 예전 버전의 코드가 그 레코드를 읽고 다시 저장하면 자신이 모르는 필드를 잃어버릴 수 있다. 즉, 애플리케이션 수준에서 **알 수 없는 필드를 보존해야 한다**는 문제가 생긴다.
    
- 또 데이터베이스에서는 **데이터가 코드보다 오래 산다(data outlives code)** 는 점이 중요하다. 코드는 몇 분 만에 새 버전으로 갈아낄 수 있지만, 데이터는 몇 년 동안 남아 있을 수 있다. 그래서 하나의 DB 안에는 서로 다른 시점의 서로 다른 스키마 버전 데이터가 섞여 존재할 수 있다.
    
- 이 때문에 가능하면 전체 데이터를 매번 새 형식으로 다시 쓰지 않고도 읽을 수 있어야 한다. 결국 스키마 발전이란, 저장소 안에 여러 버전의 데이터가 섞여 있어도 전체 시스템은 마치 하나의 일관된 스키마를 쓰는 것처럼 보이게 만드는 기술이라고 할 수 있다.
    
- 백업이나 데이터 웨어하우스 적재용 덤프는 보통 최신 스키마 기준으로 다시 부호화한다. 이 경우에는 Avro 객체 컨테이너 파일이나, 분석 친화적인 Parquet 같은 형식으로 저장하는 것이 적합하다.

### 10. 서비스를 통한 데이터플로: REST와 RPC

- 네트워크를 통해 통신하는 프로세스는 보통 클라이언트와 서버 구조를 이룬다. 서버는 API를 제공하고, 클라이언트는 그 API를 호출해 요청을 보낸다. 여기서도 결국 한쪽이 데이터를 부호화하고 다른 쪽이 그것을 복호화한다는 점은 같다.
    
- 서비스는 데이터베이스와 비슷하게 데이터를 주고받지만, DB처럼 임의 질의를 허용하지는 않는다. 대신 서비스는 미리 정해진 입력과 출력만 허용하며, 이 점이 일종의 캡슐화 역할을 한다. 즉, 서비스는 “무엇을 할 수 있는가”를 더 좁고 명확하게 제어한다.
    
- HTTP를 기본 프로토콜로 쓰는 서비스를 보통 웹 서비스라고 한다. 대표적인 방식은 REST와 SOAP이다.
    
- **REST**는 프로토콜이라기보다 HTTP 원칙을 활용한 설계 철학이다. URL로 리소스를 식별하고, 캐시나 인증, 콘텐츠 협상 같은 HTTP 기능을 적극적으로 활용한다. 비교적 단순하고 공개 API나 마이크로서비스 맥락에서 널리 쓰인다.
    
- 반면 **SOAP**은 XML 기반 프로토콜이다. WSDL을 이용해 API를 기술하고, 코드 생성과 도구 지원에 많이 의존한다. 기능은 많지만 복잡하고 무겁기 때문에, 지금 기준에서는 대체로 REST보다 덜 선호되는 편이다.
    
- 정리하면 REST는 단순성과 생태계가 강점이고, SOAP은 강한 표준화와 도구 지원이 강점이라고 볼 수 있지만, 실제로는 REST 쪽이 더 가볍고 다루기 쉬워서 많이 쓰인다.

### 11. RPC와 그 문제점

- RPC(Remote Procedure Call)는 원격 서비스 호출을 마치 **로컬 함수 호출처럼 보이게 만들려는 아이디어**다. 처음에는 편리해 보이지만, 사실 네트워크 호출은 로컬 함수 호출과 근본적으로 다르다.
    
- 로컬 함수 호출은 보통 성공하거나 예외를 던지거나, 아예 반환하지 않는 정도의 비교적 예측 가능한 형태를 가진다. 하지만 네트워크 요청은 요청이나 응답이 유실될 수 있고, 타임아웃이 날 수 있고, 상대가 느려질 수도 있다. 즉 **실패 방식이 훨씬 다양하고 예측하기 어렵다**.
    
- 또 응답이 없을 때, 요청이 실제로 전달되지 않은 건지, 전달은 됐는데 응답만 유실된 건지 알기 어렵다. 그래서 재시도하면 같은 작업이 중복 수행될 위험이 생긴다. 이 때문에 멱등성(idempotence) 같은 개념이 중요해진다.
    
- 네트워크 호출은 로컬 함수 호출보다 훨씬 느리고 지연 시간 변동도 크다. 또 매개변수는 모두 바이트열로 부호화해야 하므로 객체 전달도 자연스럽지 않다. 게다가 클라이언트와 서버가 서로 다른 언어일 수도 있어서 타입 매핑 문제도 생긴다.
    
- 즉, 네트워크 호출을 로컬 호출처럼 보이게 만들려는 시도는 편리해 보여도 한계가 명확하다. 오히려 REST의 장점 중 하나는, 이것이 네트워크 프로토콜이라는 사실을 숨기지 않는다는 데 있다.
    
- 그래도 RPC는 여전히 많이 쓰인다. gRPC, Thrift RPC, Avro RPC 같은 프레임워크들이 있고, 최근에는 future/promise나 스트리밍 같은 기능을 넣어 네트워크 호출의 비동기성과 실패 가능성을 더 정직하게 드러내는 방향으로 발전하고 있다.
    
- 보통 공개 API는 REST가 강하고, 같은 데이터센터 안의 내부 서비스 간 통신은 이진 부호화 기반 RPC가 성능상 더 유리한 경우가 많다. 결국 무엇을 선택할지는 성능, 디버깅 편의성, 생태계, 조직 내 사용 방식까지 함께 봐야 한다.

### 12. 메시지 전달 데이터플로

- 마지막 방식은 **비동기 메시지 전달(asynchronous message passing)** 이다. 이 방식은 RPC처럼 요청을 보내지만, 직접 상대에게 보내지 않고 **메시지 브로커(message broker)** 라는 중간 단계를 거친다는 점에서 다르다.
    
- 메시지 브로커를 쓰면 수신자가 잠시 죽어 있거나 과부하 상태여도 메시지를 버퍼링할 수 있어서 시스템 안정성이 높아진다. 또 메시지를 다시 전달해서 유실을 줄일 수 있고, 송신자는 수신자의 IP 주소나 포트 번호를 몰라도 된다. 하나의 메시지를 여러 수신자에게 전달할 수 있다는 점도 장점이다.
    
- 즉, 메시지 브로커는 **송신자와 수신자를 느슨하게 결합**시켜 준다. 송신자는 그냥 메시지를 게시하고, 누가 그것을 소비하는지는 크게 신경 쓰지 않아도 된다. 이 때문에 RPC보다 훨씬 유연한 구조를 만들 수 있다.
    
- 메시지 전달은 보통 단방향이다. 즉, 보낸 쪽은 즉시 응답을 기대하지 않는다. 필요하면 응답도 다른 큐나 토픽으로 보낼 수는 있지만, 기본 감각은 RPC보다 느슨한 비동기 통신에 가깝다.
    
- 메시지 브로커 자체는 특정 데이터 모델을 강요하지 않는 경우가 많다. 메시지는 그냥 메타데이터가 붙은 바이트열이므로, 어떤 부호화 형식이든 사용할 수 있다. 따라서 이때도 결국 상위 호환성과 하위 호환성을 갖는 부호화 형식을 선택하는 것이 중요하다.

### 13. 분산 액터 프레임워크

- 액터 모델은 원래 단일 프로세스 안에서 동시성을 다루기 위한 프로그래밍 모델이다. 각 액터는 자신의 로컬 상태를 가지고, 다른 액터와는 비동기 메시지로만 통신한다. 각 액터는 한 번에 하나의 메시지만 처리하므로, 스레드 경쟁 조건이나 잠금을 직접 다루지 않아도 된다.
    
- 분산 액터 프레임워크는 이 모델을 여러 노드로 확장한 것이다. 같은 노드 안의 액터든 다른 노드의 액터든 비슷한 방식으로 메시지를 주고받게 만들려 한다. 다른 노드로 가는 메시지는 결국 네트워크를 타기 때문에 바이트열로 부호화되어 전송된다.
    
- 액터 모델은 원래부터 메시지 유실 가능성을 어느 정도 전제하므로, 위치 투명성이 RPC보다 조금 더 자연스럽게 작동한다. 그래도 순회식 업그레이드를 하려면 결국 예전 버전 액터와 새로운 버전 액터가 동시에 메시지를 주고받을 수 있으므로, 여기서도 상위 호환성과 하위 호환성을 신경 써야 한다.

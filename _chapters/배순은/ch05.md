# 인트로

- 왜 여러 장비를 쓰는가
    - 확장성 Scalability
        - 데이터, 사용자, 읽기/쓰기 요청 많음→ 한 대의 서버가 감당 못함
        - 여러 대 서버로 확장해서, 나누어서 처리, 나누어서 저장
    - 내결함성 Fault tolerance / 고가용성 **High availability**
        - **내결함성:** 고장이 나도 전체 시스템이 망가지지 않게 버티는 능력
        - **고가용성:** 서비스가 가능한 한 오래 켜져 있고, **사용자가 계속 접근할 수 있게 하는** 성질
    - 지연 시간 Latency
        - 요청을 보내고 응답을 받기까지 걸리는 시간
        - 지연 시간 관점에서 여러 장비를 쓰는 이유는: **사용자와 가까운 곳에서 데이터를 제공해서 더 빠르게 응답하기 위해서**
        - 사용자와 지리적으로 가까운 곳의 데이터센터에서 서비스를 제공하기 위해 전 세계 다양한 곳에 서버를 두고 싶을 것
        - 네트워크 패킷이 지구를 반 바퀴 돌아서 올 때까지 기다릴 필요가 없다

# 고부하로 확장

- **고부하:** 서버가 감당해야 할 일이 많아진 상태
    - 예를 들면:
        
        사용자가 많아짐
        
        읽기 요청이 많아짐
        
        쓰기 요청이 많아짐
        
        저장해야 할 데이터가 많아짐
        
        쿼리가 무거워짐
        
    - 이때 서버가 느려지거나 죽지 않게 하려면 시스템을 키워야 합니다. 이것을 **확장 scaling**
- 수직 확장 vertical scaling / 용량 확장 scale up
    - 서버 여러 대로 나누기 전에, 그냥 한 대를 더 큰 컴퓨터로 바꾸는 것
    - 분산 시스템처럼 여러 서버 사이의 복잡한 통신, 복제, 충돌, 일관성 문제를 많이 고민하지 않아도 됩
- 공유 메모리 아키텍처 (shared-memory architecture)
    - CPU가 여러 개 있어도 모두 같은 메모리 공간에 접근할 수 있습니다. 
    디스크도 같은 시스템 안에서 접근
        
        ```
        CPU 1 ┐
        CPU 2 ├── 같은 RAM ─── 같은 Disk
        CPU 3 ┘
        ```
        
    - 그래서 애플리케이션 입장에서는 “서버가 여러 대”가 아니라 **“아주 강한 서버 한 대”**처럼 느껴집
    - 문제:
        - 비용이 너무 빨리 증가
        - 성능도 선형적으로 늘지 않습
        장비 크기 2배 ≠ 처리 성능 2배
    - 핫 스왑 hot-swap (장비를 완전히 끄지 않고 부품을 교체할 수 있다)
        - 예를 들어:
            
            디스크 하나 고장 → 서버를 끄지 않고 디스크 교체
            메모리 모듈 고장 → 중단 없이 교체 가능한 고급 장비도 있음
            CPU 일부 고장 → 고급 장비에서는 교체 가능할 수도 있음
            
        - 그래서 일반 서버보다는 안정적일 수 있습
        - 하지만 중요한 한계:
        **결국 하나의 물리적 위치에 있는 하나의 큰 장비라는 점**
            - 그 장비가 있는 데이터센터에 큰 장애가 나거나, 전원/네트워크/운영체제 수준 문제가 생기면 전체가 영향을 받을 수 있습
            - 전 세계 사용자에게 가까운 곳에서 서비스하는 문제도 해결하기 어렵습

- **공유 디스크 아키텍처 shared-disk architecture**
    - 여러 CPU가 같은 RAM과 디스크를 공유하는 큰 한 대의 컴퓨터
    - 각 장비는 자기 CPU와 자기 RAM을 가지고 있지만, 디스크 저장소는 함께 공유하는 구조
    - 즉, 서버 A, 서버 B, 서버 C가 각각 따로 존재합니다.
    각자 CPU와 메모리는 따로 씁니다.
    하지만 데이터가 저장된 디스크 배열은 공통으로 접근
        
        ```
        서버 A: CPU, RAM ┐
        서버 B: CPU, RAM ├── 공유 디스크 저장소
        서버 C: CPU, RAM ┘
        ```
        
    - 한계: 잠금 경합 lock contention 과 오버헤드 overhead 
    → 서버 많이 붙인다고 빨라지는 게 아님
        - “지금 이 데이터는 내가 수정 중이니까, 다른 서버는 잠깐 기다려”
        - 근데 서버가 많아지고 요청이 많아질수록, 서로 같은 데이터를 잡으려고 기다리는 일이 늘어납 = 잠금경합
        - 조율 비용이 **오버헤드 overhead**
        또한 서버들끼리 “누가 어떤 데이터를 잠갔는지”, “누가 최신 데이터를 가지고 있는지”를 계속 조율해야 합니다.

- 그렇다면 데이터를 여러 장비가 각자 나눠 갖는 방식, 즉 shared-nothing 구조를 생각해야 한다.
    - 중요한 기술이 바로 5장의 **복제 replication**과 6장의 **파티셔닝 partitioning**

## 비공유 아키텍처 (shared-nothing)

- 노드 = 서버
    - **데이터베이스 소프트웨어가 실행되는 서버 한 대**
    또는 클라우드에서는:
    **데이터베이스 소프트웨어가 실행되는 가상 서버 한 대**
- 서로 필요한 게 있으면 반드시 **네트워크로 요청**해야
- 노드 간 코디네이션은 네트워크를 사용해 **소프트웨어 수준에서** 수행한다
    - 조율: **코디네이션 coordination**
    - **DB 소프트웨어가 네트워크 메시지를 주고받으면서 처리
    역할 분담과 장애 대응을 소프트웨어가 함**
    
    ```
    어떤 데이터가 어느 노드에 있는가?
    데이터를 몇 개 복사해 둘 것인가?
    어떤 노드가 쓰기를 받을 것인가?
    한 노드가 죽으면 누가 대신할 것인가?
    여러 노드가 다른 값을 가지고 있으면 무엇을 최신값으로 볼 것인가?
    ```
    
    예를 들어:
    
    ```
    노드 A: “내가 user_id 1~1000 담당할게”
    노드 B: “나는 user_id 1001~2000 담당할게”
    노드 C: “A가 죽으면 내가 A 데이터 복사본으로 응답할게”
    ```
    
    - 비싼 초대형 서버 1대 보다 평범한 서버 여러 대
    가격 대비 성능이 좋을 수 있
- 수평 확장이 쉽습
    - 서버를 옆으로 더 붙이는 방식
    - 서버 대수를 늘려서 처리량을 키우는 방식
- 여러 지역에 분산할 수 있습
    - 비공유 구조는 각 노드가 독립적이기 때문에, 노드를 서로 다른 지역에 둘 수 있습
    
    ```
    한국 노드
    미국 노드
    유럽 노드
    ```
    
    - **지연 시간 latency**이 줄어듭니다.
    - 또한 지역 데이터센터가 통째로 장애가 나도 다른 지역이 살아 있으면 서비스가 계속될 수 있습
- 클라우드와 잘 맞습
    - 클라우드에서는 가상 서버를 여러 대 띄우기 쉽습
    - 그래서 작은 회사도 초대형 장비를 직접 사지 않고, 여러 지역에 분산된 구조를 만들 수 있습

- 단점
    - 성능과 가용성은 좋아질 수 있지만, 대신 **복잡성**이 올라갑
    노드들이 서로의 RAM/Disk를 직접 볼 수 없기 때문입니다.
    
    ```
    어느 노드에 어떤 데이터가 있는지 찾아야 함
    데이터를 여러 노드에 복사하면 복사본들이 달라질 수 있음
    네트워크가 느리거나 끊길 수 있음
    노드 하나가 죽었을 때 복구해야 함
    동시에 여러 노드에 쓰기가 들어오면 충돌할 수 있음
    ```
    
- 데이터베이스 스스로 이런 점을 마술처럼 숨길 수는 없다
    - 분산 DB를 쓰면 겉으로는 그냥 DB 하나처럼 보일 수 있습니다.
    - 복잡성을 DB가 어느 정도 숨겨주긴 하지만, 완전히 없애지는 못합
        
        ```
        앱 → 분산 DB
        ```
        
        하지만 내부에서는 실제로 이런 일이 벌어집니다.
        
        ```
        앱
         ↓
        노드 A, 노드 B, 노드 C, 노드 D
        각 노드에 데이터가 나뉘어 있음
        일부 데이터는 복사되어 있음
        네트워크로 계속 조율함
        ```
        
    - 예를 들어 개발자는 결국 이런 선택을 이해해야 합니다.
        
        ```
        빠른 응답을 우선할 것인가?
        항상 최신 데이터를 읽는 것을 우선할 것인가?
        장애 상황에서도 쓰기를 허용할 것인가?
        데이터 충돌이 나면 어떻게 해결할 것인가?
        ```
        
        이런 게 5장 이후의 핵심 주제
        
- 아무튼 정리
    - **비공유 아키텍처는 여러 서버가 각자 자기 CPU, RAM, Disk를 가지고 독립적으로 움직이되, 네트워크를 통해 서로 조율하면서 하나의 데이터베이스처럼 동작하게 만드는 구조입니다.**
    - 장점은 **싸고, 수평 확장이 쉽고, 여러 지역에 분산하기 좋다**는 것입니다.
    - 단점은 **데이터를 나누고 복사하고 동기화하는 문제가 생겨서 시스템이 훨씬 복잡해진다**

## 복제 대 파티셔닝

- 비공유 구조에서 데이터를 여러 노드에 두는 방법은 크게 두 가지
    
    ```
    복제 replication:
    같은 데이터를 여러 노드에 복사해 둠
    
    파티셔닝 partitioning:
    데이터를 여러 노드에 나누어 저장함
    ```
    
    5장은 그중 **복제 replication**을 다룹
    

# 5장 인트로

- 같은 데이터를 여러 서버에 복사해 두면 좋은데, 그 복사본들을 어떻게 계속 같은 상태로 유지하지?
- 그런데 현실에서는 서버가 죽고, 네트워크가 끊기고, 메시지가 늦게 도착하고, 복제본끼리 값이 달라질 수 있습니다. → 어떻게 복구할지
- 복제란
    - 네트워크로 연결된 여러 장비에 동일한 데이터의 복사본을 유지하는 것
- 왜 복제를 하는가? 이유 3개
    - 1) 사용자와 가까운 곳에 데이터를 두기 위해→ **지연 시간 latency**가 줄어듭
        - 한국 사용자가 미국 서버에 매번 요청하면 느립니다.
        - 네트워크가 지구 반대편을 오가기 때문에 시간이 걸립
    - 2) 장애가 나도 계속 동작하게 하기 위해 → 가용성 availability
    - 3) 읽기 처리량을 늘리기 위해→ 읽기 성능 확장
        
        복제본이 여러 개면:
        
        ```
        읽기 요청 일부 → 노드 A
        읽기 요청 일부 → 노드 B
        읽기 요청 일부 → 노드 C
        ```
        
        이렇게 나눠 처리할 수 있습
        
- 그런데 복제는 언제 어려워지나?
    - 데이터가 시간이 지나도 변하지 않는다면 복제는 쉽다.
    - 문제는 데이터베이스는 보통 계속 바뀐다는 점
- 세 가지 복제 방식
    - 세 가지 알고리즘
    
    ```
    단일 리더 single-leader
    다중 리더 multi-leader
    리더 없는 leaderless
    ```
    
    - 1) 단일 리더 복제 single-leader replication
        
        하나의 노드를 **대표 쓰기 담당자**로 정합니다.
        
        ```
        쓰기 요청 → 리더
        리더 → 팔로워들에게 변경사항 전달
        읽기 요청 → 리더 또는 팔로워
        ```
        
        그림으로 보면:
        
        ```
                  쓰기
        사용자 ─────→ 리더 노드
                      │
                      ├── 복제 → 팔로워 노드 1
                      └── 복제 → 팔로워 노드 2
        ```
        
        가장 흔한 방식입니다.
        
        장점은 구조가 비교적 단순하다는 것입니다.
        
        단점은 리더가 죽으면 새 리더를 뽑아야 하고, 모든 쓰기가 리더를 거쳐야 한다는 것
        
    - 2)다중 리더 복제 multi-leader replication
        
        여러 노드가 쓰기를 받을 수 있습니다.
        
        ```
        한국 리더: 한국 사용자 쓰기 처리
        미국 리더: 미국 사용자 쓰기 처리
        유럽 리더: 유럽 사용자 쓰기 처리
        ```
        
        장점은 각 지역에서 빠르게 쓰기할 수 있다는 것입니다.
        
        단점은 충돌이 생길 수 있습니다.
        
        예를 들어 같은 사용자 이름을 한국 리더와 미국 리더에서 동시에 바꿨다고 해봅시다.
        
        ```
        한국 리더: 이름 = 철수
        미국 리더: 이름 = 민수
        ```
        
    - 3) 리더 없는 복제 leaderless replication
        
        장점은 리더 하나에 의존하지 않는다는 것입니다.
        
        단점은 어느 복제본이 최신인지 판단하는 로직이 더 복잡해집
        
        특정한 리더를 두지 않고, 여러 노드가 직접 읽기/쓰기에 참여합니다.
        
        예를 들어 쓰기할 때 여러 복제본에 동시에 보냅니다.
        
        ```
        쓰기 요청 → 노드 A
        쓰기 요청 → 노드 B
        쓰기 요청 → 노드 C
        ```
        
        그리고 몇 개 이상 성공하면 성공으로 봅니다.
        
        이때 나오는 개념이 나중의 **quorum**입
        
- 동기식 복제와 비동기식 복제
    - 중요한 트레이드오프 중 하나
    - 동기식 복제
        - 리더가 팔로워에게도 데이터가 저장된 것을 확인한 뒤 사용자에게 성공을 알려줍니다.
        - 장점: 복제본이 최신 상태일 가능성이 높음
        - 단점: 느림. 팔로워가 느리면 전체 쓰기도 느려짐
    - 비동기식 복제
        - 리더가 자기 자신에게만 저장하고 바로 성공을 알려줍니다. 팔로워에게는 나중에 전달
        - 장점: 빠름
        - 단점: 리더는 최신인데 팔로워는 아직 옛날 값일 수 있음
        - 이 차이 때문에 **복제 지연 replication lag** 문제
- read-your-writes: 
내가 방금 쓴 글은, 내가 다시 읽을 때 보여야 한다는 보장
    
    예를 들어 내가 프로필 이름을 바꿨습니다.
    
    ```
    이름: 지민 → 지민2
    ```
    
    그런데 바로 새로고침했더니 예전 이름이 보이면 이상합니다.
    
    ```
    내가 방금 바꿈
    그런데 내가 다시 읽으니 옛날 값이 보임
    ```
    
    이걸 막는 보장이 **read-your-writes**
    
- monotonic reads: 
한 번 최신 값을 봤으면, 나중에 더 오래된 값으로 되돌아가 보이면 안 된다는 보장
(**복제본마다 반영 속도가 다르면 이런 일이 생길 수 있습**)
    
    예를 들어 처음 조회했을 때:
    
    ```
    게시글 댓글 수 = 10
    ```
    
    을 봤습니다.
    
    그런데 다시 조회했더니:
    
    ```
    게시글 댓글 수 = 8
    ```
    
    처럼 과거로 돌아가면 이상합니다.
    
    **복제본마다 반영 속도가 다르면 이런 일이 생길 수 있습**
    

# [1] 리더와 팔로워

- 리더 기반 복제, leader-based replication
    - 쓰기 요청은 리더 1대가 받고, 리더가 처리한 변경사항을 팔로워들이 따라 복사한다.
    - 읽기 요청은 리더나 팔로워에서 처리할 수 있
- 복제 서버 replica
    - 데이터베이스의 복사본을 저장하는 각 노드를 복제 서버(replica)
    - 서버 모두 **replica**
    다만 역할에 따라 하나는 **leader** 
    나머지는 **follower**
- 변경이 **모든 복제본에 반영되어야**
    - 그런데 여러 서버가 동시에 있고, 네트워크로 연결되어 있기 때문에 복잡해집니다.
        - 누가 먼저 변경을 받을 것인가?
        - 변경 순서는 누가 정할 것인가?
        - 팔로워가 늦게 따라오면 어떻게 할 것인가?
        - 리더가 죽으면 어떻게 할 것인가?
    - 이 문제를 풀기 위한 가장 흔한 방식이 **리더 기반 복제**
- 리더는 다른 말로:
    - leader = master = primary
- 팔로워는 다른 말로:
    - follower = read replica = slave = secondary = hot standby
- **리더 기반 복제의 기본 구조**
    - 리더 기반 복제에서는 **쓰기의 입구를 하나로 제한**합니다. 
    (변경 요청은 **리더 복제 서버**로 갑)
        - 리더는 먼저 자기 로컬 저장소에 변경을 기록
        
        ```
        모든 쓰기 요청 → 리더
        ```
        
    - 그러면 리더가 순서를 정합니다.
        - 리더는 이 변경사항을 팔로워들에게 보냅 (복제 스트림)
        
        ```
        리더가 정한 순서: A 먼저, B 나중
        ```
        
    - 팔로워들은 그 순서를 그대로 따라갑니다.
    (팔로워들은 리더에게 받은 변경사항을 자기 DB에 똑같이 적용)
        
        ```
        팔로워1: A → B
        팔로워2: A → B
        ```
        
        그래서 최종 결과가 같아질 수 있습
        
- 데이터 변경을 복제 로그(replication log)나 변경 스트림(change stream)의 일부로 팔로워에게 전송한다.
    - 변경 기록의 흐름이 **replication log** 또는 **change stream**
    : 데이터 변경 기록
    - 중요한 건 팔로워가 SQL을 새로 “생각해서” 실행하는 게 아니라, **리더가 이미 정한 변경 순서를 그대로 받아서 적용한다**는 점
- 리더가 처리한 것과 동일한 순서로 모든 쓰기를 적용한다
    - 팔로워들은 리더가 정한 순서대로 변경을 적용해야 합니다.
    이래야 복제본들이 같은 상태를 유지할 수 있습
- 팔로워는 클라이언트 입장에서 **읽기 전용 read-only**입니다.
    - 그래서 follower를 **read replica**라고도 부릅니다.
        
        ```
        팔로워 = 읽기용 복제본
        ```
        
- 그런데 문제: 팔로워가 늦을 수 있음
    - 리더가 변경사항을 팔로워에게 보내더라도, 팔로워가 즉시 따라잡는다는 보장은 없습니다.
    - 이때 시점 2에 사용자가 팔로워에서 읽으면 옛날 값을 볼 수 있습니다.
    - 이것이 뒤에서 나오는 **복제 지연 replication lag** 문제입니다.
    - 그래서 리더 기반 복제는 **구조가 단순하지만, 읽기 일관성 문제가 생길 수 있습**

## (1) 동기식 대 비동기식 복제

- 복제에서 리더가 팔로워의 확인 응답을 기다리는지
- **동기식 복제**는 리더가 팔로워의 확인을 기다린 뒤 사용자에게 성공을 알립니다. 그래서 팔로워가 최신 데이터를 가지고 있음을 보장할 수 있지만, 팔로워가 느리거나 죽으면 쓰기 작업이 멈춥니다.
- **비동기식 복제**는 리더가 팔로워에게 변경 내용을 보내기만 하고 응답을 기다리지 않습니다. 그래서 빠르고 가용성이 좋지만, 리더가 갑자기 죽으면 아직 팔로워에게 복제되지 않은 데이터가 유실될 수 있습니다.
- **반동기식 복제**는 현실적인 타협안입니다. 보통 팔로워 하나만 동기식으로 두고 나머지는 비동기식으로 둡니다. 이렇게 하면 최소한 리더와 동기식 팔로워 하나에는 최신 데이터가 있으면서도, 모든 팔로워를 기다리느라 전체 시스템이 멈추는 문제를 줄일 수 있습니다

## (2) 새로운 팔로워 설정

- 새 팔로워를 만들 때는 리더의 DB 파일을 그냥 복사하면 안 됩니다. 복사하는 동안에도 데이터베이스에는 계속 쓰기가 발생하기 때문에, 파일마다 서로 다른 시점의 상태가 섞일 수 있습니다.
- 그래서 보통은 먼저 리더의 **일관된 스냅샷**을 뜹니다. 이 스냅샷은 “복제 로그의 어느 위치까지 반영된 상태인지”와 연결되어 있어야 합니다. PostgreSQL에서는 이를 LSN, MySQL에서는 binlog coordinate 같은 이름으로 부릅니다.
- 그 다음 스냅샷을 새 팔로워에 복사하고, 새 팔로워는 리더에게 “스냅샷 이후 발생한 변경 로그”를 요청합니다. 새 팔로워가 그 밀린 변경분, 즉 backlog를 모두 처리하면 리더를 따라잡은 상태가 됩니다. 이후에는 리더에서 새로 발생하는 변경을 계속 받아 처리하면 정상적인 팔로워로 동작할 수 있습니다.

## (3) 노드 중단 처리

- 노드 중단 처리는 **개별 서버가 죽어도 전체 시스템을 계속 동작시키기 위한 방법**입니다.

### 1) 팔로워 장애: 따라잡기 복구

- 팔로워 장애는 비교적 쉽습니다. 팔로워는 자신이 마지막으로 처리한 로그 위치를 알고 있으므로, 다시 살아난 뒤 리더에게 “내가 놓친 변경분을 보내달라”고 요청하면 됩니다. 밀린 로그를 모두 적용하면 리더를 따라잡고 다시 정상 팔로워가 됩니다.

### 2) 리더 장애: 장애 복구

- 리더 장애는 어렵습니다. 팔로워 중 하나를 새 리더로 승격해야 하고, 클라이언트와 다른 팔로워들이 새 리더를 사용하도록 재설정해야 합니다. 이 과정을 failover라고 합니다.
- failover의 어려움은 여러 가지입니다. 비동기식 복제에서는 기존 리더의 일부 쓰기가 새 리더에 없어서 데이터가 유실될 수 있습니다. 외부 캐시나 저장소와 DB 상태가 어긋날 수도 있습니다. 두 노드가 동시에 리더라고 믿는 split brain이 발생하면 데이터가 손상될 수 있습니다. 또한 timeout을 너무 길게 잡으면 복구가 늦고, 너무 짧게 잡으면 불필요한 failover가 생길 수 있습니다.
- 결국 이 부분의 핵심은 **팔로워 복구는 로그를 따라잡으면 되지만, 리더 복구는 새 리더 선출·클라이언트 재설정·데이터 유실·split brain까지 고려해야 하는 훨씬 어려운 문제**라는 것

## (4) 복제 로그 구현

- 복제 로그 구현은 **리더의 변경 사항을 팔로워에게 어떤 형태로 전달할지**에 대한 문제

### 1) 구문 기반 복제

- **구문 기반 복제**는 리더가 실행한 SQL 문장을 그대로 팔로워에게 보내는 방식입니다. 단순하지만 `NOW()`, `RAND()` 같은 비결정적 함수, auto-increment처럼 실행 순서에 민감한 구문, 트리거와 스토어드 프로시저의 부수 효과 때문에 리더와 팔로워 결과가 달라질 수 있습니다.

### 2) 쓰기 전 로그배송

- **WAL 배송**은 데이터베이스 저장 엔진이 내부적으로 사용하는 write-ahead log를 팔로워에게 보내는 방식입니다. 팔로워가 리더의 내부 로그를 그대로 재생하므로 정확한 복제본을 만들 수 있지만, 로그가 너무 저수준이라 DB 버전이나 저장 엔진 구조에 강하게 묶입니다. 그래서 무중단 업그레이드가 어려워질 수 있습니다.

### 3) 논리적(로우 기반) 로그 복제

- **논리적/로우 기반 로그 복제**는 SQL 문장이 아니라 실제로 바뀐 row의 내용을 기록합니다. INSERT는 새 row 값, DELETE는 삭제할 row의 식별 정보, UPDATE는 바뀐 row의 새 값을 기록합니다. 저장 엔진 내부 파일 구조와 분리되어 있어 호환성이 좋고, 외부 시스템이 읽기 쉬워 CDC에도 유용합니다.

### 4) 트리거 기반 복제

- **트리거 기반 복제**는 데이터 변경이 발생했을 때 트리거나 외부 애플리케이션 로직을 실행해 복제를 처리하는 방식입니다. 일부 데이터만 복제하거나 서로 다른 종류의 DB로 복제하는 등 유연성이 크지만, DB 내장 복제보다 오버헤드와 복잡도가 크고 버그 가능성도 높습니다.
- **구문 기반은 “명령”을 복제하고, WAL 배송은 “DB 내부 기록”을 복제하고, 논리적 로그는 “변경 결과”를 복제하고, 트리거 기반은 “사용자 정의 변경 감지 로직”으로 복제하는 방식**

# [2] 복제 지연 문제

- 복제는 단순히 장애 대비용만이 아니라, **읽기 요청을 여러 팔로워에게 분산하기 위한 확장성 목적**으로도 사용됩니다. 웹 서비스는 보통 쓰기보다 읽기가 훨씬 많기 때문에, 팔로워를 여러 대 두고 읽기 요청을 나눠 처리하면 리더의 부담을 줄일 수 있습니다.
- 하지만 이런 읽기 확장은 보통 **비동기 복제**에서 현실적으로 가능합니다. 모든 팔로워를 동기식으로 복제하면 팔로워 하나만 느려져도 리더의 쓰기가 막힐 수 있기 때문입니다.
- 비동기 복제에서는 리더의 변경이 팔로워에 즉시 반영되지 않을 수 있습니다. 그래서 같은 데이터를 읽어도 리더에서는 최신값이 보이고, 팔로워에서는 예전값이 보일 수 있습니다. 이 차이가 **복제 지연(replication lag)** 입니다.
- 이런 시스템은 보통 **최종적 일관성(eventual consistency)** 을 가집니다. 즉, 지금 당장은 리더와 팔로워가 다를 수 있지만, 새로운 쓰기가 멈추고 시간이 지나면 결국 팔로워가 리더를 따라잡아 같은 상태가 된다는 뜻입니다.
- **팔로워를 늘리면 읽기 성능은 좋아지지만, 비동기 복제 때문에 사용자가 잠시 오래된 데이터를 볼 수 있고, 이것이 복제 지연 문제**

## (1) 자신이 쓴 내용 읽기

- **동기 복제에서 사용자가 방금 쓴 데이터를 다시 읽었을 때 안 보일 수 있는 문제**를 설명합니다.
- 쓰기 요청은 리더에 반영되지만, 읽기 요청은 팔로워에서 처리될 수 있습니다. 그런데 팔로워가 아직 리더의 최신 변경을 복제받지 못했다면, 사용자가 방금 쓴 댓글이나 프로필 변경이 보이지 않을 수 있습니다. 사용자 입장에서는 데이터가 유실된 것처럼 느껴집니다.
- 이를 막기 위한 보장이 **쓰기 후 읽기 일관성(read-after-write consistency)** 또는 **자신의 쓰기 읽기 일관성(read-your-writes consistency)** 입니다. 이 보장은 모든 사용자가 항상 최신 데이터를 본다는 뜻이 아니라, **적어도 사용자는 자신이 제출한 변경사항을 다시 읽을 때 반드시 볼 수 있어야 한다**는 뜻입니다.
- 구현 방법으로는, 사용자가 수정할 수 있는 데이터는 리더에서 읽게 하거나, 사용자가 최근에 쓴 직후 일정 시간 동안 리더에서 읽게 하거나, 클라이언트가 마지막 쓰기 타임스탬프를 기억해서 그 시점까지 반영한 팔로워에서만 읽게 하는 방식이 있습니다.
- 여러 데이터센터나 여러 기기를 사용하는 경우에는 더 복잡합니다. 한 기기에서 쓴 내용을 다른 기기에서도 바로 볼 수 있어야 하므로, 마지막 쓰기 시점 같은 메타데이터를 중앙에서 관리하거나 요청을 적절한 데이터센터로 라우팅해야 합니다.
- **복제 지연이 있어도 “내가 쓴 것은 내가 바로 볼 수 있게 하자”가 쓰기 후 읽기 일관성의 핵심**

## (2) 단조 읽기

- **단조 읽기(monotonic reads)** 는 비동기 복제에서 사용자가 여러 번 읽을 때 **시간이 거꾸로 가는 것처럼 보이는 현상**을 막는 보장입니다.
- 복제 지연 때문에 팔로워마다 최신도가 다를 수 있습니다. 사용자가 첫 번째 요청에서는 최신 팔로워에서 읽고, 두 번째 요청에서는 오래된 팔로워에서 읽으면, 처음에는 보였던 댓글이 나중에는 사라진 것처럼 보일 수 있습니다.
- 단조 읽기는 이런 상황을 막습니다. 즉, 사용자가 한 번 더 최신 데이터를 봤다면, 그 이후에는 그보다 더 오래된 데이터를 보지 않게 합니다. 오래된 값을 처음에 보는 것은 가능하지만, 새 값을 본 뒤 다시 옛값으로 돌아가는 것은 허용하지 않습니다.
- 구현 방법 중 하나는 각 사용자의 읽기 요청을 항상 같은 복제 서버로 보내는 것입니다. 예를 들어 사용자 ID의 해시값으로 팔로워를 선택하면 같은 사용자는 계속 같은 팔로워에서 읽게 됩니다. 다만 그 팔로워가 장애가 나면 다른 팔로워로 재라우팅해야 하므로, 이때도 이전보다 더 오래된 데이터를 읽지 않도록 추가 처리가 필요합니다.
- **단조 읽기는 “항상 최신은 아니어도, 적어도 사용자가 본 데이터가 과거로 되돌아가 보이지 않게 하는 보장”**

## (3) 일괄된 순서로 읽기

- **일관된 순서로 읽기(consistent prefix reads)** 는 복제 지연으로 인해 **인과관계가 뒤집혀 보이는 문제**를 막는 보장입니다.
- 예를 들어 “질문 → 답변”이라는 순서로 쓰기가 발생했다면, 읽는 사람도 질문을 먼저 보고 답변을 나중에 봐야 합니다. 그런데 파티션된 데이터베이스에서는 질문과 답변이 서로 다른 파티션에 저장될 수 있고, 각 파티션의 복제 지연이 다르면 답변이 질문보다 먼저 보일 수 있습니다.
- Consistent prefix reads는 사용자가 전체 쓰기 순서의 중간이 뒤섞인 상태를 보지 않도록 합니다. 최신 데이터 전체를 보장하는 것은 아니지만, 적어도 쓰기의 순서가 깨진 상태는 보지 않게 합니다. 예를 들어 `질문만 보임`은 가능하지만, `답변만 보임`은 안 됩니다.

## (4) 복제 지연을 위한 해결책

- 해결책으로는 인과관계가 있는 쓰기를 같은 파티션에 저장하거나, 시스템이 쓰기 간 인과관계를 명시적으로 추적하는 방법이 있습니다. 다만 둘 다 구현상 제약과 복잡도가 있습니다.
- 마지막으로 이 내용은 트랜잭션과 연결됩니다. 복제 지연 문제를 애플리케이션 코드에서 직접 처리할 수도 있지만 복잡하고 실수하기 쉽습니다. 트랜잭션은 이런 일관성 문제를 데이터베이스가 대신 다뤄 주기 위한 장치입니다. 다만 분산 시스템에서는 트랜잭션이 성능과 가용성 측면에서 비용이 크기 때문에, 어떤 보장이 필요한지 신중히 선택해야 합니다.
- **일관된 순서로 읽기는 “최신은 아니어도, 원인보다 결과가 먼저 보이는 이상한 상태는 보여주지 말자”는 보장**

# [3] 다중 리더 복제

- **다중 리더 복제**는 쓰기를 받을 수 있는 리더를 여러 개 두는 복제 방식입니다. 각 리더는 자기에게 들어온 쓰기를 처리하고, 그 변경 사항을 다른 리더들에게 복제합니다. 그래서 마스터-마스터 복제 또는 액티브/액티브 복제라고도 부릅니다.

## (1) 다중 리더 복제의 사용 사례

### 1) 다중 데이터센터 운영

- 다중 리더 복제는 특히 **여러 데이터센터를 운영할 때** 유용합니다. 각 데이터센터에 리더를 두면 사용자는 가까운 데이터센터에 쓰기 요청을 보낼 수 있어 지연 시간이 줄어듭니다. 또한 한 데이터센터가 장애가 나도 다른 데이터센터는 계속 쓰기를 받을 수 있고, 데이터센터 간 네트워크가 잠시 끊겨도 각 지역은 독립적으로 동작할 수 있습니다.

### 2) 오프라인 작업을 하는 클라이언트

- 또 다른 사용 사례는 **오프라인 작업을 하는 클라이언트**입니다. 휴대전화나 노트북의 캘린더 앱처럼 인터넷이 없어도 데이터를 보고 수정해야 하는 경우, 각 기기는 로컬 DB에 먼저 쓰고 나중에 서버 및 다른 기기와 동기화합니다. 이 구조는 각 기기가 작은 리더처럼 동작한다는 점에서 다중 리더 복제와 비슷합니다.

### 3) 협업편집

- 세 번째 사용 사례는 **협업 편집**입니다. 여러 사용자가 같은 문서를 동시에 편집하면 각 사용자의 화면에는 로컬 변경이 즉시 반영되고, 그 변경이 다른 사용자와 서버로 비동기 복제됩니다. 이 역시 다중 리더 복제와 비슷한 문제를 가집니다.
- 하지만 다중 리더 복제의 가장 큰 단점은 **쓰기 충돌**입니다. 같은 데이터를 서로 다른 리더에서 동시에 수정하면, 나중에 복제할 때 어떤 값을 최종값으로 삼아야 하는지 결정해야 합니다. auto-increment, 트리거, 무결성 제약조건 같은 DB 기능과도 예상치 못한 문제가 생길 수 있습니다.
- **다중 리더 복제는 여러 곳에서 쓰기를 받을 수 있어 성능·가용성·오프라인 지원에 유리하지만, 동시에 같은 데이터를 수정할 수 있기 때문에 충돌 해결이 가장 큰 문제인 구조**

## (4) 쓰기 충돌 다루기

- 다중 리더 복제의 가장 큰 문제는 **쓰기 충돌**입니다. 서로 다른 리더가 같은 데이터를 동시에 수정하면, 각 리더에서는 쓰기가 성공하지만 나중에 복제할 때 충돌이 발견됩니다. 예를 들어 같은 위키 페이지 제목을 한 사용자는 `B`로, 다른 사용자는 `C`로 바꾸면 최종 제목을 무엇으로 할지 결정해야 합니다.

### 1) 동기 대 비동기충돌감지

- 단일 리더에서는 모든 쓰기가 하나의 리더를 거치므로 충돌을 즉시 감지하거나 순서를 정하기 쉽습니다. 반면 다중 리더에서는 각 리더가 로컬 쓰기를 먼저 성공시킨 뒤 나중에 비동기 복제를 하므로, 충돌 감지가 늦어질 수 있습니다.

### 2) 충둘회피

- 가장 쉬운 전략은 **충돌 회피**입니다. 특정 레코드의 모든 쓰기를 항상 같은 리더로 보내면 충돌 가능성이 줄어듭니다. 하지만 장애, 사용자 이동, 라우팅 변경이 생기면 이 전략이 깨질 수 있습니다.

### 3) 일관된상태 수렴

- 충돌이 생겼다면 모든 복제 서버가 결국 같은 상태가 되도록 **수렴**해야 합니다. 이를 위해 `last write wins`처럼 하나의 쓰기를 승자로 고르거나, 특정 리더에 우선순위를 주거나, 값을 병합하거나, 여러 버전을 모두 저장한 뒤 애플리케이션이나 사용자가 나중에 해결할 수 있습니다.

### 4) 사용자 정의 충돌 해소 로직

- 충돌 해결 로직은 애플리케이션마다 다릅니다. 어떤 시스템은 쓰기 중에 충돌을 자동 처리하고, 어떤 시스템은 읽기 시 여러 버전을 반환해서 애플리케이션이 해결하게 합니다. CRDT, 병합 가능한 데이터 구조, operational transformation 같은 자동 충돌 해결 기법도 있습니다.

### 5) 충돌은 무엇인가?

- 마지막으로 충돌은 단순히 “같은 필드를 동시에 수정한 경우”만이 아닙니다. 회의실 예약처럼 서로 다른 쓰기가 합쳐졌을 때 비즈니스 규칙이 깨지는 것도 충돌입니다.
- **다중 리더 복제는 여러 곳에서 쓰기를 받아 성능과 가용성을 높이지만, 동시에 발생한 쓰기들이 충돌할 수 있으므로 반드시 충돌 감지·해결·수렴 전략이 필요**

## (5) 다중 리더 복제 토폴로지

- **복제 토폴로지**는 다중 리더 복제에서 한 리더의 쓰기가 다른 리더들에게 어떤 경로로 전달되는지를 나타내는 연결 구조입니다.
- 대표적인 토폴로지에는 **원형 토폴로지**, **별 모양 토폴로지**, **전체 연결 토폴로지**가 있습니다. 원형은 각 리더가 다음 리더에게 전달하는 구조이고, 별 모양은 중심 노드를 통해 전달하는 구조입니다. 이 둘은 단순하지만 중간 노드가 장애 나면 복제 흐름이 막힐 수 있습니다.
- **전체 연결 토폴로지**는 모든 리더가 서로 직접 연결되는 방식입니다. 중간 노드에 덜 의존하므로 장애에는 더 강하지만, 네트워크 경로 차이 때문에 복제 메시지가 잘못된 순서로 도착할 수 있습니다.
- 그림 5-9에서는 먼저 `insert key='x', value=1`이 발생하고, 그 후 `update value=value+1 where key='x'`가 발생합니다. 하지만 어떤 리더에는 update가 insert보다 먼저 도착할 수 있습니다. 그러면 아직 존재하지 않는 row를 업데이트하려는 이상한 상황이 됩니다.
- 이 문제는 단순히 타임스탬프를 붙이는 것만으로는 해결하기 어렵습니다. 분산 시스템에서는 각 노드의 시계가 완전히 동기화되어 있다고 믿을 수 없기 때문입니다. 그래서 인과 순서를 추적하기 위해 **버전 벡터(version vector)** 같은 기법을 사용할 수 있습니다.
- **다중 리더 복제에서는 변경 사항을 어떻게 퍼뜨릴지뿐 아니라, 그 변경들이 올바른 인과 순서로 적용되는지도 반드시 보장해야**

# [4] 리더 없는 복제

**리더 없는 복제**는 특정 리더 없이, 클라이언트가 여러 복제 서버에 직접 읽기와 쓰기 요청을 보내는 방식입니다. 리더가 쓰기 순서를 정하지 않으므로, 하나의 리더가 죽어서 전체 쓰기가 막히는 문제를 줄일 수 있습니다.

예를 들어 복제 서버가 3개 있을 때, 클라이언트가 3개 서버 모두에 쓰기를 보내고 그중 2개가 성공하면 쓰기 성공으로 간주할 수 있습니다. 한 서버가 다운되어 쓰기를 놓쳐도 전체 작업은 성공할 수 있습니다.

## (1) 노드가 다운됐을 때 데이터베이스에 쓰기

하지만 다운되었던 서버가 나중에 다시 살아나면 오래된 값을 가지고 있을 수 있습니다. 그래서 읽을 때도 여러 복제 서버에 병렬로 요청을 보내고, 버전 번호를 비교해서 최신 값을 선택합니다.

### 1) 읽기 복구와 안티 엔트로피

오래된 복제본을 고치는 방법에는 **읽기 복구**와 **안티 엔트로피 처리**가 있습니다. 읽기 복구는 읽기 요청 중 오래된 값을 발견하면 그 서버에 최신 값을 다시 써 주는 방식입니다. 안티 엔트로피는 백그라운드에서 복제 서버들끼리 데이터를 비교해 누락된 변경을 복사하는 방식입니다.

### 2) 읽기와 쓰기를 위한 정족수

정족수(quorum)는 성공으로 인정하기 위해 필요한 최소 응답 수입니다. `n`은 전체 복제 서버 수, `w`는 쓰기 성공에 필요한 서버 수, `r`은 읽기 성공에 필요한 서버 수입니다. `w + r > n`이면 읽기한 서버 집합과 최근 쓰기에 성공한 서버 집합이 적어도 하나는 겹치므로, 최신 값을 찾을 가능성이 생깁니다.

예를 들어 `n = 3, w = 2, r = 2`라면 3개 중 2개 서버에 쓰기 성공하면 되고, 읽기도 2개 서버에서 응답을 받으면 됩니다. 노드 하나가 죽어도 읽기와 쓰기를 계속할 수 있습니다.

**리더 없는 복제는 리더 없이 여러 복제 서버에 직접 요청을 보내고, 정족수와 버전 비교를 통해 일부 노드 장애를 견디면서 최신 값을 찾아내는 복제 방식**

## (2) 정족수 일관성의 한계

**정족수 일관성의 한계**는 `w + r > n` 조건을 만족해도 항상 최신값을 읽는 것이 보장되지는 않는다는 점입니다.

정족수 방식에서는 `n`개의 복제 서버 중 `w`개에 쓰기가 성공하고, 읽을 때 `r`개 서버에서 읽습니다. `w + r > n`이면 읽기 집합과 쓰기 집합이 최소 하나는 겹치기 때문에 최신값을 읽을 가능성이 높아집니다.

하지만 실제 시스템에서는 예외가 있습니다. 느슨한 정족수를 쓰면 읽기와 쓰기 노드 집합이 실제로 겹치지 않을 수 있습니다. 두 쓰기가 동시에 발생하면 어느 쓰기가 먼저인지 불분명할 수 있습니다. 읽기와 쓰기가 동시에 일어나면 읽기가 옛값을 볼 수도 있고 새값을 볼 수도 있습니다. 실패한 쓰기가 일부 서버에는 반영될 수도 있습니다. 장애 복구 과정에서 옛값이 다시 나타날 수도 있습니다.

따라서 정족수는 최신값을 읽을 가능성을 높여 주지만, 강한 일관성이나 트랜잭션 보장을 제공하는 것은 아닙니다. Dynamo 스타일 데이터베이스는 보통 최종적 일관성을 허용하는 사용 사례에 맞게 설계되어 있습니다.

### 1) 최신성 모니터링

**최신성 모니터링**도 중요합니다. 리더 기반 복제에서는 리더와 팔로워의 로그 위치 차이를 통해 복제 지연을 비교적 쉽게 측정할 수 있습니다. 하지만 리더 없는 복제에서는 전체 쓰기 순서를 고정하기 어렵고, 읽기 복구만 사용하는 경우 거의 읽히지 않는 데이터가 오래된 상태로 남을 수 있어 모니터링이 더 어렵습니다.

 **정족수는 오래된 값을 읽을 확률을 줄여 주지만 완전히 없애지는 못하며, 운영에서는 복제본이 얼마나 오래되었는지 계속 측정해야 합니다.**

## (3) 느슨한 정족수와 암시된 핸드오프

**느슨한 정족수(sloppy quorum)** 는 원래 데이터를 저장해야 하는 담당 복제 서버에 접근할 수 없을 때, 현재 연결 가능한 다른 노드에 임시로 데이터를 저장해서 쓰기를 성공시키는 방식입니다. 즉, 원래 담당 서버가 아니어도 일단 쓸 수 있는 곳에 저장합니다.

**암시된 핸드오프(hinted handoff)** 는 이렇게 임시로 저장한 데이터를 나중에 네트워크나 장애가 복구되었을 때 원래 담당 서버로 넘겨주는 과정입니다. 임시 저장 노드는 “이 데이터는 원래 어느 서버가 가져야 하는지”에 대한 힌트를 가지고 있다가, 해당 서버가 돌아오면 전달합니다.

이 방식의 장점은 쓰기 가용성이 높다는 것입니다. 일부 노드나 네트워크가 끊겨도 사용자는 계속 쓰기를 할 수 있습니다. 하지만 단점은 읽을 때 최신값을 항상 보장하지 못한다는 것입니다. 최신값이 원래 담당 서버가 아닌 임시 노드에만 있을 수 있기 때문입니다. 따라서 느슨한 정족수는 전통적인 의미의 정족수라기보다는 “데이터가 어딘가에는 저장되었다”는 지속성 보장에 가깝습니다.

### 1) 다중 데이터센터운영

다중 데이터센터 운영에서도 리더 없는 복제는 유용합니다. 클라이언트는 보통 가까운 로컬 데이터센터 안의 노드들로부터 정족수 응답을 기다리고, 다른 데이터센터로의 복제는 백그라운드에서 비동기적으로 진행됩니다. 이렇게 하면 데이터센터 간 지연이나 중단의 영향을 줄이고, 빠른 응답과 높은 가용성을 얻을 수 있습니다.

**느슨한 정족수는 “원래 서버가 안 되면 다른 서버에라도 일단 저장하자”이고, 암시된 핸드오프는 “나중에 원래 서버가 돌아오면 그 데이터를 돌려주자”는 방식**

## (4) 동시 쓰기 감지

**동시 쓰기 감지**는 리더 없는 복제에서 여러 클라이언트가 같은 key에 동시에 쓰는 상황을 다룹니다. 네트워크 지연과 장애 때문에 각 복제 서버가 쓰기를 서로 다른 순서로 받을 수 있으므로, 단순히 “나중에 도착한 값으로 덮어쓰기”를 하면 복제본들이 서로 다른 값을 가지거나 데이터가 유실될 수 있습니다.

### 1) 최종 쓰기 승리(동시 쓰기 버리기)

가장 단순한 해결책은 **최종 쓰기 승리(LWW)** 입니다. 타임스탬프나 버전 번호를 기준으로 가장 최신이라고 판단되는 값 하나만 남깁니다. 이 방식은 복제본들이 결국 같은 값으로 수렴하게 하지만, 성공한 쓰기 중 일부가 조용히 사라질 수 있으므로 데이터 손실 위험이 있습니다.

### 2) ”이전 발생" 관계와 동시성

더 안전한 방식은 **이전 발생 관계(happens-before)** 를 추적하는 것입니다. 어떤 작업 B가 작업 A를 알고 있거나 A의 결과를 바탕으로 실행되었다면 A는 B보다 이전에 발생한 것입니다. 반대로 두 작업이 서로를 모른다면 동시 발생한 작업입니다.

### 3) 이전 발생 관계 파악하기

동시 발생한 값들은 서로 덮어쓰면 안 되므로 **형제 값(sibling)** 으로 보존됩니다. 예를 들어 장바구니에서 한 사용자가 우유를 넣고 다른 사용자가 달걀을 넣었다면, 둘 중 하나를 버리지 않고 두 값을 모두 보존한 뒤 애플리케이션이 병합해야 합니다.

### 4) 동시에 쓴 값 병합

장바구니처럼 추가만 있는 경우에는 합집합으로 병합할 수 있지만, 삭제가 있는 경우에는 삭제 사실을 나타내는 **툼스톤(tombstone)** 이 필요합니다. 그렇지 않으면 삭제한 상품이 병합 과정에서 다시 살아날 수 있습니다.

### 5) 버전벡터

단일 복제본에서는 버전 번호로 작업 간 관계를 추적할 수 있지만, 여러 복제본이 있는 리더 없는 복제에서는 **버전 벡터(version vector)** 가 필요합니다. 버전 벡터는 각 복제본별 버전 번호를 기록하여 어떤 값이 어떤 값을 포함하는지, 또는 두 값이 동시 발생했는지를 판단하게 해줍니다.

**리더 없는 복제에서 충돌을 안전하게 다루려면 “무엇이 더 최신인가”보다 “어떤 쓰기가 어떤 쓰기를 알고 있었는가”를 추적해야 하며, 이를 위해 버전 번호와 버전 벡터를 사용**

- **시스템은 계속 바뀌므로, 데이터 형식도 바뀜**
- **그래서 새 버전과 옛 버전이 함께 돌아갈 수 있도록 호환성을 고려한 부호화와 스키마 설계가 필요함**

# [1] 데이터 부호화 형식 141

- 프로그램 내부 표현과 저장/전송 표현은 다르다.
- 그래서 두 표현 사이를 오가는 변환이 꼭 필요하다.
- 이 문제를 해결하려고 JSON 같은 여러 **부호화 형식과 라이브러리**가 존재한다.

## (1) 언어별 형식

### 핵심 요약

- 많은 언어는 객체를 바이트열로 바꾸는 내장 기능을 제공함
- 이 기능은 코드가 적고 사용이 쉬워서 편리함
- 하지만 보통 다음 문제가 큼:
    - 특정 언어에 종속적이라 다른 언어와 호환이 어려움
    - 복호화 과정에서 보안 취약점이 생길 수 있음
    - 버전 변화와 호환성 관리가 어려움
    - 성능과 데이터 크기도 비효율적일 수 있음
- 그래서 아주 일시적인 목적이 아니면 일반적으로 추천되지 않음

## (2) JSON과 XML, 이진 변형

- JSON, XML, CSV는 널리 쓰이는 언어 독립적 텍스트 기반 형식임
- 장점:
    - 사람이 읽을 수 있음
    - 여러 언어와 시스템에서 쉽게 사용 가능함
    - 데이터 교환용으로 매우 실용적임
- 단점:
    - 숫자 표현이 애매함
        - 정수/실수/정밀도 문제가 생길 수 있음
    - 큰 숫자에서 오차 문제가 생길 수 있음
        - 특히 자바스크립트 같은 환경에서 주의
    - 이진 데이터 표현이 불편함
        - Base64 같은 우회가 필요하고 크기도 커짐
    - 스키마가 약하거나 없으면 해석 책임이 코드로 넘어감
    - CSV는 특히 의미 정의와 파싱 규칙이 모호함
- 그럼에도 불구하고,조직 간 데이터 교환에서는 매우 유용해서 앞으로도 계속 널리 쓰일 것임

### 1) 이진부호화

- 조직 내부 데이터라면 사람 친화적 텍스트 형식 대신 더 작고 빠른 이진 형식을 쓸 수 있음
- JSON/XML의 이진 버전(MessagePack 등)은 텍스트보다 공간을 덜 쓰고 파싱도 빠를 수 있음
- 하지만 JSON/XML 데이터 모델을 그대로 유지하면,
필드 이름 같은 정보가 데이터에 계속 들어가서 낭비가 남음
- 예제에서 MessagePack은 텍스트 JSON 81바이트를 66바이트로 줄였지만, 절감 폭은 크지 않음
- 그래서 단순한 “바이너리 JSON”보다,스키마를 이용해 필드 이름 반복을 없애는 형식이 더 큰 효과를 냄
- 이 페이지는 바로 그 다음 주제(ProtoBuf, Thrift, Avro)로 넘어가기 위한 연결 고리임

## (3) 스크리프트와 프로토콜 버퍼

- 스리프트와 프로토콜 버퍼는 스키마 기반 이진 부호화 형식임
- 데이터를 보내기 전에 먼저 스키마(IDL)를 정의함
- 이 스키마에는 각 필드의
    - 번호(tag)
    - 타입
    - 필수/선택 여부
    - 반복 여부가 적혀 있음
- 실제 부호화된 데이터에는 필드 이름 대신 태그 번호가 들어감
- 그래서 JSON/MessagePack보다 훨씬 작아질 수 있음
- 예제 크기 비교:
    - 텍스트 JSON: 81바이트
    - MessagePack: 66바이트
    - Thrift Binary: 59바이트
    - Thrift Compact: 34바이트
    - Protobuf: 33바이트
- 스리프트 컴팩트와 프로토콜 버퍼는 가변 길이 정수(varint) 같은 방식을 써서 작은 숫자를 더 적은 바이트로 저장함
- required, optional 은 스키마의 검증 규칙이지, 이진 데이터 안에 직접 표시되는 것은 아님

### 1) 필드태그와 스키마 발전

- 필드의 데이터 타입 변경은 가능할 수도 있지만, 값 손실이나 잘림 위험이 있음
- 예를 들어 32비트 정수 → 64비트 정수로 바꾸면:
    - 새 코드가 예전 데이터를 읽는 것은 대체로 가능함
    - 예전 코드가 새 데이터를 읽는 것은 큰 값에서 잘림 문제가 생길 수 있음
- 프로토콜 버퍼에서 `repeated` 필드는 같은 필드 태그가 여러 번 나타나는 방식으로 인코딩됨
- 그래서 optional 필드를 repeated 필드로 바꾸는 것은 비교적 유연함:
    - 새 코드는 예전 데이터를 0개 또는 1개 원소 리스트로 읽을 수 있음
    - 예전 코드는 새 데이터의 여러 값 중 마지막 값 하나만 보게 됨
- 스리프트는 별도의 list 타입이 있어서, 프로토콜 버퍼처럼 단일값 ↔ 다중값 변경을 같은 방식으로 허용하지는 않음

### 2) 데이터타입과 스키마 발전

- 필드의 데이터 타입 변경은 가능할 수도 있지만, 값 손실이나 잘림 위험이 있음
- 예를 들어 32비트 정수 → 64비트 정수 변경 시:
    - 새 코드가 옛 데이터를 읽는 것은 대체로 가능함
    - 옛 코드가 새 데이터를 읽는 것은 큰 값에서 깨질 수 있음
- 프로토콜 버퍼의 repeated는 같은 필드 태그가 여러 번 나타나는 방식으로 표현됨
- 그래서 optional 필드를 repeated 로 바꾸는 것은 비교적 유연함:
    - 새 코드는 옛 데이터를 0개/1개 원소 리스트로 읽을 수 있음
    - 옛 코드는 새 데이터의 여러 값 중 마지막 값 하나만 보게 됨
- 스리프트는 별도의 list 타입이 있어서, 프로토콜 버퍼처럼 단일값↔다중값 변경을 같은 방식으로 다루지 않음

## (4) 아브로

- 아브로는: 스리프트/프로토콜 버퍼와 비슷한 스키마 기반 이진 부호화 형식
- Avro는 사람이 쓰기 쉬운 IDL과 기계가 읽기 쉬운 JSON 기반 스키마 표현을 제공함
- 예제 스키마는 Person 레코드에 대해
    - userName: 문자열
    - favoriteNumber: null 또는 long
    - interests: 문자열 배열을 정의함
- 아브로의 큰 특징은 필드 태그 번호가 없다는 점임
- 그래서 부호화된 데이터에는 필드 이름도, 태그도 거의 없고 값만 순서대로 이어짐
- 이 덕분에 예제 레코드는 32바이트로, 앞서 본 형식들 중 가장 짧음
- 하지만 그 대신 데이터를 읽는 쪽은 스키마의 필드 순서와 타입을 미리 알아야 함
- 즉, writer 스키마와 reader 스키마의 관계가 매우 중요해지며, 이 점이 곧 스키마 발전 문제로 이어짐

### 1) 쓰기 스키마와 읽기 스키마

- 아브로에는 쓰기 스키마(writer’s schema) 와 읽기 스키마(reader’s schema) 개념이 있음
- 쓰기 스키마는 데이터를 기록할 때 사용한 스키마이고,
읽기 스키마는 현재 읽는 코드가 기대하는 스키마임
- 아브로의 핵심은 두 스키마가 완전히 같지 않아도, 호환 가능하면 읽을 수 있도록 한다는 점임
- 이를 위해 아브로는 복호화할 때 쓰기 스키마와 읽기 스키마를 함께 비교해 차이를 해소함
- 필드 순서가 달라도 괜찮음
이유는 순서가 아니라 이름으로 필드를 매칭하기 때문임
- 쓰기 스키마에만 있는 필드는 읽기 시 무시함
- 읽기 스키마에는 있지만 쓰기 스키마에 없는 필드는 기본값(default value) 으로 채움

### 2) 스키마발전규칙

- 아브로에서
    - 상위 호환성 = 새 데이터 → 옛 코드가 읽기 가능
    - 하위 호환성 = 옛 데이터 → 새 코드가 읽기 가능
- 기본값이 있는 필드만 안전하게 추가/삭제할 수 있음
    - 기본값 없는 필드 추가 → 하위 호환성 깨짐
    - 기본값 없는 필드 삭제 → 상위 호환성 깨짐
- 아브로는 optional/ required 대신유니온 타입 + 기본값을 사용함
- null을 허용하려면 반드시 union에 null을 명시해야 함
- 필드 이름 변경은 alias를 이용해 가능하지만,
보통 하위 호환성만 있고 상위 호환성은 없음
- 유니온 타입에 새 타입 추가도
보통 하위 호환성만 있고 상위 호환성은 없음
- 아브로는 일부 타입 변환도 지원해서 스키마 발전을 유연하게 처리함

### 3) 그러면 쓰기 스키마는 무엇인가?

- 아브로는 데이터를 작게 저장하기 위해 레코드마다 전체 스키마를 넣지 않음
- 그 이유는 스키마가 데이터보다 더 클 수도 있어서 비효율적이기 때문임
- 그래서 쓰기 스키마는 상황에 따라 바깥에서 알아냄
- 대표 방식 3가지:
    - 큰 파일: 파일 시작 부분에 스키마를 한 번만 넣기
    - 데이터베이스 레코드: 각 레코드에 스키마 버전 번호를 넣고, 별도 목록에서 스키마를 찾기
    - 네트워크 통신: 연결 설정 시 스키마 버전을 합의하고 그 뒤 계속 사용하기
- 스키마 버전 관리는 항상 유용함
- 버전 번호는 증가 정수나 스키마 해시값으로 표현할 수 있음

### 4) 동적 생성 스키마

- 아브로의 장점 중 하나는 필드 태그 번호가 없다는 점임
- 이 덕분에 Avro는 동적 생성 스키마에 더 잘 맞음
- 예를 들어 관계형 데이터베이스 스키마를 보고
    - 아브로 record 생성
    - DB 컬럼을 아브로 field로 매핑
    하는 작업을 쉽게 자동화할 수 있음
- DB 스키마가 바뀌면 새 아브로 스키마를 다시 생성해서 데이터를 내보내면 된다.
- 아브로는 필드를 이름 기준으로 식별하므로, 읽는 쪽은 변경된 스키마와 예전 스키마를 비교적 쉽게 맞출 수 있음
- 반면 Thrift/ Protobuf는 필드 태그 번호를 수동 또는 신중하게 관리해야 함
- 따라서 DB 스키마처럼 자주 바뀌는 외부 구조를 자동으로 따라가는 용도에는 아브로가 더 자연스러움

### 5) 코드 생성과 동적 타입 언어

- Thrift와 Protobuf는 보통 스키마로부터 코드를 생성해서 사용하는 방식에 의존함
- 이 방식은 자바, C++, C# 같은 정적 타입 언어에서 특히 유용함
    - 타입 검사
    - IDE 자동완성
    - 효율적인 인메모리 구조 때문
- 자바스크립트, 루비, 파이썬 같은 동적 타입 언어에서는 코드 생성의 장점이 상대적으로 작음
- 특히 동적으로 생성되는 스키마 환경에서는 코드 생성 단계가 오히려 불필요한 장벽이 될 수 있음
- Avro는 정적 타입 언어를 위해 선택적으로 코드 생성을 지원하지만,코드 생성 없이도 사용할 수 있음
- Avro 객체 컨테이너 파일은 스키마를 내부에 포함하므로 자기 기술적(self-describing) 임
- 그래서 Apache Pig 같은 데이터 처리 환경에서는 Avro 파일만 있으면 바로 읽고 분석을 시작할 수 있음

## (5) 스키마의 장점

- 프로토콜 버퍼, 스리프트, 아브로는 스키마 기반 이진 부호화 형식임
- 이 방식은 XML/JSON 같은 텍스트 형식의 대안이 될 수 있음
- 장점:
    - 데이터에서 필드 이름을 생략할 수 있어 크기가 더 작음
    - 스키마가 실제 부호화/ 복호화에 사용되므로 문서와 실제가 어긋날 가능성이 적음
    - 스키마 저장소를 두면 상·하위 호환성 검사를 미리 할 수 있음
    - 정적 타입 언어에서는 코드 생성과 타입 체크에 유리함
- 이런 접근은 완전히 새로운 건 아니며 ASN.1 같은 오래된 선례도 있음
- 결론적으로, 스키마 기반 이진 부호화는유연성도 어느 정도 가지면서, 데이터 품질과 도구 지원은 더 잘 보장하는 방식임

# [2] 데이터플로 모드

- 데이터를 다른 프로세스로 보내려면 부호화/복호화가 필요함
- 시스템이 점진적으로 바뀌려면 상위 호환성/하위 호환성이 중요함
- 이런 문제는 결국 데이터가 어떤 방식으로 전달되느냐, 즉 데이터플로 문제로 이어짐
- 데이터플로란 한 프로세스에서 다른 프로세스로 데이터를 전달하는 방식임
- 책은 이후 대표적인 3가지 데이터플로를 다룸
    1. 데이터베이스를 통한 데이터플로
    2. 서비스 호출을 통한 데이터플로 (REST, RPC)
    3. 비동기 메시지 전달을 통한 데이터플로

## (1) 데이터베이스를 통한 데이터플로

- 데이터베이스는 한 프로세스가 다른 프로세스에게 데이터를 전달하는 매개체임
- 가장 단순하게 보면, DB에 기록하는 것은 미래의 자신에게 메시지를 남기는 것과 같음
- 따라서 하위 호환성은 필수임
새 코드가 예전 데이터를 읽을 수 있어야 함
- 실제 운영에서는 여러 버전의 프로세스가 동시에 DB를 접근하므로 상위 호환성도 대개 필요함
옛 코드가 새 데이터도 읽을 수 있어야 함
- 더 조심해야 할 문제는 옛 코드가 새 필드를 모른 채 레코드를 읽고 다시 저장하면서 그 필드를 지워버릴 수 있다는 점임
- 그림 4-7은 바로 이 상황, 즉 photoURL 같은 새 필드가 옛 코드의 재저장 과정에서 유실되는 예를 보여줌
- 따라서 DB 기반 데이터플로에서는 단순한 읽기 호환성뿐 아니라 알지 못하는 필드 보존도 중요함

### 1) 다양한 시점에 기록된 다양한 값

- 데이터베이스 안의 데이터는 서로 다른 시점에 기록되므로, 같은 DB 안에도 서로 다른 버전의 데이터가 섞여 있을 수 있음
- 애플리케이션 코드는 빨리 교체되지만, 데이터는 오래 남기 때문에데이터가 코드보다 더 오래 삶(data outlives code)
- 옛 데이터를 전부 새 스키마로 다시 쓰는 것은 가능하지만, 대용량 데이터셋에서는 비용이 커서 보통 피함
- 그래서 대부분의 시스템은 기존 데이터를 그대로 두고,
    - 새 컬럼 추가
    - 누락된 값은 NULL/기본값 처리 
    같은 방식으로 스키마 변화를 처리함
- 결과적으로 저장소 내부에는 여러 버전의 스키마로 기록된 데이터가 섞여 있어도,애플리케이션 입장에서는 하나의 일관된 스키마처럼 보이게 만듦

### 2) 보관저장소

- 운영 DB는 여러 버전 데이터가 섞여 있어도 되지만,
- 보관 저장소로 옮길 때는 최신 스키마로 정리해 일관된 형식으로 저장하는 것이 보통 더 유리함

## (2) 서비스를 통한 데이터플로: REST와 RPC

- 네트워크를 통한 대표적 데이터플로는 클라이언트-서버 구조임
- 서버가 공개한 API를 서비스(service) 라고 함
- 웹 브라우저의 HTTP 요청/응답은 대표적인 서비스 호출 예시임
- 클라이언트는 브라우저뿐 아니라 모바일 앱, 자바스크립트 코드, 다른 서버일 수도 있음
- 서버 응답은 HTML일 수도 있고, JSON 같은 프로그램용 데이터일 수도 있음
- HTTP 같은 전송 규약은 표준이지만, API의 구체적 의미는 서비스마다 다르므로 클라이언트와 서버가 세부 사양에 합의해야 함
- 서버가 다른 서버를 호출하는 구조는 SOA, 마이크로서비스와 연결됨
- 서비스는 DB와 비슷하게 데이터를 주고받지만, DB보다 더 제한적이고 캡슐화된 API를 제공함
- 서비스/마이크로서비스 환경에서는 각 컴포넌트를 독립적으로 배포하므로, 옛 버전과 새 버전이 동시에 공존할 수 있음
- 따라서 서비스 API가 사용하는 데이터 부호화는 버전 간 호환성을 가져야 함

### 1) 웹 서비스

- HTTP를 이용해 서비스와 통신하면 흔히 웹 서비스라고 부르지만, 이 말은 웹페이지뿐 아니라 앱-서버, 서비스-서비스, 조직 간 API 통신까지 넓게 포함한다.
- 웹 서비스의 대표적 방식은 REST와 SOAP 임
- REST
    - 프로토콜이 아니라 HTTP 기반 설계 철학
    - URL, GET/POST, 캐시, 인증, 콘텐츠 타입 협상 등 HTTP 기능을 적극 활용
    - 비교적 단순하고 웹 친화적이며 마이크로서비스와도 자주 연결됨
- SOAP
    - XML 기반의 네트워크 API 프로토콜
    - HTTP 위에서 많이 쓰이지만 HTTP 자체보다는 별도 규칙과 WS-* 표준에 더 의존함
    - WSDL로 API를 기술하고 코드 생성이 가능함
    - 정적 타입 언어에서는 유용하지만 전체적으로 복잡하고 도구 의존성이 큼
- SOAP은 표준화가 강하지만 상호운용성 문제와 복잡성 때문에 부담이 크고, RESTful API는 더 단순한 접근을 선호함
- RESTful API 문서화에는 Swagger/OpenAPI 같은 형식을 사용할 수 있음

### 2) 원격 프로시저 호출(RPC) 문제

- RPC는 **원**격 서비스 호출을 로컬 함수 호출처럼 보이게 하려는 방식임
- 하지만 네트워크 호출은 로컬 호출과 본질적으로 다름
- 주요 차이점:
    - 실패 방식이 모호함: 타임아웃, 응답 유실, 처리 여부 불명
    - 재시도가 위험함: 중복 실행 가능 → 멱등성 중요
    - 지연 시간이 큼: 느리고 변동폭이 큼
    - 객체 참조를 직접 넘길 수 없음: 부호화/복호화 필요
    - 서로 다른 언어/타입 체계 문제
- 따라서 RPC의 “로컬 호출처럼 보이게 하려는 추상화”는 편해 보여도 위험할 수 있음
- 중요한 것은 원격 호출이 네트워크 호출이라는 사실을 숨기지 않는 것임
- REST의 장점 중 하나는 이 점을 덜 숨긴다는 것임

### 3) RPC 의 현재 방향

- 현대 RPC는 네트워크 호출의 현실을 더 인정하는 방향으로 발전했고,
- REST는 성능보다 사용성과 생태계 덕분에 공개 API에서 계속 강함

### 4) 데이터 부호화와 RPC 의 발전

- RPC의 발전성은 요청은 새 서버가 옛 클라이언트를 이해해야 하고,
- 응답은 옛 클라이언트가 새 서버를 이해해야 한다는 방향의 호환성 문제임

## (3) 메시지 전달 데이터플로

- 메시지 전달 데이터플로는 **비동기 메시지 전달 시스템**을 사용하는 방식임
- 송신자는 수신자에게 직접 보내지 않고, **메시지 브로커/메시지 큐** 같은 중간 계층을 통해 보냄
- 이 방식은 RPC와 DB의 성격을 일부 섞은 구조라고 볼 수 있음
- 장점:
    - 수신자가 바쁘거나 죽어 있어도 브로커가 **버퍼 역할**을 할 수 있음
    - 메시지를 다시 전달할 수 있어 **유실 방지**에 유리함
    - 송신자가 수신자의 IP/포트를 몰라도 됨
    - 하나의 메시지를 여러 수신자에게 전달할 수 있음
    - 송신자와 수신자가 **논리적으로 분리됨**
- 메시지 전달은 보통 **단방향/비동기**이며, 송신자는 응답을 기다리지 않음
- 응답이 필요하면 보통 **별도 채널**을 사용함

### 1) 메시지브로커

- 메시지 브로커는 메시지를 전달만 해주는 중간자이기 때문에
- 생산자와 소비자를 느슨하게 분리해주지만,
- 그만큼 메시지 부호화 형식의 호환성과 알지 못하는 필드 보존이 매우 중요함

### 2) 분산액터 프레임워크

- 액터 모델은 공유 상태 대신 비동기 메시지 전달로 동시성을 처리하는 모델임
- 각 액터는 자기 로컬 상태를 가지고, 보통 한 번에 하나의 메시지만 처리한다.
- 분산 액터 프레임워크는 이 모델을 여러 노드로 확장한 것임
- 같은 노드든 다른 노드든 기본적으로 메시지 전달 구조는 동일하며, 다른 노드일 경우 메시지를 부호화해 네트워크로 전송함
- 액터 모델은 원래부터 메시지 유실과 비동기성을 어느 정도 전제하므로, 로컬/원격 차이를 RPC보다 더 자연스럽게 다룸
- 하지만 순차 업그레이드 중에는 새 버전 노드와 옛 버전 노드가 메시지를 주고받을 수 있으므로, 여전히 상위/하위 호환성이 중요함
- 예시:
    - Akka: 기본은 자바 내장 직렬화라 호환성이 약하지만 Protobuf 같은 방식으로 대체 가능함
    - Orleans: 기본 직렬화는 순차 업그레이드에 불리해서 새 클러스터로 이관하는 방식이 흔함
    - Erlang OTP: 순차 업그레이드는 가능하지만 레코드 스키마 변경은 쉽지 않음, maps 같은 유연한 구조가 도움될 수 있음

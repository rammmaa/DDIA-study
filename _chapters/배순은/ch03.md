- 작업 목적에 따라 어떤 저장소 엔진이 적합한지 이해하기

# [1] 데이터베이스를 강력하게 만드는 데이터 구조 98

- **append-only 로그 구조**는 쓰기에 강함
- 하지만 그대로는 **검색이 느림**
- 그래서 **색인**이 필요함
- 대신 색인은 **읽기 속도 향상 ↔ 쓰기 오버헤드 증가**라는 트레이드오프가 있음
- 따라서 애플리케이션의 **작업부하(workload)** 에 맞게 색인을 골라야 함

## (1) 해시 색인

- 해시 색인은 키 하나를 빠르게 찾는 데 아주 효과적이며,
- append-only 로그와 결합하면 단순하고 빠른 저장소를 만들 수 있음
- 하지만 메모리 제약이 있고 범위 질의에 약하기 때문에, 모든 상황에 만능은 아님

## (2) SSTable들과 LSM 트리

- SSTable: 키 순으로 정렬된 불변 세그먼트 파일
- 같은 키가 여러 개면 컴팩션 때 최신 값만 유지함
- 정렬되어 있어서 병합이 효율적임
- 전체 키를 메모리에 둘 필요 없이 희소 인덱스 만으로 조회 가능함
- 블록 압축이 쉬워서 디스크와 I/O 효율이 좋아짐
- 이것을 실제 쓰기 많은 저장소에 적용한 대표 개념이 LSM 트리임

### 1) SS 테이블생성과유지

- 무작위 쓰기를 바로 SSTable에 넣기 어려움
- 그래서 메모리에 멤테이블을 둠
- 멤테이블이 차면 디스크에 SSTable로 flush함
- 조회는 멤테이블 → 최신 SSTable → 오래된 SSTable 순으로 봄
- 백그라운드에서 컴팩션/병합함
- 장애 복구를 위해 추가 전용 로그(WAL 비슷한 것) 를 따로 둠

### 2) SS 테이블에서 LSM 트리 만들기

- SSTable + 멤테이블 + 컴팩션 = LSM 트리
- 실제로 LevelDB, RocksDB, Cassandra, HBase 등이 사용됨
- Lucene도 단어→문서목록 색인을 정렬 파일과 병합 방식으로 관리함

### 3) 성능 최적화

- 없는 키 조회는 블룸 필터로 최적화함
- SSTable 병합 방식은 크기 계층 컴팩션 / 레벨 컴팩션 이 핵심임
- LSM 트리는 결국 순차 쓰기 + 정렬 파일 병합 덕분에 큰 데이터와 많은 쓰기에 강함

## (3) B 트리

- **LSM 트리**: 쓰기를 차곡차곡 쌓고 나중에 병합
- **B 트리**: 페이지 안에 정렬 상태를 유지하며 바로 갱신

### 1) 신뢰할 수 있는 B 트리 만들기

- B 트리는 제자리 갱신 방식이라 구현이 까다롭고
- 그래서 WAL 과 잠금/래치 가 중요하며
- 이런 점에서는 로그 구조 저장소가 오히려 더 단순할 수 있다는 것임

### 2) B 트리 최적화

- 덮어쓰기 대신 copy-on-write 를 쓰는 구현도 있음
- 내부 페이지 키를 축약해 한 페이지에 더 많이 넣음
- 그래서 분기 수 증가 → 트리 높이 감소
- 리프 페이지를 연속 배치하거나 형제 포인터를 둬 범위 스캔 최적화함
- 더 나아가 프랙탈 트리처럼 로그 구조 아이디어를 섞은 변형도 있음

## (4) B 트리와 LSM 트리 비교

- 대체로 LSM은 쓰기, B 트리는 읽기에 강하다고 보지만,
- 진짜 선택 기준은 내 서비스의 실제 workload임

### 1) LSM 트리의 장점

- B 트리는 WAL + 페이지 갱신 + 분할 때문에 쓰기 증폭이 커지기 쉬움
- LSM도 컴팩션 때문에 다시 쓰지만, 보통 순차 쓰기라 더 유리함
- LSM은 압축과 공간 활용도 더 좋은 편임
- 그래서 쓰기 많은 시스템에서 LSM이 강점이 큼

### 2) LSM 트리의 단점

- LSM은 컴팩션이 읽기/쓰기와 자원 경쟁함
- 그래서 평균보다 tail latency 와 성능 변동성이 문제될 수 있음
- 컴팩션이 밀리면 SSTable 증가, 읽기 저하, 디스크 압박 발생함
- B 트리는 더 예측 가능하고 트랜잭션 의미론에 유리한 면이 있음

## (5) 기타 색인 구조

- 기본키 색인 = 레코드의 고유 식별자 용
- 보조 색인 = 다른 컬럼/속성으로 추가 검색 용
- 보조 색인은 같은 키값이 여러 번 나올 수 있음
- 그래서 레코드 ID 목록 등을 함께 관리하며, B 트리/LSM 둘 다 사용 가능함

### 1) 색인 안에 값 저장하기

- 보통 색인은 실제 로우 위치를 가리킴
- 이때 실제 데이터는 힙 파일에 저장됨
- 읽기 성능을 위해 색인 안에 데이터를 넣으면: 클러스터드/커버링 색인
- 대신 공간 증가 + 쓰기 오버헤드가 생김

### 2) 다중 칼럼 색인

- 일반 색인은 보통 한 컬럼 기준임
- 여러 컬럼을 함께 찾으려면 다중 칼럼 색인 필요함
- 가장 흔한 건 결합 색인이고, 컬럼 순서가 중요함
- 위도·경도 같은 2차원 범위 질의는 일반 B 트리/ LSM으로 비효율적임
- 그래서 R 트리 같은 공간/ 다차원 색인이 쓰임

### 3) 전문 검색과 퍼지 색인

- 일반 색인 = 정확한 값/범위 검색
- 전문 검색 = 동의어, 근접 단어, 오타 허용까지 처리
- Lucene은: SSTable 비슷한 구조 + 트라이/오토마톤 같은 추가 구조 사용함
- 퍼지 검색은: 편집 거리 기반으로 비슷한 단어를 효율적으로 찾음

### 4) 모든것을 메모리에 보관

- 지금까지의 저장 구조는 주로 디스크의 느림을 극복하기 위한 것임
- 이제는 데이터 전체를 메모리에 두는 DB도 실용적임
- 지속성은 로그, 스냅샷, 복제 등으로 확보 가능함
- 인메모리 DB는 단순히 디스크를 안 읽어서가 아니라,
 형태 변환 오버헤드 감소로도 빠름
- 앞으로 NVM 이 보급되면 저장소 엔진 설계가 더 바뀔 수 있음

## (1) 데이터 웨어하우징

- OLTP DB는 실제 업무 처리용이라 무거운 분석 질의에 약함
- 그래서 분석용으로 별도 데이터 웨어하우스를 둠
- 데이터는 ETL(추출-변환-적재) 로 가져옴
- 이렇게 하면 운영과 분석을 분리해 둘 다 더 잘 최적화할 수 있음

### 1) OLTP 데이터베이스와 데이터 웨어하우스의 차이점

- 둘 다 SQL을 써서 겉보기엔 비슷함
- 하지만 OLTP와 OLAP의 내부 최적화 목표는 다름
- 그래서 대부분 DB는 둘 중 한쪽에 더 특화됨
- 데이터 웨어하우스용 전용 제품과 SQL-on-Hadoop 시스템이 따로 발전함

## (2) 분석용 스키마: [별 모양 스키마와 눈꽃송이 모양 스키마]

- 중심 = 사실 테이블: 판매/클릭 같은 개별 이벤트
- 주변 = 차원 테이블: 제품, 날짜, 매장, 고객, 프로모션 등
- 사실 테이블은: 수치값 + 차원 참조 키를 가짐
- 별 모양 스키마는: 단순하고 분석하기 쉬움
- 눈꽃송이 스키마는” 더 정규화한 변형임

# [3] 칼럼 지향 저장소

- 분석 질의는 보통 전체 행이 아니라 일부 칼럼만 사용
- 로우 지향 저장은 필요 없는 칼럼까지 같이 읽기 쉬움
- 칼럼 지향 저장은 각 칼럼을 따로 저장
- 그래서 필요한 칼럼만 읽으면 되어 I/O가 크게 줄어듦
- 대용량 OLAP/데이터 웨어하우스 에 특히 적합

## (1) 칼럼 압축

- 칼럼 저장은 압축이 잘 됨
- 특히 고유값별 비트맵 인코딩 이 효과적
- 비트맵은 0이 많아서 RLE 압축 이 잘 됨
- 질의 조건은 비트 OR / AND 로 빠르게 계산 가능
- 단, 칼럼 패밀리 = 진짜 칼럼 지향 저장소 는 아님

### 1) 메모리 대역폭과 벡터화 처리

- 병목은 디스크뿐 아니라 메모리 대역폭과 CPU 처리에도 있음
- 칼럼 저장은 CPU가 다루기 좋은 형태임
- 압축 덕분에 캐시에 더 많은 데이터를 넣을 수 있음
- 그래서 분석 엔진은 벡터화 처리 + SIMD 로 성능을 높임

## (2) 칼럼 저장소의 순서 정렬

- 칼럼 저장소도 공통 행 순서가 필요함
- 자주 쓰는 질의 기준 칼럼으로 정렬하면 스캔 범위 감소함
- 1차, 2차 정렬 키를 둘 수 있음
- 정렬은 질의 성능 + 압축 효율 둘 다 개선함

### 1) 다양한순서 정렬

- 질의마다 유리한 정렬 순서가 다름
- 그래서 같은 데이터를 여러 정렬 방식으로 저장
- 복제본을 서로 다르게 정렬하면 분석 성능에 도움
- 로우 저장소의 보조 색인과 비슷해 보이지만, 실제로는 포인터가 아니라 데이터 자체의 여러 정렬 버전이라는 점이 다름

## (3) 칼럼 지향 저장소에 쓰기

- 칼럼 저장은 읽기 최적화에는 좋음
- 하지만 삽입/갱신 은 어려움
- 그래서 새 쓰기를 메모리에 모았다가
- 나중에 디스크 칼럼 파일과 병합함
- 사용자 입장에서는 최신 변경이 바로 반영된 것처럼 보임

## (4) 집계: 데이터 큐브와 구체화 뷰

- 구체화 뷰: 자주 쓰는 질의 결과를 미리 저장한 것
- 데이터 큐브: 여러 차원 기준 집계를 미리 계산한 특수한 구체화 뷰
- 장점: 아주 빠른 집계 질의
- 단점: 질의 유연성 감소, 원본 변경 시 갱신 비용 발생

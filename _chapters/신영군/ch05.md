## 3.1 Operational Transformation

This real-time sharing (conflict resolving) algorithm is the one behind the Google Docs. In original book, it simply depicted:  
It was designed particularly for concurrent editing of an ordered list of items, such as the list of characters that constitute a text document.  
Since this algorithm is the one behind Google Docs, I tried to implement it in Python. And gain more insights.
It is really hard to connect the real-time sharing problem with the replication problem. But actually the users are maintaining their local replica and commit to the cloud side (or leader) node

### Problem

Let's say there are two users, Alice and Bob, who are editing the same document 'abc'. Alice inserts 'X' at index 1 as operation_1(insert, 1, 'X') and Bob inserts 'Y' at index 2 as operation_2(insert, 2, 'Y').  
The document will have 2 different results depending on the order of operations:  
'aXYbc' when operation_1 is applied first.  
or 'aXbYc' when operation_2 is applied first.  
Since the author said it's not appropriate to naively use the order of the edited time to merge the operation. This OT algorithm is proposed to solve this problem.

```python
class InsertOp:
    def __init__(self, position, char, user_id):
        self.position = position
        self.char = char
        self.user_id = user_id

    def __repr__(self):
        return f"Insert('{self.char}' at {self.position} by {self.user_id})"

def transform(incoming_op, local_history_op):
    """
    Transforms the incoming_op based on a local_history_op that occurred concurrently.
    """
    # If the incoming op happens AFTER the local op, the local op already shifted
    # all the characters to the right. So we must push the incoming op's position + 1.
    if incoming_op.position > local_history_op.position:
        return InsertOp(incoming_op.position + 1, incoming_op.char, incoming_op.user_id)

    # If the incoming op happens BEFORE the local op, no shift is needed.
    elif incoming_op.position < local_history_op.position:
        return InsertOp(incoming_op.position, incoming_op.char, incoming_op.user_id)

    # If they happen at the EXACT SAME position, we need a tie-breaker.
    # We can use the user_id to deterministically decide who goes first.
    else:
        if incoming_op.user_id > local_history_op.user_id:
            # Shift the incoming op to the right
            return InsertOp(incoming_op.position + 1, incoming_op.char, incoming_op.user_id)
        else:
            # Keep incoming op where it is
            return InsertOp(incoming_op.position, incoming_op.char, incoming_op.user_id)

def apply_operation(document, op):
    """Applies an operation to a string document."""
    return document[:op.position] + op.char + document[op.position:]

# ==========================================
# DEMO: Simulating Concurrent Edits
# ==========================================
initial_doc = "abc"

# 1. Concurrent operations happen
# Alice inserts 'X' at index 1 -> local state = "aXbc"
op_Alice = InsertOp(1, 'X', user_id="Alice")

# Bob inserts 'Y' at index 2 -> local state = "abYc"
op_Bob = InsertOp(2, 'Y', user_id="Bob")

# 2. They sync. Alice receives Bob's operation.
# Alice transforms Bob's operation against her own history.
transformed_op_Bob = transform(op_Bob, op_Alice)
print(f"Alice transforms Bob's op: {op_Bob} -> {transformed_op_Bob}")

# 3. They sync. Bob receives Alice's operation.
# Bob transforms Alice's operation against his history.
transformed_op_Alice = transform(op_Alice, op_Bob)
print(f"Bob transforms Alice's op: {op_Alice} -> {transformed_op_Alice}")

# 4. Applying the transformed results
alice_final_doc = apply_operation("aXbc", transformed_op_Bob)
bob_final_doc = apply_operation("abYc", transformed_op_Alice)

print(f"\nFinal state for Alice: {alice_final_doc}")
print(f"Final state for Bob:   {bob_final_doc}")
print(f"Consistent?            {alice_final_doc == bob_final_doc}")
```

Here the algorithm basically used the data structure of list, and while the position is in right side, means the time of editing is later.

### Result

```terminal
>>> print(f"\nFinal state for Alice: {alice_final_doc}")

Final state for Alice: aXbYc
>>> print(f"Final state for Bob:   {bob_final_doc}")
Final state for Bob:   aXbYc
>>> print(f"Consistent?            {alice_final_doc == bob_final_doc}")
Consistent?            True
```

We can see that the final state is consistent. And the operation order is Operation_Alice->Operation_Bob. It reflected the Alice's insert operation at index 1 and Bob's insert operation at index 2. After the op1, the index is changed, so algorithm changed the inserting index of the op2 from 2 to 3. Finally, the result is 'aXbYc'.

# 4. Specific Application Cases & Concept Review

## 4.1 Leader vs Followers

| Feature                | Leader                                                                                                                | Follower                                                                                                                                               |
| :--------------------- | :-------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Common Aliases**     | Master, Primary                                                                                                       | Read replica, Slave, Secondary, Hot standby                                                                                                            |
| **Primary Role**       | Acts as the central point for data ingestion and generates the replication log.                                       | Maintains a backup copy of the data by consuming the replication log from the leader.                                                                  |
| **Write Operations**   | Exclusively accepts all write requests from clients. It writes new data to its local storage first.                   | Read-only from the client's perspective. It does not accept direct write requests from clients.                                                        |
| **Read Operations**    | Can be queried by clients to read data.                                                                               | Can be queried by clients to read data (which is highly useful for scaling read-heavy workloads).                                                      |
| **Internal Data Flow** | After writing to its local storage, it sends the data changes to all followers as a replication log or change stream. | Takes the replication log from the leader and updates its local copy by applying all writes in the exact same order they were processed on the leader. |

## 4.2 Trade-offs of Replication

Basically it is the trade-off between the fault tolerance and the latency. Also we need to understand the business scenario of our application. And choose the best replica model. From the Single Leader replica system, which is the fastest replica model but while the leader fails, the system will be read-only mode, harms the consistency. And Leaderless system is relatively hard to construct, but while the system is being designed properly, the consistency and availability can be maintained. But since the writes are scattered across multiple nodes, the latency is relatively high.

## 4.3 Handling Node Outages

### Node Outage Handling by Replication Model

| Replication Model | Node Role             | Impact on Availability                                                                          | Recovery / Saving Approach                                                                                                                                      |
| :---------------- | :-------------------- | :---------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Single-Leader** | **Follower**          | **No impact.** The system continues to serve reads and writes normally.                         | **Catch-up recovery**: The crashed follower reconnects and requests the replication log from the leader for the period it was down.                             |
| **Single-Leader** | **Leader**            | **High impact.** Writes will fail until a new leader is elected.                                | **Failover**: The system must detect the crash, elect a new leader from the followers, and reconfigure clients to send writes to the new leader.                |
| **Multi-Leader**  | **Leader (Any Node)** | **Low impact.** Clients can simply route their reads and writes to another healthy leader node. | **Catch-up**: The node reconnects and pulls missing changes from other leaders. Concurrent writes during outage may need conflict resolution upon recovery.     |
| **Leaderless**    | **Any Node**          | **No immediate impact.** System functions normally as long as Quorum ($W + R > N$) is met.      | **Read Repair** (clients update stale nodes when they read old data) & **Anti-entropy processes** (background sync comparing node data to copy missing writes). |

## 4.4 Read after Write Consistency (Read-Your-Own-Writes)

When replication is asynchronous, a user might submit a write (like updating their profile picture) and then immediately refresh the page. If the read request is routed to a follower that hasn't synced the new data yet, it looks like their data was lost.
**Solution:** Guarantee that a user always reads _their own_ updates from a replica that holds the latest data (e.g., forcing their reads to go to the Leader or remembering the timestamp of their last update).

### Monotonic Reads (Time Moving Backward)

Monotonic reads solve a different problem: observing time moving backward. Let's say you upload a student's score.

1. A teacher queries the score, their request hits **Follower A** (which is up-to-date), and they see the score.
2. The teacher refreshes the page, their request hits **Follower B** (which is lagging behind). Suddenly, the score disappears!
   This anomaly is caused by reading from replicas at different points in time.
   **Solution:** A monotonic read guarantee ensures that once a user has seen data, they will never read an older version of that data again. The simplest way to achieve this is to ensure that a single user's reads are always routed to the **same exact replica** (e.g., by hashing their User ID).

## 4.5 Causality Issues (Consistent Prefix Reads)

While Monotonic Reads focus on a single user observing an event sequence, the Causality Issue focuses on relationships between _multiple different users/items_.

**The Problem:** Let's say there is a conversation between Alice and Bob:

- **Alice:** Who is your favorite singer? (Takes 2 seconds to reach the replica)
- **Bob:** Taylor Swift. (Takes 0.5 seconds to reach the replica)

Because of varying network delays between partitions, another user observing the chat might see Bob shout "Taylor Swift" _before_ Alice even asks the question. The logical "cause and effect" is broken.

**Solution: Consistent Prefix Reads**. This guarantee ensures that if a sequence of writes happens in a certain causal order, anyone reading those writes will see them appear in the identical order. This is typically solved by ensuring that any writes that are causally related to each other are written to the exact same partition.

# 1. Summary

This chapter based on a prerequisite concept of "Evolvability". Since the environment of users and developers always are not the same. We should design programs to tolerate different data types.
The chapter first categorizes Encoding Formats into language-specific formats (often brittle), textual formats (JSON, XML - human-readable but bulky), and binary formats (Thrift, Protocol Buffers, Avro - efficient and schema-driven).Subsequently, it examines the Modes of Dataflow, discussing how encoded data travels through a system: via databases (data outlives code), via service calls (REST/RPC), or via asynchronous message-passing. The core takeaway is that the "correct" encoding depends on the compatibility requirements (Forward/Backward) and the specific trade-offs between performance and flexibility.

# 3. Code

## 3.1 Example: Manual Schema Versioning (The "Shim")

When using flexible formats like JSON, application code often handles evolution with "shims" to maintain backward compatibility.

```python
# Old Record format
old_user = {"user_id": 1, "name": "Alice"}

# New Record format (added 'email')
new_user = {"user_id": 2, "name": "Bob", "email": "bob@example.com"}

def read_user_profile(record):
    """
    Simulating Backward Compatibility:
    The new code handles missing fields from old data.
    """
    user_id = record["user_id"]
    name = record["name"]

    # Provide a default for the missing field in old records
    email = record.get("email", "unknown@example.com")

    return f"ID: {user_id}, Name: {name}, Email: {email}"

print(read_user_profile(old_user)) # ID: 1, Name: Alice, Email: unknown@example.com
print(read_user_profile(new_user)) # ID: 2, Name: Bob, Email: bob@example.com
```

## 3.2 Concept: Protocol Buffers Style Encoding

Unlike JSON, Protobuf uses field tags (numbers) to map data, allowing fields to be renamed without breaking the encoding.

```Protocol Buffers
// schema.proto
message Person {
  required string name = 1; // Field Tag '1' is the identity
  optional int32 id = 2;    // Field Tag '2'
  optional string email = 3;
}
```

# 4. Specific Application Cases & Concept Review

## 4.1 Forward vs. Backward Compatibility

Understanding these directions is critical for zero-downtime deployments:Backward Compatibility: New code can read data that was written by old code. This is usually easy: the new code just needs to handle missing fields (defaults).Forward Compatibility: Old code can read data that was written by new code. This is harder: the old code must know how to ignore fields it doesn't recognize without crashing or losing data.

## 4.2 Comparison: Thrift/Protobuf vs. Avro

| Feature              | Thrift / Protocol Buffers             | Apache Avro                                    |
| :------------------- | :------------------------------------ | :--------------------------------------------- |
| **Field Identity**   | Numeric Tags (1, 2, 3...)             | Writer's Schema vs. Reader's Schema            |
| **Handling Changes** | Add tags; cannot change tag numbers   | Use schema resolution to bridge differences    |
| **Data Overhead**    | Schema must be known by both sides    | Schema is often sent with the data (or via ID) |
| **Use Case**         | RPC, Internal service communication   | Hadoop/Big Data, high-volume log storage       |

## 4.3 Dataflow Through Databases

In a database, the code that writes data is often different from the code that reads it later (sometimes years later). Kleppmann describes this as "Data outlives code".
If an old version of the application reads a record written by a new version, modifies it, and saves it back, there is a risk that the new fields (unknown to the old code) will be lost. This is a major reason why database schemas require careful migration strategies.

## 4.4 The "Impedance Mismatch" of RPC

While REST and RPC aim to make remote requests look like local function calls, this is a "leaky abstraction." Network calls can fail, hang, or return different results due to latency—variables that a local function does not have to manage. Modern systems often prefer REST for public APIs and binary RPC (like gRPC) for internal, high-performance service-to-service communication.

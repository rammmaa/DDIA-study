# 1. Summary

In this chapter, we will discuss partitioning, which is a technique to distribute data across multiple nodes to improve performance and scalability. Like the traditional concept of trade-off in the previous chapters, partitioning also has its own trade-offs. The main goal of partitioning is to spread the data and query load evenly across nodes. If partitioning is unfair, some nodes will have more data or queries than others, creating a "hot spot".

## 3.1 Consistent Hashing

A major challenge in partitioning is how to map data items to nodes, especially when nodes are added or removed (rebalancing). A naive approach like `hash(key) % N` works poorly because changing `N` (the number of nodes) shifts almost all the data, requiring massive data movement.

Consistent Hashing is a technique that minimizes data movement when nodes join or leave. Both data and nodes are hashed onto the same "ring", and a data item is assigned to the first node that appears clockwise on the ring. We also use "virtual nodes" to ensure better load balancing.

### Problem

We need to distribute 5 users across 3 database nodes. Later, we add a 4th node because our load increased. We want to see how consistent hashing handles the data placement and limits data migration compared to the modulo approach.

```python
import hashlib
import bisect

class ConsistentHashRing:
    def __init__(self, nodes=None, virtual_nodes=3):
        # virtual_nodes helps to distribute load more evenly
        self.virtual_nodes = virtual_nodes
        self.ring = {}
        self.sorted_keys = []

        if nodes:
            for node in nodes:
                self.add_node(node)

    def _hash(self, key):
        # MD5 provides a decent uniform distribution for the ring
        return int(hashlib.md5(key.encode('utf-8')).hexdigest(), 16)

    def add_node(self, node):
        for i in range(self.virtual_nodes):
            virtual_node_name = f"{node}#VN{i}"
            key = self._hash(virtual_node_name)
            self.ring[key] = node
            bisect.insort(self.sorted_keys, key)

    def remove_node(self, node):
        for i in range(self.virtual_nodes):
            virtual_node_name = f"{node}#VN{i}"
            key = self._hash(virtual_node_name)
            if key in self.ring:
                del self.ring[key]
                self.sorted_keys.remove(key)

    def get_node(self, item):
        if not self.ring:
            return None

        key = self._hash(item)

        # Find the first node with a hash greater than or equal to the item's hash
        index = bisect.bisect_right(self.sorted_keys, key)

        # Wrap around to the start of the ring if the item's hash is the largest
        if index == len(self.sorted_keys):
            index = 0

        return self.ring[self.sorted_keys[index]]

# ==========================================
# DEMO: Data Distribution & Node Rebalancing
# ==========================================
ring = ConsistentHashRing(["Node_A", "Node_B", "Node_C"], virtual_nodes=3)

data_items = ["user:123", "user:456", "user:789", "user:001", "user:002"]

print("--- Initial Distribution (3 Nodes) ---")
for item in data_items:
    print(f"Data '{item}' -> {ring.get_node(item)}")

print("\n--- Adding Node_D ---")
ring.add_node("Node_D")
for item in data_items:
    print(f"Data '{item}' -> {ring.get_node(item)}")
```

### Result

```terminal
--- Initial Distribution (3 Nodes) ---
Data 'user:123' -> Node_B
Data 'user:456' -> Node_C
Data 'user:789' -> Node_C
Data 'user:001' -> Node_A
Data 'user:002' -> Node_B

--- Adding Node_D ---
Data 'user:123' -> Node_B
Data 'user:456' -> Node_C
Data 'user:789' -> Node_D
Data 'user:001' -> Node_A
Data 'user:002' -> Node_B
```

As you can see, when `Node_D` was added, only `user:789` was moved from `Node_C` to `Node_D`. The rest of the keys stayed exactly where they were. This solves the rebalancing problem effectively!

# 4. Specific Application Cases & Concept Review

## 4.1 Key-Value Data Partitioning

How do we decide which records go to which node?

| Partitioning Method | Description                                                                             | Pros                                                                    | Cons                                                                                                               |
| :------------------ | :-------------------------------------------------------------------------------------- | :---------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------- |
| **By Key Range**    | Assign a continuous range of keys (e.g., A-F, G-M) to each partition.                   | Excellent for range queries (e.g., time-series data between two dates). | High risk of hot spots if access patterns are not completely uniform (e.g., everyone accessing the letter 'A').    |
| **By Hash of Key**  | Pass the key through a hash function (like MD5) and assign partition based on the hash. | Distributes data very evenly; highly effective at avoiding hot spots.   | Destroys ordering. You can no longer efficiently run range queries (you have to send the query to all partitions). |

_Note on skewed workloads:_ Even with hashing, an extreme workload (e.g., millions of followers commenting on a celebrity's post) can create a hot spot. In these edge cases, applications often append a random number to the key to split the heavy record across multiple partitions.

## 4.2 Partitioning and Secondary Indexes

If a database involves secondary indexes (e.g., searching by color or price instead of user ID), they don't map neatly to partitions.

| Indexing Method                        | Description                                                                                                                             | Pros                                                                    | Cons                                                                                                                                                         |
| :------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Document-partitioned (Local Index)** | Each partition maintains its own secondary index, covering only the documents in that partition.                                        | Writing is fast (only updates the local partition).                     | Reading is slow (Scatter/Gather). To query the index, you must query all partitions and combine the results.                                                 |
| **Term-partitioned (Global Index)**    | A global index is partitioned separately from the main data. For example, colors A-M are stored in Partition 1, and N-Z in Partition 2. | Reading is fast. You know exactly which partition holds the index term. | Writing is slower and more complex. An update to a document might affect index entries residing in different partitions (requires distributed transactions). |

## 4.3 Rebalancing Strategies

When you add or remove nodes (e.g., scaling up CPU, replacing a failed disk), data must be moved from one node to another. This is called rebalancing.

| Strategy                                 | Mechanism                                                                                                                                                                                                    |
| :--------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Hash mod N (DON'T DO THIS)**           | `hash(key) % N`. If N changes from 10 to 11, almost every key changes its partition. Creates unacceptable network load.                                                                                      |
| **Fixed Number of Partitions**           | Create many more partitions than nodes (e.g., 1000 partitions on 10 nodes). When a new node joins, it steals a few whole partitions from the existing nodes. Very common and reliable.                       |
| **Dynamic Partitioning**                 | Similar to B-trees. When a partition grows too large, it splits into two. When it shrinks, it merges with an adjacent partition.                                                                             |
| **Partitioning proportionally to nodes** | Used in Cassandra. The number of partitions is proportional to the number of nodes. When a new node joins, it randomly selects a fixed number of existing partitions to split, taking ownership of one half. |

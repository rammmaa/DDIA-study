# 3.1 example of converting OLTP db to OLAP db

```python
# 1. OLTP DATA (Row-Oriented)
# Typical of what you'd get from a SQL SELECT * or a document DB.
oltp_records = [
    {"order_id": 1, "user_id": 101, "price": 25.50, "status": "shipped"},
    {"order_id": 2, "user_id": 102, "price": 10.00, "status": "pending"},
    {"order_id": 3, "user_id": 103, "price": 45.00, "status": "shipped"},
    {"order_id": 4, "user_id": 104, "price": 5.25,  "status": "shipped"},
]

# 2. CONVERSION LOGIC (The "Pivot")
def convert_to_olap(rows):
    if not rows: return {}
    # Use the keys from the first row to initialize empty lists for each column
    columns = {key: [] for key in rows[0].keys()}

    for row in rows:
        for key, value in row.items():
            columns[key].append(value)

    return columns

# 3. OLAP DATA (Column-Oriented)
# Each key points to a contiguous block of memory (an array).
olap_columns = convert_to_olap(oltp_records)

print("OLAP Structure:")
for col_name, values in olap_columns.items():
    print(f"{col_name}: {values}")
```

# 3.2 code example of LSM tree and B tree

```python
import bisect

class LSMTree:
    def __init__(self):
        self.memtable = {}  # In reality, this would be a balanced tree
        self.sstables = []  # List of sorted on-disk segments (simulated as lists)
        self.threshold = 3  # Low for demonstration

    def put(self, key, value):
        # 1. Write to Write-Ahead Log (WAL) for durability (omitted)
        # 2. Write to memtable (fast in-memory update)
        self.memtable[key] = value

        if len(self.memtable) >= self.threshold:
            self.flush_to_sstable()

    def flush_to_sstable(self):
        # Convert memtable to a sorted list of pairs and "flush" to disk
        sorted_segment = sorted(self.memtable.items())
        self.sstables.insert(0, sorted_segment) # Newest first
        self.memtable = {}
        print(f"Flushed to SSTable! Current segments: {len(self.sstables)}")

    def get(self, key):
        # 1. Check memtable first
        if key in self.memtable:
            return self.memtable[key]

        # 2. Check SSTables from newest to oldest
        for segment in self.sstables:
            # Efficiently search in sorted list using binary search
            keys = [pair[0] for pair in segment]
            idx = bisect.bisect_left(keys, key)
            if idx < len(segment) and segment[idx][0] == key:
                return segment[idx][1]

        return None

# Usage
lsm = LSMTree()
lsm.put("A", 1); lsm.put("B", 2); lsm.put("C", 3) # Triggers flush
lsm.put("D", 4)
print(f"Value for 'A': {lsm.get('A')}")
#======================The implementation code of B tree=====================
class BTreeNode:
    def __init__(self, leaf=False):
        self.keys = []      # Sorted keys in this "page"
        self.values = []    # Values (or pointers to child pages)
        self.leaf = leaf    # Is this a bottom-level page?

class SimpleBTree:
    def __init__(self, branching_factor=4):
        self.root = BTreeNode(leaf=True)
        self.t = branching_factor

    def search(self, key, node=None):
        if node is None: node = self.root

        # Find the first key >= target key
        i = 0
        while i < len(node.keys) and key > node.keys[i]:
            i += 1

        # If key is here, return it
        if i < len(node.keys) and node.keys[i] == key:
            return node.values[i]

        # If it's a leaf and we didn't find it, it doesn't exist
        if node.leaf:
            return None

        # Otherwise, recurse down to the appropriate child page
        return self.search(key, node.values[i])

    def insert(self, key, value):
        # (Simplified: assumes no splitting for this example)
        # Real B-Trees split a page into two when it gets full
        node = self.root
        i = bisect.bisect_left(node.keys, key)
        node.keys.insert(i, key)
        node.values.insert(i, value)

# Usage
btree = SimpleBTree()
btree.insert(10, "User10")
btree.insert(20, "User20")
print(f"B-Tree Search 10: {btree.search(10)}")
```

# 4. Specific Application Cases & Concept Review

# 4.1 Column-Oriented Storage

so there is a trait in memory or disk that when reading some contents, it is mandatory to read it in a row (continuous part in memory), which makes the column oriented storage in sence, so when we searching for some specific data, it goes like

```python
for i in range (row):
    for j in range (column):
```

we always first search per row, and see the attribute(column) in it, but there will be a lot redundancy while having business analysis, so if we reverse this

```python
for i in range (column):
    for j in range (row):
```

now actually the row is the attributes, hence it it convenient for us to conduct the business analysis. To declare, we didn't change the reading order of the disk, but we change the way we store the data in memory.

# 4.2 comparison of LSM tree and B tree

| Feature               | LSM-Tree                         | B-Tree                     |
| :-------------------- | :------------------------------- | :------------------------- |
| **Write Performance** | High (Sequential appends)        | Lower (Random page writes) |
| **Read Performance**  | Lower (May check multiple files) | High (Direct path to page) |
| **Storage Layout**    | Sorted Strings (SSTables)        | Fixed-size Pages           |
| **Used In**           | Cassandra, RocksDB, LevelDB      | PostgreSQL, MySQL, Oracle  |

We can easily observe that there are trade-offs between these 2 basic data structures, so we need to choose the most appropriate one according to the application. While intuitively, the B tree is faster in read, and we are easily to think this structure is better at OLAP system. But actually, the OLAP system do not use these structures, instead, they use the column-oriented storage, which is more efficient for the business analysis. Hence we can also know the column-oriented storage is a parallel concept with LSM tree and B tree.

# 1. Summary

The concept of a Transaction is a way for an application to group several reads and writes together into a single logical unit. All the reads and writes in a transaction are executed as one operation: either the entire transaction succeeds (commit) or it fails (abort, rollback). This abstraction simplifies the programming model for applications by delegating the handling of partial failures and complex concurrency issues to the database system.

## 3.1 The Lost Update Problem

A classic concurrency problem in transactions is the "Lost Update". It happens when two clients concurrently read the same data, modify it, and write it back. If they don't coordinate, one client's update can overwrite the other's without incorporating it.

In this Python simulation, we'll demonstrate a lost update on a bank account balance and how using a simple Mutex (Lock) can prevent it, which conceptually mimics how databases use locks for isolation.

### Problem

Alice and Bob both want to deposit $10 into the same account simultaneously. If the balance is initially $100, the final balance should be $120. However, if they read the balance at the same time, they might both read $100, add $10, and both write $110, causing a "lost update".

```python
import threading
import time

class BankAccount:
    def __init__(self, initial_balance):
        self.balance = initial_balance
        self.lock = threading.Lock()

    def deposit_without_lock(self, amount, user):
        # 1. Read balance
        current_balance = self.balance
        print(f"[{user}] Read balance: {current_balance}")
        
        # Simulate some processing delay or network latency
        time.sleep(0.1) 
        
        # 2. Modify and Write back
        self.balance = current_balance + amount
        print(f"[{user}] Wrote new balance: {self.balance}")

    def deposit_with_lock(self, amount, user):
        # Using a lock to ensure exclusive access (similar to database locks)
        with self.lock:
            # 1. Read balance
            current_balance = self.balance
            print(f"[{user}] (Locked) Read balance: {current_balance}")
            
            # Simulate some processing delay
            time.sleep(0.1) 
            
            # 2. Modify and Write back
            self.balance = current_balance + amount
            print(f"[{user}] (Locked) Wrote new balance: {self.balance}")

# ==========================================
# DEMO 1: Unsafe Concurrent Updates (Lost Update)
# ==========================================
account1 = BankAccount(100)

thread1 = threading.Thread(target=account1.deposit_without_lock, args=(10, "Alice"))
thread2 = threading.Thread(target=account1.deposit_without_lock, args=(10, "Bob"))

thread1.start()
thread2.start()
thread1.join()
thread2.join()

print(f"Final balance after unsafe deposits: {account1.balance}\n")

# ==========================================
# DEMO 2: Safe Concurrent Updates (Using Locks)
# ==========================================
account2 = BankAccount(100)

thread3 = threading.Thread(target=account2.deposit_with_lock, args=(10, "Alice"))
thread4 = threading.Thread(target=account2.deposit_with_lock, args=(10, "Bob"))

thread3.start()
thread4.start()
thread3.join()
thread4.join()

print(f"Final balance after safe deposits: {account2.balance}")
```

### Result

```terminal
[Alice] Read balance: 100
[Bob] Read balance: 100
[Alice] Wrote new balance: 110
[Bob] Wrote new balance: 110
Final balance after unsafe deposits: 110

[Alice] (Locked) Read balance: 100
[Alice] (Locked) Wrote new balance: 110
[Bob] (Locked) Read balance: 110
[Bob] (Locked) Wrote new balance: 120
Final balance after safe deposits: 120
```

Without isolation (locks), the update from either Alice or Bob is lost, resulting in $110. With proper isolation, the operations are serialized, correctly resulting in $120.

# 4. Specific Application Cases & Concept Review

## 4.1 The ACID Meaning

The safety guarantees provided by transactions are often described by the acronym ACID.

| Property       | Meaning |
| :------------- | :------ |
| **Atomicity**  | All or nothing. If a transaction is aborted, the database must discard or undo any writes made in that transaction. It guarantees partial failures are safely rolled back. |
| **Consistency**| The database remains in a "good" or valid state. It ensures data invariants are maintained. (Often considered an application-level property rather than a database one). |
| **Isolation**  | Concurrently executing transactions are isolated from each other. They should not step on each other's toes (e.g., resulting in lost updates or dirty reads). |
| **Durability** | Once a transaction commits successfully, any data it has written will not be forgotten, even in the event of a hardware fault or database crash. |

## 4.2 Weak Isolation Levels

Databases don't always use Serializable isolation because of performance costs. Instead, they use weaker levels.

| Isolation Level | Guarantees | Vulnerable to | Typical Implementation |
| :--- | :--- | :--- | :--- |
| **Read Uncommitted** | Prevents dirty writes. | Dirty Reads, Read Skew, Lost Updates, Write Skew, Phantoms. | Row-level write locks. |
| **Read Committed** | Prevents dirty writes and dirty reads. | Read Skew, Lost Updates, Write Skew, Phantoms. | Row-level write locks + reading old values while locks are held. |
| **Snapshot Isolation / Repeatable Read** | Prevents dirty writes, dirty reads, and read skew (non-repeatable reads). | Lost Updates (sometimes), Write Skew, Phantoms. | Multi-Version Concurrency Control (MVCC). |
| **Serializable** | Prevents all race conditions. Complete isolation. | None. | Actual Serial Execution, 2-Phase Locking (2PL), Serializable Snapshot Isolation (SSI). |

## 4.3 Race Conditions Explained

| Phenomenon | Description |
| :--- | :--- |
| **Dirty Read** | Reading data that has been written by a transaction but not yet committed. |
| **Dirty Write** | Overwriting data that was written by an uncommitted transaction. |
| **Read Skew (Non-repeatable Read)** | Reading the same object twice in a transaction and seeing different values because a concurrent transaction modified it and committed in between. |
| **Lost Update** | Two clients read a value, modify it, and write it back. One client's write overwrites the other without including its changes. |
| **Write Skew** | A transaction reads something, makes a decision based on the read, and writes to the database. However, by the time the write occurs, the premise of the decision is no longer true due to a concurrent write. |
| **Phantom Read** | A transaction reads a set of rows that match a search condition. Another transaction modifies the data (inserts/deletes), changing the set of rows that match the condition for the first transaction. |

## 복제 (Replication)

- **복제**: 동일한 데이터의 복사본을 네트워크로 연결된 여러 노드에 유지
- 이유:
	- **지연 감소**: 사용자와 지리적으로 가까운 노드에서 서빙
	- **가용성 향상**: 일부 노드 장애 시에도 서비스 유지
	- **읽기 처리량 확장**: 여러 노드에서 병렬 읽기

- 어려운 부분: **변경되는 데이터**를 어떻게 복제하느냐
- 세 가지 주요 알고리즘: **단일 리더**, **다중 리더**, **리더 없음**

---

## 1. 리더와 팔로워 (단일 리더 복제)

- 노드 중 하나를 **리더(leader/master/primary)** 로 지정
- 쓰기는 반드시 리더로만 → 리더가 팔로워에 **복제 로그(replication log)** 전달
- 팔로워(replica/secondary)는 복제 로그를 받아 같은 순서로 적용
- **읽기는 리더 또는 팔로워 어디서든 가능**
- 예: PostgreSQL, MySQL, Oracle Data Guard, SQL Server, MongoDB, Kafka, RabbitMQ

### 동기식 vs 비동기식 복제

- **동기식**: 리더가 팔로워의 확인을 기다림 → 팔로워는 항상 최신 데이터 보장, 하지만 하나라도 느리면 쓰기 전체가 막힘
- **비동기식**: 리더가 팔로워 확인 안 기다림 → 빠르지만 팔로워가 뒤처질 수 있음, 리더 장애 시 미복제 데이터 유실 가능
- **반동기식(semi-synchronous)**: 팔로워 하나는 동기, 나머지는 비동기 → 균형점

### 새 팔로워 추가

- 단순히 복사하면 안 됨 — 복사 중에도 데이터가 계속 바뀜
- **절차**:
	1. 리더의 데이터 스냅샷 (잠금 없이 가능해야 함)
	2. 스냅샷을 새 팔로워에 복사
	3. 팔로워가 스냅샷 이후의 변경분 요청 (로그 포지션 기준: PostgreSQL은 *log sequence number*, MySQL은 *binlog coordinates*)
	4. 따라잡기 완료 → 정상 운영

### 노드 중단 처리

**팔로워 장애 — 따라잡기 복구**
- 팔로워 자신의 로그에서 마지막으로 처리한 트랜잭션 확인
- 리더에 그 이후 변경분 요청 → 따라잡으면 정상 복구

**리더 장애 — 장애 복구 (Failover)**
1. 리더가 죽었는지 판단 (보통 타임아웃)
2. 새 리더 선출 (팔로워 중 최신 데이터를 가진 노드 선택) — 합의 문제
3. 새 리더로 쓰기 요청 리다이렉트, 옛 리더가 살아 돌아오면 팔로워로 전환

**장애 복구의 어려움**
- 비동기 복제 → 새 리더가 이전 쓰기를 일부 못 받을 수 있음 → 데이터 유실
- "옛 리더가 살아났는데 새 리더와 충돌" — GitHub 사례: MySQL 자동 증가 키가 재사용돼 Redis와 불일치 → 개인정보 노출
- **스플릿 브레인**: 두 노드가 동시에 자기가 리더라고 생각 → 두 곳에 쓰기 발생 → 데이터 충돌
- 타임아웃 설정 어려움: 너무 짧으면 불필요한 failover, 너무 길면 복구 느림

### 복제 로그 구현 방식

**구문 기반 복제 (Statement-based)**
- SQL 구문을 그대로 팔로워에 전달
- 문제: `NOW()`, `RAND()` 등 비결정적 함수, AUTO_INCREMENT, 사이드 이펙트 → 팔로워마다 결과 다를 수 있음
- MySQL 5.1 이전 사용, 현재는 비권장

**WAL 전달 (WAL Shipping)**
- 리더의 WAL(연속 바이트 시퀀스)을 팔로워에게 전달
- PostgreSQL, Oracle 사용
- 단점: WAL은 스토리지 엔진에 매우 밀착 → DB 버전 업그레이드 시 리더/팔로워가 동시에 다른 버전을 사용 불가 (무중단 업그레이드 어려움)

**행 기반 복제 (Row-based, Logical Log)**
- 스토리지 엔진 포맷과 분리된 **논리적 로그** 사용
- 행 수준에서 삽입/수정/삭제 내역 기록 (변경 전/후 값)
- MySQL binlog가 이 방식
- 스토리지 엔진과 독립 → 버전 다른 리더/팔로워 가능, 외부 시스템 전달(CDC)에 활용

**트리거 기반 복제**
- DB 트리거로 변경사항을 별도 테이블에 기록 → 외부 프로세스가 읽어 전달
- 유연하지만 오버헤드 크고 버그 가능성 높음
- Bucardo(PostgreSQL), Databus(Oracle) 등

## 2. 복제 지연 문제 (Replication Lag)

- 비동기 복제에서 팔로워가 뒤처지면 같은 질의를 리더/팔로워에서 다르게 응답 → **최종 일관성(eventual consistency)**
- 복제 지연이 수초~수분이면 문제가 됨

### 자신이 쓴 내용 읽기 (Read-Your-Writes)

- 문제: 사용자가 쓴 후 즉시 읽으면 팔로워가 아직 반영 못해서 이전 내용이 나올 수 있음
- 해결책:
	- 사용자가 수정 가능한 데이터는 항상 리더에서 읽기 (예: 자기 프로필 → 리더, 남의 프로필 → 팔로워)
	- 마지막 쓰기 후 1분 이내면 리더에서 읽기
	- 클라이언트가 최근 쓰기의 타임스탬프를 기억 → 해당 시점 이후 반영된 복제본에서만 읽기
	- 여러 기기 간 **크로스 기기 읽기 후 자신의 쓰기** 보장은 더 어려움 (기기 간 타임스탬프 공유 필요)

### 단조 읽기 (Monotonic Reads)

- 문제: 사용자가 팔로워 A → 팔로워 B로 연속 읽기 시, B가 A보다 더 뒤처져 있으면 시간이 거꾸로 흐르는 것처럼 보임
- 예: 댓글이 보였다가 사라졌다가 하는 현상
- 해결: **사용자 ID 기반으로 항상 같은 복제본에서 읽기** (해시 기반 라우팅)

### 일관된 접두사 읽기 (Consistent Prefix Reads)

- 문제: 쓰기 순서 A → B인데 팔로워에 B만 도달하고 A가 늦으면, 읽는 쪽에서 B를 먼저 보게 됨
- 인과관계가 있는 쓰기들이 항상 같은 순서로 읽혀야 함
- 해결: 인과적으로 연관된 쓰기는 같은 파티션에 → 어렵거나 비효율적

### 복제 지연 해결의 어려움

- 애플리케이션 코드에서 복제 지연을 신경 쓰게 하면 복잡도 폭증
- → **트랜잭션**이 이 문제를 DB가 직접 보장하는 방법 (6, 7장에서 다룸)

## 3. 다중 리더 복제

- 여러 노드가 쓰기를 받아 처리 → 각 리더는 다른 리더에게 변경 전달
- **언제 유용한가?**

### 다중 데이터센터

- 단일 리더: 모든 쓰기가 리더 데이터센터를 통해야 함 → 지연, 가용성 위협
- 다중 리더: 데이터센터마다 리더 → 각 데이터센터 내 지연만 신경 쓰면 됨
- 데이터센터 간 복제는 비동기 → 내부는 빠름, 데이터센터 간 전달은 백그라운드
- **단점**: 같은 데이터를 두 곳에서 동시에 수정 → **쓰기 충돌** 발생 가능 → 다중 리더의 핵심 어려움
- 많은 앱(외부 프레임워크 Tungsten for MySQL, BDR for PostgreSQL)이 쓰기 충돌 처리를 직접 구현

### 오프라인 클라이언트 (오프라인 작업)

- 모바일 앱, 캘린더 앱 등 인터넷 없이도 수정 가능 → 다시 온라인 시 동기화
- 각 기기의 로컬 DB가 리더 역할, 기기 간 동기화가 다중 리더 복제와 동일
- CouchDB, Google Docs 등

### 쓰기 충돌 처리

**충돌 감지**
- 단일 리더: 충돌이 즉시 감지 (동시 쓰기 시 두 번째는 블록)
- 다중 리더: 충돌이 나중에야 감지 → 이미 양쪽 사용자에게 성공 응답 후 충돌 발견

**충돌 회피**
- 특정 레코드는 항상 같은 리더로 → 충돌 없음
- 단, 리더 변경 필요 시(사용자가 다른 데이터센터로 이동) 충돌 발생 가능

**일관된 상태로 수렴**
- 최종적으로 하나의 값으로 합의해야 함 (모든 복제본이 같아져야)
- 방법:
	- **LWW(Last Write Wins)**: 최신 타임스탬프 값 채택 — 데이터 유실 위험
	- **높은 ID 우선**: 리더 ID 높은 쪽 승리 — 역시 데이터 유실
	- **병합**: 충돌 값을 합쳐 보존 (예: `B/C` 형태)
	- **충돌 보존 + 사용자 해결**: 앱 코드나 사용자에게 충돌 해결 위임 (CouchDB)

**커스텀 충돌 해결 로직**
- 쓰기 시: 충돌 감지 즉시 핸들러 호출 (Bucardo)
- 읽기 시: 모든 충돌 버전 저장, 읽을 때 앱에 반환 → 앱이 해결 후 재작성 (CouchDB)
- 자동 충돌 해결 연구: 충돌 없는 복제 자료 구조(CRDT), 병합 함수(Operational Transformation) 등

### 다중 리더 복제 토폴로지

- **원형(circular)**: 각 노드가 다음 노드에만 전달 → 한 노드 장애 시 복제 끊김
- **별형(star)**: 중앙 노드가 모두에게 전달 → 중앙 노드 단일 장애점
- **전체 연결(all-to-all)**: 모든 리더가 모든 리더에게 전달 → 가장 내결함성 높음, 하지만 메시지 순서 문제 발생 가능
	- 인과성 위반: 쓰기 A → B 순인데 B가 A보다 먼저 도달할 수 있음
	- 해결: **버전 벡터(version vector)** 사용

## 4. 리더 없는 복제 (Leaderless Replication)

- Amazon Dynamo에서 부활시킨 아이디어 → **Dynamo 스타일**
- Cassandra, Riak, Voldemort 등

### 쓰기와 읽기

- 클라이언트가 모든 복제본(또는 코디네이터를 통해)에 직접 쓰기 전송
- 일부 복제본이 다운돼 있으면 해당 쓰기는 놓침
- **읽기도 여러 복제본에서 병렬로** → 버전 번호로 최신 값 판단

**읽기 복구 (Read Repair)**
- 읽기 시 복제본들의 값이 다름 → 클라이언트가 최신 값을 오래된 복제본에 다시 씀

**안티 엔트로피 프로세스 (Anti-Entropy)**
- 백그라운드 프로세스가 복제본 간 차이를 감지하고 동기화 (순서 보장 없음)

### 쿼럼 읽기/쓰기

- n개의 복제본 중:
	- 쓰기 성공 조건: **w** 개 복제본 확인
	- 읽기: **r** 개 복제본에서 읽기
	- `w + r > n` 이면 최신 값 읽기 보장
- 예: n=3, w=2, r=2 → 하나 노드 장애 허용
- n=5, w=3, r=3 → 두 노드 장애 허용

**쿼럼의 한계**
- 네트워크 파티션 → 일부 복제본에만 쓰기 성공 후 장애 복구 → 이전 값 덮어씌울 위험
- 쓰기와 읽기가 동일 노드에서 겹치지 않을 수 있음 (운이 나쁘면 최신 값 못 읽음)
- 쓰기 중 장애 → 일부 복제본 성공, 일부 실패 → 롤백 없음
- 결론: **쿼럼은 완전한 일관성 보장이 아님** — 확률적 보장

**느슨한 쿼럼 (Sloppy Quorum)**
- n개 지정 노드가 아닌, 살아있는 임의 노드에 쓰기 가능
- 네트워크 장애 시 가용성 높임, 하지만 w + r > n 보장 안 됨
- **hinted handoff**: 임시 노드가 보관하다가 원래 노드 복구 시 전달

### 동시 쓰기 감지

- 여러 클라이언트가 같은 키에 동시 쓰기 → 충돌 발생

**LWW (Last Write Wins)**
- 각 쓰기에 타임스탬프 부여, 최신 것만 유지
- Cassandra 기본 방식
- **데이터 유실** 발생: 동시 쓰기 중 하나가 버려짐
- LWW 쓸 경우 키를 immutable로 사용하는 게 안전 (한 번만 쓰는 경우)

**"이전" 관계와 동시성**
- 쓰기 A가 B보다 먼저 → A는 B의 맥락을 알 수 있음
- 두 쓰기가 서로 모른다면 → 동시(concurrent)
- 동시성 판단: 타임스탬프 X, 인과관계로 판단 (버전 번호 사용)

**버전 벡터 (Version Vectors)**
- 단일 복제본: 버전 번호 하나
- 다중 복제본: 복제본마다 버전 번호 → 버전 벡터
- 어떤 값이 이전이고 어떤 것이 동시인지 판단 가능
- 클라이언트가 읽을 때 버전 벡터도 받아 → 쓸 때 함께 전달 → DB가 동시 쓰기 판단
- Riak에서는 **dotted version vector** 라고 부름

## 저장소와 검색

- DB가 내부적으로 어떻게 데이터를 저장하고 검색하는지 알아야 적합한 스토리지 엔진을 선택하고 튜닝할 수 있음
- 스토리지 엔진은 크게 두 가지 계열:
	- **로그 구조(log-structured)**: LSM-Tree 기반
	- **페이지 지향(page-oriented)**: B-Tree 기반
- OLTP(온라인 트랜잭션 처리) vs OLAP(온라인 분석 처리)도 저장소 선택에 영향

---

## 1. 데이터베이스를 강화하는 자료 구조

### 가장 단순한 DB: append-only 로그

```bash
#!/bin/bash
db_set () { echo "$1,$2" >> database; }
db_get () { grep "^$1," database | tail -n 1 | cut -d',' -f2; }
```

- 쓰기: O(1) — 파일 끝에 추가만 하면 됨
- 읽기: O(n) — 전체 파일 스캔
- 인덱스가 없으면 읽기가 너무 느림 → 인덱스 필요

**인덱스의 트레이드오프**
- 인덱스는 읽기를 빠르게 하지만 쓰기를 느리게 만듦
- 따라서 모든 컬럼에 자동으로 인덱스 걸지 않고 개발자가 수동으로 선택

---

### 해시 인덱스 (Hash Index)

- 키 → 파일 내 바이트 오프셋 매핑을 메모리 해시맵으로 유지
- **Bitcask** (Riak의 기본 스토리지 엔진)가 이 방식
	- 모든 키가 메모리에 있어야 함 → 키가 많지 않고 값이 자주 갱신되는 경우에 적합
	- 예: URL별 조회수 카운터

**Compaction (압축)**
- append-only이므로 로그가 무한히 커지는 걸 막아야 함
- 세그먼트로 나누고, 세그먼트마다 compaction 수행 (중복 키 제거, 최신 값만 유지)
- 여러 세그먼트를 병합(merge)할 수도 있음 → 백그라운드 스레드에서 처리

**구현 시 고려사항**
- **파일 포맷**: 이진 형식이 CSV보다 빠르고 단순
- **레코드 삭제**: 삭제 표시(tombstone)를 추가, 병합 시 해당 키 버림
- **충돌 복구**: 크래시 시 해시맵 유실 → 각 세그먼트 스냅샷으로 복구 속도 향상
- **부분 쓰기 레코드**: 체크섬으로 손상된 레코드 감지
- **동시성 제어**: 쓰기 스레드 하나, 읽기 스레드 여럿

**append-only가 좋은 이유**
- 순차 쓰기가 임의 쓰기보다 훨씬 빠름 (HDD는 물론 SSD도)
- 동시성과 충돌 복구가 단순함 (덮어쓰면 이전 값 손상 가능성)
- 세그먼트 병합으로 단편화 방지

**한계**
- 모든 키가 메모리에 들어와야 함 → 메모리 부족 시 문제
- 범위 쿼리 비효율: "kitty00000 ~ kitty99999" 같은 범위는 키 하나하나 조회해야 함

### SSTable과 LSM-Tree

**SSTable (Sorted String Table)**
- 세그먼트 파일에서 키-값 쌍을 **키 기준으로 정렬**
- 해시 인덱스 대비 장점:
	1. 세그먼트 병합이 효율적 — 여러 파일을 동시에 읽으며 merge sort (외부 정렬)
	2. 인덱스를 sparse하게 유지 가능 → 메모리 절약 (인덱스 항목 사이 범위는 스캔)
	3. 범위 쿼리 블록 압축 가능

**SSTable 구성 방법 — LSM-Tree**
1. 쓰기 → 메모리 내 균형 트리(**memtable**, 보통 red-black tree)에 추가
2. memtable이 일정 크기(수 MB) 초과 → 디스크에 SSTable로 플러시
3. 읽기 → memtable 먼저, 그 다음 최신 SSTable, 이전 SSTable 순으로 확인
4. 백그라운드에서 주기적으로 compaction 및 병합 수행
5. 크래시 대비: 별도 append-only 로그에 모든 쓰기 기록 → memtable 복구용

**성능 최적화**
- 없는 키 조회 시 모든 SSTable 확인해야 함 → **Bloom filter**로 사전 차단
- Compaction 전략:
	- **Size-tiered**: 작은 SSTable을 모아 더 큰 SSTable로 병합 (HBase, Cassandra 기본)
	- **Leveled**: 키 범위로 쪼개어 레벨별로 관리, 더 적은 공간 사용 (LevelDB, RocksDB)

**LSM-Tree 사용 DB**: LevelDB, RocksDB, Cassandra, HBase, Lucene(검색 인덱스)

### B-Tree

- 가장 널리 사용되는 인덱스 구조 (1970년 도입, 여전히 표준)
- 고정 크기 **페이지**(보통 4KB) 단위로 데이터 읽기/쓰기
	- 디스크도 고정 크기 블록 단위 → 하드웨어와 잘 맞음
- 각 페이지는 n개의 키와 n+1개의 자식 페이지 참조 (**branching factor**, 보통 수백)
- 항상 balanced → 트리 높이 O(log n), 4단계 트리면 4TB까지 커버

**값 갱신**
- 리프 페이지를 찾아 값 변경 후 재기록
- 새 키 추가 시 공간 부족하면 페이지를 둘로 분할 → 부모 페이지 갱신

**신뢰성**
- 크래시 시 트리 불일치 가능성 (분할 도중 장애 등)
- 모든 변경 전 **WAL(Write-Ahead Log, redo log)** 기록 → 복구에 사용
- 동시성: 래치(가벼운 잠금)로 여러 스레드가 같은 페이지 동시 수정 방지

**최적화 기법**
- Copy-on-write: 수정 시 새 위치에 쓰고 부모가 가리키도록 → 동시성에 유리 (LMDB)
- 키 약어 저장: 내부 페이지는 경계만 구분하면 되므로 키를 줄여 branching factor 증가
- 리프 페이지 순서 배치: 범위 스캔 시 순차 읽기를 위해 물리적으로 연속 배치 (유지 어려움)
- 형제 포인터: 리프 페이지가 양쪽 형제를 가리킴 → 부모 이동 없이 순차 스캔

---

### B-Tree vs LSM-Tree 비교

| 항목 | B-Tree | LSM-Tree |
|------|--------|----------|
| 읽기 성능 | 빠름 | 비교적 느림 (여러 SSTable 확인) |
| 쓰기 성능 | 느림 (WAL + 페이지 기록) | 빠름 (순차 쓰기) |
| Write amplification | 낮음 | 높음 (compaction 반복) |
| 공간 효율 | 단편화 가능 | 압축으로 효율적 |
| 쓰기 예측 가능성 | 높음 | 낮음 (compaction 영향) |
| 키 중복 | 없음 (한 위치에만 존재) | 있음 (compaction 전까지) |

- LSM-Tree는 쓰기 처리량 높은 워크로드에 유리
- B-Tree는 트랜잭션 격리를 키 범위 잠금으로 구현하기 쉬움 → 관계형 DB가 선호

---

### 기타 인덱싱 구조

**보조 인덱스 (Secondary Index)**
- 기본 키 외 컬럼으로 검색 시 필요
- 문제: 한 인덱스 항목이 여러 로우를 가리킬 수 있음
	- 해결 1: 항목 값에 로우 ID 목록 저장
	- 해결 2: 항목에 행 번호 suffix 추가하여 키를 고유하게 만듦
- B-Tree와 LSM-Tree 모두 보조 인덱스 지원

**클러스터드 인덱스 vs 힙 파일**
- **힙 파일**: 인덱스는 실제 데이터의 위치(힙 파일 내 오프셋)를 가리킴
	- 여러 인덱스가 같은 데이터를 참조 → 데이터 중복 없음
	- 값 갱신 시 같은 크기면 제자리 갱신, 커지면 새 위치로 이동 + 포인터 갱신
- **클러스터드 인덱스**: 인덱스 내에 실제 데이터를 함께 저장
	- 읽기 성능 향상 (포인터 따라가는 과정 불필요)
	- InnoDB: 기본 키가 항상 클러스터드 인덱스
- **커버링 인덱스 (covering index)**: 자주 쓰는 쿼리 컬럼을 인덱스에 포함 → 인덱스만으로 응답 가능

**다중 컬럼 인덱스 (Multi-column Index)**
- 단일 키로 여러 컬럼을 묶어 질의
- 연결(concatenated) 인덱스: (성, 이름) → 성으로 정렬, 같은 성 안에서 이름 정렬
	- 성+이름 동시 검색 또는 성만으로 검색 가능 / 이름만으로는 사용 불가
- 공간 인덱스 (R-tree): 위도+경도 같은 2차원 검색 → PostGIS 등에서 사용

**전문 검색 및 퍼지 인덱스**
- 오타 허용, 유사어 검색 등 → Lucene이 FSM(유한 상태 기계) 기반 인덱스 사용
- Levenshtein automaton: 특정 편집 거리 내의 단어를 효율적으로 검색

## 2. 트랜잭션 처리와 분석 처리

| 항목 | OLTP | OLAP |
|------|------|------|
| 주요 읽기 패턴 | 조건으로 소수 레코드 조회 | 많은 레코드 집계 |
| 주요 쓰기 패턴 | 사용자 입력 기반 임의 접근, 낮은 지연 | 대량 가져오기 또는 이벤트 스트림 |
| 주로 사용하는 쪽 | 최종 사용자 (웹 앱 등) | 내부 분석가 |
| 데이터 표현 | 현재 데이터 (최신 상태) | 이벤트 이력 (시간에 따른 변화) |
| 데이터셋 크기 | GB ~ TB | TB ~ PB |

- 1970~80년대엔 OLTP/OLAP 구분 없이 같은 DB 사용
- 이후 OLAP는 별도 **데이터 웨어하우스(Data Warehouse)** 로 분리

### 데이터 웨어하우스

- OLTP DB에서 ETL(Extract-Transform-Load)로 데이터 복사
- 분석가가 OLTP 시스템 부담 없이 쿼리 가능
- SQL 인터페이스는 비슷하지만 내부 구조가 다름 → OLTP 엔진과 최적화 방향 다름
- 상용: Teradata, Vertica, SAP HANA, ParAccel(Redshift) / 오픈소스: Apache Hive, Spark SQL, Presto

**별 모양 스키마와 눈꽃 모양 스키마**
- 데이터 웨어하우스의 전형적 구조
- **팩트 테이블**: 비즈니스 이벤트 각각을 로우로 저장 (개별 판매, 페이지뷰 등)
	- 컬럼 수가 수백 개에 달하기도 함
- **차원 테이블**: 팩트의 속성을 저장 (날짜, 제품, 고객, 매장 등)
- **별 모양 스키마**: 팩트 테이블 중심, 차원 테이블이 주변 배치 → 조인이 단순
- **눈꽃 모양 스키마**: 차원 테이블을 더 세분화 → 정규화됐지만 쿼리 더 복잡

## 3. 칼럼 지향 저장소 (Column-Oriented Storage)

- 팩트 테이블: 컬럼 수백 개 + 수십억 로우 → 일반 OLTP 인덱스로는 역부족
- OLAP 쿼리는 보통 컬럼 몇 개만 사용 (예: `SELECT SUM(price) ... WHERE date = ...`)
- **칼럼 지향 저장소**: 각 컬럼을 별도 파일에 저장 → 필요한 컬럼만 읽음

```sql
-- 이 쿼리는 100개 컬럼 중 date, product, quantity, net_price 4개만 씀
SELECT
  product_sk,
  SUM(quantity * net_price) AS total_sales
FROM fact_sales
WHERE date_key BETWEEN 20240101 AND 20241231
GROUP BY product_sk;
```

- 로우 기반 저장이면 쿼리하지 않는 컬럼 데이터까지 디스크에서 읽어야 함 → 낭비

### 칼럼 압축

- 같은 컬럼 내 값들이 비슷한 경우가 많음 → 압축에 유리
- **비트맵 인코딩**: 각 고유값에 비트맵 하나씩 → 카디널리티 낮으면 매우 효율적
	- 비트맵에 런 길이 인코딩(RLE) 추가로 공간 절약
	- WHERE 조건 = 비트맵 AND/OR 연산 → 매우 빠름 (CPU 친화적)
- Cassandra, HBase의 **컬럼 패밀리**: 칼럼들을 로우 키 기준으로 함께 저장 → 진정한 칼럼 지향은 아님

### 칼럼 저장소의 정렬

- 칼럼별로 독립 정렬하면 순서 잃음 → 로우 단위로 같이 정렬해야 함
- 가장 자주 쓰는 쿼리 기준으로 정렬 컬럼 선택 → 날짜로 정렬하면 날짜 범위 쿼리 빠름
- **C-Store / Vertica**: 동일 데이터를 다른 방식으로 정렬해서 여러 벌 저장
	- 어차피 중복 저장하므로 정렬 순서도 여러 개 유지

### 칼럼 지향 저장소의 쓰기

- 압축된 칼럼에 중간 삽입 어려움 → B-Tree 쓰기 방식이 작동 안 함
- **LSM-Tree와 유사한 방식**: 쓰기를 메모리 버퍼에 모았다가 디스크 칼럼 파일에 병합
- 쿼리 시 디스크 + 메모리 양쪽 합쳐서 응답 (Vertica가 이 방식)

### 집계: 데이터 큐브와 구체화 뷰

- **구체화 뷰(Materialized View)**: 자주 쓰는 집계 쿼리 결과를 실제 저장
	- 갱신 비용: 기반 데이터 바뀌면 뷰도 갱신해야 함 → OLTP에는 비효율
	- OLAP에서는 읽기가 많고 쓰기가 적어 효과적
- **데이터 큐브 (OLAP 큐브)**: 여러 차원으로 집계한 값을 격자 형태로 저장
	- 예: 날짜 × 제품별 총매출을 미리 계산
	- 쿼리 매우 빠름 but 유연성 없음 — 미리 정의된 차원 집계만 빠름
	- 상세 데이터가 필요한 쿼리엔 원본 데이터가 필요

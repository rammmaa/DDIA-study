## 인코딩과 발전

- 앱 기능 추가/변경 → 데이터 스키마도 변경 필요
- 변경이 생겨도 시스템이 계속 잘 돌아가려면:
	- **하위 호환성(backward compatibility)**: 새 코드가 옛 데이터를 읽을 수 있음
	- **상위 호환성(forward compatibility)**: 옛 코드가 새 데이터를 읽을 수 있음 (더 어려움)
- 서버 롤링 업그레이드, 모바일 앱처럼 사용자가 업데이트를 미루는 경우 등 → 여러 버전이 동시에 실행

## 1. 데이터 인코딩 형식

- 데이터는 두 가지 형태로 존재:
	- **메모리**: 객체, 구조체, 리스트, 해시맵 등 → CPU가 효율적으로 접근 가능
	- **디스크/네트워크**: 바이트 시퀀스 → 포인터는 의미 없어서 인코딩 필요

- **인코딩(직렬화/마샬링)**: 메모리 → 바이트 시퀀스
- **디코딩(역직렬화/언마샬링)**: 바이트 시퀀스 → 메모리

### 언어 내장 인코딩

- Java의 `Serializable`, Python의 `pickle`, Ruby의 `Marshal` 등
- **문제점**:
	- 특정 언어에 종속 → 다른 언어로 읽기 어려움
	- 버전 관리가 취약 (하위/상위 호환성 소홀히 하기 쉬움)
	- 보안 취약점 — 역직렬화 시 임의 클래스 인스턴스화 가능
	- 성능 낮음
- **결론**: 임시 용도 외에는 사용하지 말 것

### JSON, XML, CSV

**장점**
- 사람이 읽을 수 있음 (human-readable)
- 언어 중립적, 거의 모든 환경에서 지원
- 웹 API는 주로 JSON 사용

**단점**
- **숫자 모호함**: JSON은 정수/소수 구분 없음, 2^53 초과 정수는 부정확 (Twitter ID 문제)
- **바이너리 미지원**: Base64 인코딩하면 크기 33% 증가
- **스키마 없음**: 선택적 스키마 지원이 있지만 복잡하고 잘 안 씀
- **XML**: 장황하고 복잡
- **CSV**: 타입 없음, 값에 쉼표/줄바꿈 포함 시 처리 복잡

### 이진 인코딩 (Binary Encoding)

**MessagePack**
- JSON 이진 인코딩 — 공간 절약은 크지 않음 (필드명이 그대로 포함되므로)

**Thrift (Facebook) & Protocol Buffers (Google)**
- 스키마를 별도로 정의하고 코드를 생성해서 사용
- 필드명 대신 **필드 태그 번호** 사용 → 공간 절약

```protobuf
// Protocol Buffers 스키마 예시
message Person {
    required string user_name       = 1;
    optional int64  favourite_number = 2;
    repeated string interests       = 3;
}
```

- Thrift BinaryProtocol: 필드 타입+번호+값 직렬화 → 필드명 없어서 JSON보다 작음
- Thrift CompactProtocol: 타입과 태그 번호를 한 바이트로 합치고 가변 길이 정수 사용 → 더 작음
- **Protocol Buffers**: Thrift CompactProtocol과 유사, 인코딩 방식 약간 다름

**필드 태그와 스키마 발전**

- 새 필드 추가:
	- 새 태그 번호 사용 → 옛 코드는 모르는 태그를 무시 → **상위 호환성** 유지
	- 새 필드가 required이면 하위 호환성 깨짐 → 반드시 optional로 추가
- 필드 삭제:
	- optional 필드만 삭제 가능
	- 삭제된 태그 번호는 절대 재사용 금지 → 옛 코드가 남긴 데이터 혼란 방지
- 데이터 타입 변경:
	- 32비트 → 64비트: 새 코드가 64비트로 읽음, 옛 코드가 64비트 값 읽으면 잘림
	- **Protocol Buffers**: repeated 필드는 0개 이상이므로 optional을 repeated로 변경 가능

### Avro (Apache)

- Hadoop 프로젝트의 일환으로 시작
- Thrift/Protobuf와 다른 접근 — **필드 태그 번호 없음**

```json
// Avro 스키마 (JSON 표현)
{
  "type": "record",
  "name": "Person",
  "fields": [
    {"name": "userName",        "type": "string"},
    {"name": "favouriteNumber", "type": ["null", "long"], "default": null},
    {"name": "interests",       "type": {"type": "array", "items": "string"}}
  ]
}
```

- 인코딩: 값들을 필드 구분자 없이 순서대로 나열 → 매우 컴팩트
- 디코딩: 스키마를 알아야만 읽을 수 있음 (어디서 하나의 값이 끝나는지도 모름)
- 핵심 아이디어: **쓰기 스키마(writer's schema)** 와 **읽기 스키마(reader's schema)** 가 달라도 됨

**스키마 발전 방식**
- Avro 라이브러리가 쓰기/읽기 스키마를 **나란히 놓고 비교** (이름으로 매칭)
- 필드 순서가 달라도 무방, 이름으로 맞춤
- 읽기 스키마에만 있는 필드 → 기본값으로 채움
- 쓰기 스키마에만 있는 필드 → 무시
- 필드 추가/삭제 시 반드시 **기본값** 있어야 함 (null 포함)
- 타입 변경: Avro 타입 변환 규칙에 따라 제한적으로 허용

**쓰기 스키마는 어디에?**
- 대용량 파일: 파일 헤더에 스키마 한 번 포함 (Avro의 Object Container Files)
- DB 레코드: 버전 번호로 스키마 레지스트리 참조
- 네트워크: 연결 수립 시 스키마 협상

**Avro의 장점**
- 동적 생성 스키마에 유리: DB 덤프 시 테이블 스키마에서 Avro 스키마 자동 생성 가능
- 코드 생성 없이도 사용 가능 → 동적 언어 친화적

---

### 스키마의 장점 정리

- Avro, Thrift, Protobuf 같은 이진 인코딩은 JSON/XML보다:
	- **더 작음**: 필드명 없이 태그/순서 사용
	- **스키마가 문서**: 별도 문서 없이도 코드로 인터페이스 이해 가능
	- **타입 체크**: 디코딩 전에 스키마 검사로 호환성 확인
	- **코드 생성**: IDE 자동완성, 컴파일 타임 타입 오류 감지

## 2. 데이터플로 모드

인코딩된 데이터가 어떻게 흘러가는지 — 프로세스 간 데이터 전달 방식 세 가지

### 데이터베이스를 통한 데이터플로

- 쓰는 프로세스가 인코딩, 읽는 프로세스가 디코딩
- "미래의 나에게 보내는 메시지"
- **하위 호환성**: 새 코드가 옛 코드가 쓴 데이터를 읽어야 하므로 필수
- **상위 호환성**: 롤링 업그레이드 중 옛 코드가 새 코드가 쓴 데이터를 읽을 수도 있음

**데이터 유실 주의**
- 옛 코드로 레코드를 읽고 다시 쓰면, 새 코드가 추가한 필드가 사라질 수 있음
- 해결: 모르는 필드는 그대로 유지하는 방식으로 구현

**스키마 마이그레이션**
- 보통 기존 데이터를 새 스키마로 재작성(migration)하지만 비용이 큼
- 대부분의 관계형 DB: `ALTER TABLE`로 새 컬럼 추가 + 기본값 설정
	- MySQL: 테이블 전체 복사 → 대형 테이블에서는 매우 느림
- 링크트인 Espresso, Cassandra 등은 컬럼 없으면 null 반환 → 마이그레이션 불필요

### 서비스를 통한 데이터플로: REST와 RPC

**웹 서비스 방식**
- 클라이언트-서버 구조: 웹 브라우저/모바일 앱, 또는 마이크로서비스 간 통신

**REST**
- HTTP 위에 구축된 설계 철학 — 표준 HTTP 기능(URL, verb, cache 등) 활용
- 단순하고 범용적, 디버깅 쉬움
- **OpenAPI(Swagger)**: REST API 명세 도구

**SOAP**
- XML 기반 프로토콜 — 매우 복잡하고 장황 → 현재 레거시 취급
- WSDL로 API 기술 → 자동 코드 생성 가능하지만 사람이 읽기 어려움

**RPC (Remote Procedure Call)**
- 네트워크 요청을 로컬 함수 호출처럼 보이게 만들자는 아이디어
- 구현: gRPC (Protobuf), Thrift RPC, Avro RPC, Finagle 등
- **문제: 네트워크 ≠ 로컬 함수**
	- 예측 불가능한 지연: 타임아웃 처리 필요
	- 부분 성공: 요청은 갔는데 응답만 안 온 경우 (멱등성 필요)
	- 반환 값이 없을 수 있음
	- 객체 직렬화 필요
	- 클라이언트와 서버가 다른 언어일 경우 타입 변환 문제

**현재의 RPC**
- 로컬 함수와 구별됨을 인정하는 방향으로 발전 (futures/promises, 스트리밍)
- 같은 조직 내 서비스 간 통신에 주로 사용 (외부 API는 REST 선호)
- **API 발전**: 서버 먼저 배포하므로 하위 호환성이 핵심, API 버저닝(URL에 v1, v2 등)

### 메시지 전달을 통한 비동기 데이터플로

- REST/RPC는 동기 (요청 → 응답 대기)
- 데이터베이스는 영구 저장
- **메시지 브로커(Message Broker)**: 중간 어딘가에 위치, 비동기

**메시지 브로커의 장점**
- 수신자가 다운돼 있어도 버퍼 역할 → 가용성 향상
- 실패한 프로세스로 메시지 재전달 가능
- 발신자가 수신자 IP/포트 몰라도 됨 (서비스 디스커버리 불필요)
- 메시지 하나를 여러 수신자에게 전달 가능
- 발신자/수신자 논리적으로 분리 (decoupling)

**메시지 브로커 사용 방식**
- 발신자가 큐/토픽에 메시지 발행 → 브로커가 하나 이상의 소비자에게 전달
- 일반적으로 단방향 (응답 원하면 별도 채널 사용)
- 주요 제품: RabbitMQ, ActiveMQ, Kafka, Kinesis

**분산 액터 프레임워크**
- **액터 모델**: 동시성 처리를 위한 프로그래밍 모델
	- 스레드 대신 액터 사용 — 각 액터는 로컬 상태를 가지고 비동기 메시지 수신/발신
	- 메시지가 전달된다는 보장 없음, 각 액터는 독립적으로 처리
- **분산 액터 프레임워크**: 액터를 여러 노드에 분산
	- 메시지 직렬화/역직렬화가 자동으로 수행
	- 스키마 발전이 여전히 중요: 노드마다 코드 버전이 다를 수 있음
	- 예: Akka(Java/Scala, 기본은 Java 직렬화지만 커스텀 가능), Orleans(.NET), Erlang OTP

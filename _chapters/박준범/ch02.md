## 데이터 모델과 질의 언어

- 데이터 모델은 소프트웨어 개발에서 제일 중요한 부분 — 문제를 어떻게 생각하는지 자체에 영향을 줌
- 애플리케이션은 데이터 모델을 계층적으로 쌓아 올림:
	- 앱 개발자: 현실 → 객체/데이터 구조/API
	- 저장할 때: JSON, XML, 관계형 테이블, 그래프 등 범용 모델
	- DB 엔지니어: 범용 모델 → 바이트 단위 표현 (메모리/디스크/네트워크)
	- HW 엔지니어: 바이트 → 전류/빛/자기장
- 각 계층이 하위 계층의 복잡성을 추상화로 숨김 → 그래야 각자 역할에 집중 가능

이 장에서 다루는 것: **관계형 모델, 문서 모델, 그래프 모델** + 각각의 질의 언어

## 1. 관계형 모델과 문서 모델

- 1970년 에드가 코드가 제안한 관계형 모델 → SQL
- 데이터를 관계(테이블)로, 각 관계는 순서 없는 튜플(로우)의 모음
- 원래는 "효율적으로 구현 가능한가?" 의문이 있었지만 → 1980년대 중반부터 RDBMS가 사실상 표준
- 25~30년간 우위 유지 — 비즈니스 데이터 처리뿐 아니라 웹 서비스 대부분이 관계형 DB 기반

### NoSQL의 탄생

- 2010년대에 관계형 모델에 대한 도전 — "NoSQL"은 원래 2009년 트위터 해시태그에서 시작
- 나중에 Not Only SQL로 재해석됨
- 채택 이유:
	- 대규모 데이터셋 / 높은 쓰기 처리량에서 더 쉬운 확장성
	- 상용 DB 대신 오픈소스 선호
	- 관계형 스키마가 지원 안 하는 특수 질의
	- 고정 스키마의 답답함 → 더 유연하고 표현력 있는 데이터 모델 필요
- 관계형 DB가 사라지는 건 아니고 비관계형과 함께 쓰임 → **다중 저장소 지속성(polyglot persistence)**

### 객체-관계형 불일치 (Impedance Mismatch)

- 대부분의 앱은 객체지향 언어로 개발하는데, 관계형 테이블에 저장하려면 거추장스러운 변환 계층이 필요
- ORM(ActiveRecord, Hibernate 등)이 상용구 코드를 줄여주긴 하지만 근본적 차이를 완전히 숨기진 못함
- 링크트인 이력서 예시: 한 사용자 → 여러 직위, 학력, 연락처 (일대다 관계)
	- 관계형: 별도 테이블 + 외래 키로 분리
	- JSON: 한 문서에 다 담을 수 있음 → 트리 구조와 잘 맞음
- JSON 표현의 장점:
	- 앱 코드의 객체 구조와 더 가까움
	- 지역성(locality) — 관련 정보가 한 곳에 있어 질의 하나로 충분
	- 다중 테이블 JOIN 불필요

### 다대일과 다대다 관계

- region_id, industry_id를 텍스트가 아닌 ID로 저장하는 이유:
	- 중복 제거 → 정규화의 핵심
	- ID 자체는 의미 없으므로 변경 불필요 (지역명 바뀌어도 ID는 그대로)
	- 일관된 스타일, 모호함 회피, 갱신 용이, 현지화, 검색 개선
- 정규화하면 다대일 관계가 필요 → 조인이 필수
- 관계형 DB는 조인 쉬움 / 문서 DB는 조인 지원이 약함 → 앱 코드에서 흉내 내야 함
- 처음엔 조인 없는 문서 모델로 충분해도, 기능 추가하면 데이터가 점점 상호 연결됨
	- 조직/학교를 엔티티로 참조, 추천서 기능 → 다대다 관계 발생

### 문서 DB는 역사를 반복하고 있나?

- 1960~70년대 IBM IMS의 계층 모델 — JSON 모델과 놀랍게도 비슷
- IMS도 일대다에는 강했지만 다대다/조인에는 약했음 → 개발자가 중복 or 수동 참조 해결
- 이 문제 해결을 위한 두 진영:
	- 관계형 모델 → SQL이 되어 세상 지배
	- 네트워크 모델 (코다실) → 초기 신봉자 많았지만 결국 사라짐

**네트워크 모델 (코다실)**
- 계층 모델을 일반화 — 레코드가 다중 부모를 가질 수 있음
- 연결이 외래 키가 아닌 포인터와 비슷 → 접근 경로를 직접 따라가야 함
- "n차원 데이터 공간을 항해하는 것" — 코다실 위원회도 인정할 정도
- 1970년대 제한된 HW에서는 효율적이었지만, 코드가 복잡하고 유연하지 못함
- 접근 경로 바꾸려면 수작업 질의 코드를 다 고쳐야 함 → 데이터 모델 변경이 매우 어려움

**관계형 모델**
- 알려진 모든 데이터를 그냥 테이블에 펼쳐놓는 것 — 중첩 구조/복잡한 접근 경로 없음
- 조건 지정하면 테이블에서 일치하는 로우를 찾아줌
- 질의 최적화기(query optimizer)가 접근 경로를 자동 결정
	- 개발자가 경로 신경 쓸 필요 없음
	- 새 색인 추가해도 질의 안 바꿔도 됨
- 질의 최적화기 만들긴 어렵지만 한 번 만들면 모든 앱이 혜택 봄

**문서 DB와의 비교**
- 문서 DB는 상위 레코드 내에 중첩 저장 (일대다) → 계층 모델 닮음
- 근데 다대일/다대다 표현에서는 관계형과 근본적으로 다르지 않음
	- 둘 다 고유 식별자로 참조함 (외래 키 vs 문서 참조)
	- 읽기 시점에 조인이나 후속 질의로 확인

### 관계형 DB와 오늘날의 문서 DB

**어떤 데이터 모델이 코드를 더 간단하게 하나?**
- 데이터가 문서처럼 생긴 트리 구조면 문서 모델이 자연스러움
- 문서를 여러 테이블로 찢는 관계형 방식은 불필요하게 복잡해질 수 있음
- 반면 다대다 관계가 많으면 문서 모델은 매력이 떨어짐 → 앱 코드가 비정규화 일관성 유지/수동 조인 떠안음
- 상호 연결 많은 데이터: 관계형이 무난하고, 그래프 모델이 가장 자연스러움

**스키마 유연성**
- 문서 DB = 스키마리스? → 정확히는 **읽기 스키마(schema-on-read)**
	- 데이터 구조가 암묵적이고, 읽을 때만 해석
	- 동적 타입 확인과 유사
- 관계형 DB = **쓰기 스키마(schema-on-write)**
	- 명시적 스키마, 쓸 때 준수 보장
	- 정적 타입 확인과 유사
- 데이터 타입 변경 시 차이:
	- 문서 DB: 새 필드로 새 문서 작성 시작, 앱에서 옛 문서 처리 코드만 추가
	- 관계형: ALTER TABLE + UPDATE (MySQL은 전체 테이블 복사해서 느림)
- 데이터가 이질적이고 구조 변경 잦으면 읽기 스키마가 유리 / 구조 일정하면 쓰기 스키마가 문서화+강제에 좋음

**질의를 위한 데이터 지역성**
- 문서는 연속된 문자열로 저장 → 전체 문서 자주 읽으면 지역성 이점 있음
- 근데 문서 일부만 읽어도 전체를 적재해야 하고, 갱신 시 전체 재작성 → 문서 작게 유지 권장
- 지역성 개념이 문서 모델만의 것은 아님:
	- 구글 스패너: 부모 테이블 내 로우 교차 배치
	- 오라클: 다중 테이블 색인 클러스터 테이블
	- 빅테이블 칼럼 패밀리 (카산드라, HBase)

**문서 DB와 관계형 DB의 통합**
- 관계형 DB도 XML/JSON 지원 강화 (PostgreSQL, MySQL, DB2 등)
- 문서 DB도 조인 지원 추가 (리싱크DB는 관계형 조인, 몽고DB는 클라이언트 측 조인)
- 시간이 지남에 따라 서로 닮아가는 중 → 혼합 모델이 미래 방향

## 2. 데이터를 위한 질의 언어

- 명령형(imperative): 특정 순서로 특정 연산 수행을 지시 (JS의 for/if 같은)
- 선언형(declarative): 원하는 결과의 패턴/조건만 지정 (SQL, 관계 대수)

선언형이 좋은 이유:
- 간결하고 쉬움
- DB 엔진 구현이 숨겨져 있어 질의 안 바꾸고도 성능 향상 가능
- 데이터 순서/물리 배치 바뀌어도 안전
- 병렬 실행에 적합 — 결과 패턴만 지정하므로 다중 코어/장비 활용 유리

### 웹에서의 선언형 질의

- DB만의 이야기가 아님 — CSS vs JavaScript DOM 조작으로 같은 걸 보여줌
- CSS: `li.selected > p { background-color: blue; }` → 패턴만 선언
- JS 명령형: getElementsByTagName으로 루프 돌면서 setAttribute → 코드 길고 복잡
- 명령형의 문제:
	- 클래스 제거되면 스타일이 자동으로 안 돌아옴 (CSS는 자동 감지)
	- 새 API 장점 취하려면 코드 재작성 필요 (CSS는 브라우저가 알아서 최적화)
- 결국 선언형이 유지보수, 최적화, 상태 관리 측면에서 다 나음

### 맵리듀스 질의

- 많은 컴퓨터에서 대량 데이터를 처리하기 위한 프로그래밍 모델 (구글이 널리 알림)
- 선언형도 아니고 완전한 명령형도 아닌 그 중간 정도
- map: 각 문서마다 호출, 키-값 쌍을 방출(emit)
- reduce: 같은 키의 값들을 모아서 합침
- 상어 관찰 예시:
	- SQL: `SELECT date_trunc('month', ...) GROUP BY ...` → 깔끔
	- 몽고DB 맵리듀스: map/reduce 함수 두 개를 따로 작성 → 더 복잡
- 제약: map/reduce는 순수 함수여야 함 → 분산 실행/재실행 가능
- 근데 함수 두 개 신중하게 작성해야 해서 사용성이 떨어지고, 최적화 기회도 적음
- 그래서 몽고DB 2.2부터 집계 파이프라인(aggregation pipeline) 추가 — SQL 부분집합과 유사한 선언형
- 결국 NoSQL도 SQL 비슷한 걸 다시 만들게 됨

## 3. 그래프형 데이터 모델

- 일대다/관계 없는 데이터 → 문서 모델 적합
- 단순한 다대다 → 관계형 OK
- 데이터 간 연결이 매우 복잡해지면 → 그래프로 모델링하는 게 자연스러움
- 그래프 = 정점(vertex) + 간선(edge)
- 예시: 소셜 그래프, 웹 그래프, 도로/철도 네트워크
- 같은 종류만이 아니라 서로 다른 유형의 객체(사람, 장소, 이벤트, 체크인 등)를 하나의 그래프에 넣을 수 있음 — 페이스북이 이렇게 함

### 속성 그래프

- 정점: 고유 식별자, 유출 간선 집합, 유입 간선 집합, 속성(키-값 쌍)
- 간선: 고유 식별자, 꼬리 정점(시작), 머리 정점(끝), 관계 레이블, 속성(키-값 쌍)
- 관계형 테이블 두 개(vertices, edges)로도 표현 가능
- 중요한 특성:
	1. 정점 간 연결에 유형 제한 없음 → 유연
	2. 정점의 유입/유출 간선을 효율적으로 탐색 가능
	3. 다른 레이블로 다른 유형의 관계 저장 → 데이터 모델 깔끔하게 유지
- 국가마다 지역 구조가 다르고, 데이터 입도도 제각각 → 관계형 스키마로 표현하기 어려운 걸 그래프는 자연스럽게 표현
- 발전성이 좋음 — 새 기능 추가 시 노드/간선만 추가하면 됨

### 사이퍼 질의 언어

- Cypher: 속성 그래프용 선언형 질의 언어 (네오포제이용)
- 화살표 표기로 패턴을 직관적으로 표현:
	- `(Idaho) -[:WITHIN]-> (USA)` → Idaho에서 USA로 가는 WITHIN 간선
- 예시: "미국에서 태어나 유럽에 사는 사람 찾기"
```
MATCH
  (person) -[:BORN_IN]-> () -[:WITHIN*0..]-> (us:Location {name:'United States'}),
  (person) -[:LIVES_IN]-> () -[:WITHIN*0..]-> (eu:Location {name:'Europe'})
RETURN person.name
```
- `[:WITHIN*0..]` = WITHIN 간선을 0회 이상 따라감 (정규표현식 `*` 같은 것)
- 선언형이라 실행 전략은 DB가 알아서 정함

### SQL의 그래프 질의

- 관계형 DB에서도 할 수는 있음 — `WITH RECURSIVE` (재귀 공통 테이블 식) 사용
- 근데 사이퍼 4줄짜리를 SQL로 쓰면 29줄 → 훨씬 장황하고 어려움
- 그래프 질의는 가변 길이 경로 탐색이 많은데, SQL은 조인 수를 미리 고정해야 해서 재귀로 풀어야 함
- 다양한 데이터 모델이 서로 다른 사용 사례를 위해 설계된 거라서 적합한 모델 선택이 중요함

### 트리플 저장소와 스파클

- 속성 그래프와 거의 동등한데 다른 용어로 표현
- 모든 정보를 (주어, 서술어, 목적어) 트리플로 저장
	- 목적어가 원시값이면 → 속성 (예: `(루시, 나이, 33)`)
	- 목적어가 다른 정점이면 → 간선 (예: `(루시, 결혼하다, 알랭)`)
- Turtle: 트리플을 사람이 읽기 쉽게 쓰는 표기법
- RDF(Resource Description Framework): 인터넷 전체 데이터 교환용으로 설계
	- 주어/서술어/목적어가 URI → 네임스페이스 충돌 방지
	- URL처럼 생겼지만 실제 접속 가능한 주소일 필요 없음, 그냥 고유 이름표 역할

**시맨틱 웹**
- "웹 정보를 컴퓨터도 읽을 수 있는 데이터로 게시하자" → 과대평가 + 지나치게 복잡한 표준
- 크게 성공은 못했지만, RDF/트리플 저장소 기술 자체는 가치 있음

**스파클(SPARQL)**
- RDF 데이터용 선언형 질의 언어
- Cypher보다 먼저 만들어짐 (Cypher가 스파클 패턴 매칭을 차용)
- `?person :bornIn / :within* / :name "United States"` 같은 문법으로 가변 경로 탐색을 간결히 표현
- RDF는 속성/간선 구분 없이 서술어로 통일 → 문법이 더 일관적

**그래프 DB vs 네트워크 모델 (코다실)**
- 언뜻 비슷해 보이지만 핵심적으로 다름:
	- 코다실: 엄격한 스키마, 접근 경로 수동 탐색, 명령형 질의, 레코드 정렬 유지
	- 그래프 DB: 스키마 제한 없음, 임의 정점 직접 참조 가능, 선언형 질의, 정렬 안 함

### 데이터로그

- 1980년대 학계에서 연구된 언어 — 스파클/사이퍼보다 훨씬 오래됨
- 이후 질의 언어의 초석이 됨
- 데이터 모델: 트리플과 유사하지만 `서술어(주어, 목적어)` 형태로 작성
	- `name(usa, 'United States').`
	- `within(idaho, usa).`
- SELECT로 바로 찾는 게 아니라 규칙(rule)을 정의해서 단계적으로 추론하는 방식
	- `within_recursive` 규칙: 재귀적으로 "어떤 장소가 더 큰 지역 안에 있는지" 추론
	- `migrated` 규칙: 출생지/거주지 조합해서 이민자 찾기
- 규칙을 결합하고 재사용할 수 있어서 간단한 일회성 질의엔 좀 불편하지만 복잡한 데이터에서는 매우 강력

## 트랜잭션 (Transactions)

- 데이터 시스템에는 여러 가지가 잘못될 수 있음:
	- 쓰기 도중 DB 크래시
	- 쓰기 도중 앱 크래시
	- 네트워크 끊김
	- 여러 클라이언트가 같은 데이터를 동시에 덮어씀
	- 부분적으로만 업데이트된 데이터를 다른 클라이언트가 읽음
- **트랜잭션**: 여러 읽기/쓰기를 하나의 논리적 단위로 묶어서 통째로 성공(commit)하거나 통째로 취소(rollback/abort)하게 만드는 것
- 1970년대 IBM System R 이후 수십 년간 유지 → 현재도 대부분의 관계형 DB + 일부 비관계형 DB 지원

## 1. ACID

트랜잭션 안전성 보장을 설명하는 약자임

### Atomicity (원자성)
- 트랜잭션의 모든 쓰기가 **전부 성공하거나 전부 실패**
- 중간에 오류가 생기면 이미 한 쓰기를 **취소(abort)** → 부분 업데이트 없음
- 구현: 쓰기를 커밋 전까지 WAL에만 저장, 크래시 시 롤백

### Consistency (일관성)
- 트랜잭션 전후로 **데이터가 항상 "유효한 상태"** 를 유지해야 한다는 것
- 사실 이건 DB가 아니라 **애플리케이션의 책임** — 무결성 제약 조건을 잘 정의하고 지켜야 함
- C는 ACID에 끼워 맞춘 것, 나머지 AID가 핵심 (Martin Kleppmann 의견)

### Isolation (격리성)
- 동시에 실행 중인 트랜잭션이 서로 간섭하지 않는 것처럼 보여야 함
- 교과서적으로는 **직렬화 가능성(serializability)**: 트랜잭션이 순차적으로 실행된 것처럼 동작
- 성능 오버헤드 때문에 실제로는 완화된 격리 수준을 많이 사용

### Durability (지속성)
- 커밋된 트랜잭션은 크래시가 나도 **영구 보존**
- 구현: 커밋 전 비휘발성 저장소(HDD/SSD)에 기록 (WAL), 복제

**BASE는 뭔가?**
- Basically Available, Soft state, Eventually consistent
- ACID의 반대 개념으로 마케팅 용도로 등장 — 구체적 의미는 모호함

## 2. 단일 객체 vs 다중 객체 트랜잭션

**단일 객체 쓰기**
- 단일 레코드 쓰기도 원자성/격리성 필요 (예: 20KB JSON 업데이트 도중 크래시)
- 거의 모든 DB가 보장 — WAL(원자성), 잠금(격리성)
- 증가 연산(increment), CAS(compare-and-set) 등도 단일 객체 원자적 연산으로 제공

**다중 객체 트랜잭션의 필요성**
- 여러 테이블에 걸친 참조 정합성 유지 (예: 이메일 미읽음 카운터 + 이메일 테이블)
- 비정규화된 문서 DB에서 여러 문서 동기화
- 인덱스 업데이트 (레코드 변경 시 인덱스도 함께 갱신)

**오류와 abort 처리**
- 트랜잭션의 핵심: 오류 시 안전하게 재시도 가능
- ORM 같은 라이브러리가 abort 시 재시도를 안 해주는 경우 있음
- 재시도 주의사항:
	- 트랜잭션은 성공했는데 응답만 유실 → 재시도 시 중복 수행
	- 과부하로 인한 오류 → 재시도가 더 나쁨 (지수 백오프 + 횟수 제한)
	- 일시적 오류가 아닌 경우 재시도 의미 없음 (constraint 위반 등)
	- 트랜잭션에 부수효과가 있으면 재시도 시 중복 (이메일 발송 등)

## 3. 완화된 격리 수준

- 직렬화 가능 격리는 성능 비용이 크므로 DB들이 완화된 수준 제공
- 개발자가 격리 수준을 이해하고 적절히 선택해야 함 (버그는 언제든 터질 수 있음)

### 커밋 후 읽기 (Read Committed)

가장 기본적인 격리 수준임 (PostgreSQL 기본값, Oracle, SQL Server)

**두 가지 보장**
1. **더티 읽기 방지**: 커밋되지 않은 데이터는 읽을 수 없음
2. **더티 쓰기 방지**: 아직 커밋 안 된 데이터를 덮어쓸 수 없음

**더티 읽기 방지 구현**
- 각 객체에 "커밋된 값"과 "진행 중인 트랜잭션이 쓴 값" 두 개 유지
- 다른 트랜잭션이 읽으면 항상 커밋된 값만 반환

**더티 쓰기 방지 구현**
- 행 수준 잠금: 트랜잭션이 객체 쓰기 시 잠금 획득 → 커밋/롤백 전까지 다른 쓰기 차단

**여전히 발생하는 문제: 비반복 읽기(non-repeatable read)**
- 트랜잭션 중 같은 행을 두 번 읽었을 때 다른 값이 나오는 현상
- 예: 계좌 잔액 합산 중 이체 트랜잭션이 끼어들어 잘못된 합계 (read skew)

### 스냅샷 격리와 반복 읽기 (Snapshot Isolation)

- **스냅샷 격리**: 각 트랜잭션이 **일관된 DB 스냅샷**에서 읽음 → 트랜잭션 시작 시점의 데이터만 봄
- 진행 중 다른 트랜잭션이 데이터를 바꿔도 영향 없음
- PostgreSQL, InnoDB(MySQL), Oracle, SQL Server(snapshot 격리 옵션)에서 지원
- **MVCC (Multi-Version Concurrency Control)** 로 구현
	- 각 행에 여러 버전 유지 (created_by 트랜잭션 ID, deleted_by 트랜잭션 ID)
	- 읽기는 트랜잭션 ID로 자신이 볼 수 있는 버전을 결정
	- 가시성 규칙: 자신의 트랜잭션 ID보다 작은(이전에 커밋된) 쓰기만 보임

**가시성 규칙 (PostgreSQL 기준)**
- 트랜잭션 시작 시 진행 중인 트랜잭션 목록 기록
- 해당 목록의 트랜잭션이 쓴 데이터는 보이지 않음
- 자신보다 ID가 큰 트랜잭션의 쓰기는 보이지 않음
- abort된 트랜잭션의 쓰기는 무시

**인덱스와 스냅샷 격리**
- 옵션 1: 모든 버전을 인덱스에서 가리킴, 쿼리 시 필터링 (PostgreSQL)
- 옵션 2: append-only B-Tree → 쓸 때 기존 페이지 수정 않고 새 페이지 생성 (CouchDB, Datomic)

### 갱신 손실 방지 (Preventing Lost Updates)

- 두 트랜잭션이 read-modify-write 패턴으로 같은 데이터를 동시 수정 → 하나의 갱신이 사라짐
- 예: 카운터 증가, 잔액 변경, JSON 문서 일부 수정

**해결 방법**

**원자적 쓰기 연산**
```sql
UPDATE counters SET value = value + 1 WHERE key = 'foo';
```
- DB 내장 원자 연산 사용 → 읽기-수정-쓰기를 DB가 원자적으로 처리
- 보통 해당 객체에 배타적 잠금 사용

**명시적 잠금**
```sql
BEGIN TRANSACTION;
SELECT * FROM figures WHERE name = 'robot' FOR UPDATE;
-- 앱 코드에서 위치 계산
UPDATE figures SET position = 'new position' WHERE id = 1234;
COMMIT;
```
- `FOR UPDATE`: 해당 행에 쓰기 잠금 → 다른 트랜잭션이 수정 불가

**자동 갱신 손실 감지**
- 일부 DB(PostgreSQL repeatable read, Oracle serializable, SQL Server snapshot)가 자동으로 감지 후 abort
- 트랜잭션 재시도로 처리

**CAS (Compare-and-Set)**
```sql
UPDATE wiki_pages SET content = 'new content'
WHERE id = 1234 AND content = 'old content';
```
- 값이 마지막으로 읽은 것과 같을 때만 갱신
- 스냅샷에서 읽을 경우 여전히 안전하지 않을 수 있음 — DB마다 다름

**복제 환경에서 갱신 손실**
- 복제된 DB에서는 CAS가 작동 안 할 수 있음 (다중 리더/리더 없는 경우)
- 교환 가능한 연산(commutative) 사용 또는 애플리케이션 레벨 충돌 해결

### 쓰기 스큐와 팬텀 (Write Skew and Phantoms)

**쓰기 스큐 (Write Skew)**
- 갱신 손실의 일반화 버전: 두 트랜잭션이 서로 다른 객체를 수정하지만, 동시에 읽고 결정한 결과가 서로 충돌
- 예: 의사 당직 시스템 — 최소 1명 유지 조건에서 두 의사가 동시에 퇴근 신청
	- 두 트랜잭션이 각각 "아직 다른 의사가 있음"을 확인하고 자신을 제거 → 결과적으로 0명

```sql
-- 두 트랜잭션이 동시에 실행
BEGIN;
SELECT COUNT(*) FROM doctors WHERE on_call = TRUE AND shift_id = 1234;  -- 결과: 2
-- 충분하다고 판단
UPDATE doctors SET on_call = FALSE WHERE name = 'Alice' AND shift_id = 1234;
COMMIT;
```

**쓰기 스큐 예시들**
- 회의실 예약 (같은 시간대 중복 예약)
- 사용자 이름 유일성
- 이중 지출 방지

**쓰기 스큐 해결 방법**
- 직렬화 가능 격리 사용 (가장 안전)
- `SELECT FOR UPDATE`로 트랜잭션이 의존하는 행 모두에 잠금
	- 단, 아직 DB에 존재하지 않는 행은 잠글 수 없음 → **팬텀**

**팬텀 (Phantom)**
- 트랜잭션의 쓰기가 다른 트랜잭션의 검색 결과를 변경하는 현상
- 검색 조건에 맞는 행이 없는 경우 잠글 수 없음 → SELECT FOR UPDATE로 해결 불가
- 해결: **매터리얼라이즈드 충돌(materializing conflicts)** — 팬텀을 일으키는 조건을 미리 행으로 만들어 잠금

## 4. 직렬화 가능성 (Serializability)

완화된 격리 수준은 버그를 막기 어려움 → 가장 강한 격리 수준이 필요

**직렬화 가능성**: 트랜잭션들이 실제로 병렬 실행되더라도 한 번에 하나씩 순차 실행한 것과 동일한 결과를 냄

### 실제 직렬 실행 (Actual Serial Execution)

- 트랜잭션을 정말 순서대로 하나씩 실행 → 동시성 문제 없음
- 2000년대 후반부터 RAM이 저렴해져 전체 데이터셋이 메모리에 들어가게 됨 → 가능해짐
- VoltDB(H-Store), Redis, Datomic 사용

**스토어드 프로시저**
- 대화형 트랜잭션(각 쿼리마다 네트워크 왕복)은 직렬 실행 시 너무 느림
- 해결: 전체 트랜잭션 로직을 **스토어드 프로시저**로 DB에 미리 제출 → 왕복 없이 한 번에 실행
- 프로그래밍 언어: VoltDB는 Java/Groovy, Datomic은 Clojure, Redis는 Lua
- 단점: 디버깅 어려움, 버전 관리 힘듦, DB별 언어 다름

**직렬 실행의 파티셔닝**
- 단일 CPU로는 처리량 한계 → 파티셔닝
- 각 파티션이 독립적으로 트랜잭션 처리
- 여러 파티션에 걸친 트랜잭션은 코디네이션 필요 → 훨씬 느림
- VoltDB: 파티션 간 트랜잭션 지원하지만 성능 저하

### 2단계 잠금 (Two-Phase Locking, 2PL)

- 30년간 직렬화 가능 격리의 표준 방법
- MySQL(InnoDB serializable), SQL Server(serializable) 사용

**기본 규칙**
- 읽는 트랜잭션은 다른 쓰는 트랜잭션을 막음
- 쓰는 트랜잭션은 다른 읽는/쓰는 트랜잭션을 막음
- "쓰기는 읽기와 쓰기 모두 차단"

**구현**
- 각 객체에 **공유 잠금(shared lock)** / **배타 잠금(exclusive lock)**
- 공유 잠금: 읽기 시 획득 → 여러 트랜잭션이 동시에 공유 잠금 가능
- 배타 잠금: 쓰기 시 획득 → 다른 모든 잠금과 충돌
- 잠금은 2단계로 관리: 트랜잭션 실행 중 잠금 획득, 커밋/롤백 시 모두 해제

**성능 문제**
- 잠금 경합으로 대기 시간 큼
- **데드락(deadlock)**: 두 트랜잭션이 서로 상대방의 잠금을 기다림 → DB가 감지하고 하나를 abort
- 스냅샷 격리보다 처리량/응답시간이 훨씬 나쁨

**팬텀 처리: 서술 잠금(predicate lock)**
- 아직 존재하지 않는 객체를 포함해 조건에 맞는 모든 객체를 잠금
- 예: "특정 시간대의 예약 행 모두" → 미래의 삽입도 차단
- 성능 문제: 활성 잠금이 많으면 매칭 확인에 시간 소요

**인덱스 범위 잠금(index-range lock, next-key lock)**
- 서술 잠금의 근사치 — 더 큰 범위를 잠그되 인덱스 기반으로 효율적
- InnoDB가 이 방식 사용

### 직렬화 가능 스냅샷 격리 (Serializable Snapshot Isolation, SSI)

- 2008년 Michael Cahill의 박사 논문에서 제안
- 스냅샷 격리의 성능 + 직렬화 가능성 보장 → 낙관적 동시성 제어
- PostgreSQL 9.1(2011)에서 serializable 수준으로 구현

**낙관적 vs 비관적**
- 2PL: **비관적** — 충돌 가능성을 항상 가정, 미리 잠금
- SSI: **낙관적** — 충돌이 없을 것이라 가정하고 진행, 커밋 시 충돌 감지 후 abort

**SSI 동작 방식**
- 스냅샷에서 읽기 + 쓰기 충돌 추적
- 두 가지 상황을 감지:
	1. **오래된 MVCC 읽기**: 스냅샷에서 읽은 후 해당 데이터가 커밋된 변경 → abort
	2. **이전 읽기에 영향을 주는 쓰기**: 다른 트랜잭션이 내가 읽은 데이터를 수정 → abort

**SSI의 장점**
- 잠금 없이 읽기/쓰기 가능 → 처리량 높음
- 응답 시간 예측 가능 (잠금 대기 없음)
- 읽기 전용 쿼리가 잠금 불필요
- 단점: 충돌 비율 높으면 abort 많아짐 → 충돌 적은 워크로드에 유리

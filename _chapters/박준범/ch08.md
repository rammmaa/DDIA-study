## 분산 시스템의 문제

- 단일 컴퓨터에서는 결정론적: 같은 연산은 항상 같은 결과
- 분산 시스템에서는 **부분 장애(partial failure)** 가 발생할 수 있음
	- 일부 컴포넌트는 살아있고 일부는 죽어있는 상태 → 어떤 것이 성공하고 실패했는지 알기 어려움
- 이 불확실성 직면하고도 올바른 소프트웨어 만드는 게 핵심임

---

## 1. 신뢰할 수 없는 네트워크

- 분산 시스템에서 쓰는 인터넷/데이터센터 네트워크는 대부분 **비동기 패킷 네트워크**
- 요청을 보내도:
	- 패킷이 유실될 수 있음
	- 원격 노드가 다운됐을 수 있음
	- 원격 노드가 요청을 받았지만 처리 중 일시 정지 후 응답이 지연될 수 있음
	- 원격 노드가 처리했지만 응답이 유실될 수 있음
- 이 모든 경우 **타임아웃**으로 판단 — 하지만 요청이 처리됐는지는 여전히 알 수 없음

**타임아웃 설정의 어려움**
- 너무 짧게: 단순 지연인데 노드 죽었다고 판단 → 불필요한 페일오버, 부하 전가로 상황 악화
- 너무 길게: 실제 죽은 노드를 너무 늦게 감지

**타임아웃 자동 튜닝**
- Akka, Cassandra: 관측된 응답 시간 분포를 보고 타임아웃 동적 조정
- Phi Accrual failure detector: 고정 임계값 대신 확률 기반으로 "이 노드가 살아있을 가능성" 계산

**네트워크 지연 예측 불가능성**
- 데이터센터 내 네트워크도 네트워크 혼잡, TCP 재전송, OS 스케줄링 지연 등으로 수백ms 발생 가능
- 전화망과 달리 인터넷 패킷 네트워크는 서킷 스위칭이 아닌 패킷 스위칭 → 대역폭을 공유, 순간 지연 발생

## 2. 신뢰할 수 없는 시계

분산 시스템에서 각 노드는 자신의 시계를 가짐 → 완벽하게 동기화되지 않음

### 단조 시계 vs 일시계

**일시계 (Time-of-Day Clock)**
- 현재 날짜/시간을 반환: `System.currentTimeMillis()`
- NTP로 동기화 → 동기화 후 "점프" (갑자기 앞/뒤로 이동 가능)
- 이벤트 순서 비교에 적합하지 않음

**단조 시계 (Monotonic Clock)**
- 항상 앞으로만 증가: `System.nanoTime()`
- 절대 시간이 아닌 경과 시간 측정에 적합 (타임아웃, 응답시간 측정 등)
- NTP가 속도를 조정할 수 있지만 뒤로 가지는 않음

### 시계 동기화 문제

- NTP 동기화도 완벽하지 않음 → 수십ms 오차, 네트워크 혼잡 시 수백ms
- 수정 발진자(quartz clock) 자체가 드리프트 (일일 수ms ~ 수백ms 오차)
- **Spanner**: GPS 수신기/원자 시계 사용해 TrueTime API 제공 → 불확실성 범위 포함한 시간 반환
	- `[earliest, latest]` 범위를 반환 → 반드시 이 범위가 겹치지 않을 때까지 대기 후 커밋

**시간 기반 분산 문제들**

**최근성에 의존한 리더 결정**
- "최근에 리더에게서 응답받은 노드가 리더다"라는 판단을 타임스탬프로 → 시계 차이로 잘못된 결정 가능
- HBase, Cassandra: "마지막 쓰기 우선(LWW)" — 시계 차이로 더 나중에 쓴 데이터가 이전 것처럼 보일 수 있음 → 데이터 유실

**프로세스 일시 정지**
- GC stop-the-world: 수십ms ~ 수분까지 프로세스 멈춤
- 가상화 환경에서 VM 일시 정지 (다른 VM에 CPU 양보)
- OS context switch, 디스크 I/O 대기 등
- → 프로세스가 임의 시점에 임의 시간 동안 멈출 수 있음

**예시: 리스 만료 문제**
```
1. 노드 A가 리스(lease) 획득 (10초 유효)
2. GC 발생으로 노드 A가 15초간 멈춤
3. 리스 만료됐지만 노드 A는 여전히 자신이 리더라고 생각
4. 노드 B가 새 리스 획득
5. 노드 A가 깨어나서 리더인 것처럼 행동 → 두 리더 동시 존재
```
- 해결: **펜싱 토큰(fencing token)** — 단조 증가하는 토큰을 스토리지에 함께 전달, 오래된 토큰은 거부

## 3. 지식, 진실, 거짓말

**노드는 자신의 상태를 확신할 수 없음**
- 요청을 보냈는데 응답이 없을 때 — 상대방이 죽었는가, 아니면 내 요청이 도달하지 않았는가?
- "다수결(quorum)"로 결정: 과반수 노드가 동의하면 그것을 진실로 간주

### 진실은 다수결로 결정

- 노드 하나가 자신이 살아있다고 믿어도, 다른 노드들이 죽었다고 판단하면 그게 진실
- 반쪽 단절(half-disconnected): 모든 메시지를 받을 수 있지만 보낼 수 없는 상황
	- 다른 노드들은 이 노드를 죽었다고 판단 → 이 노드가 리더라도 무시됨

**펜싱 토큰 (Fencing Token)**
- 리스/잠금을 획득할 때마다 단조 증가하는 토큰 발급
- 스토리지에 쓸 때 토큰도 함께 전달
- 스토리지가 더 큰(최신) 토큰이 이미 있으면 이전 토큰의 쓰기 거부
- GC 멈춤 후 깨어난 오래된 리더의 쓰기를 막을 수 있음

### 비잔틴 결함 (Byzantine Faults)

- 지금까지 가정: 노드는 거짓말하지 않음 (느리거나 죽을 뿐)
- **비잔틴 결함**: 노드가 의도적으로 거짓 메시지를 보내거나 프로토콜을 어기는 경우
- **비잔틴 내결함성**: 일부 노드가 악의적으로 행동해도 올바르게 동작
- 우주선 방사선, 블록체인, 다자간 참여 시스템 등에서 필요
- 일반 데이터베이스에서는 보통 불필요 — 모든 노드가 같은 조직 소유이면 Byzantine 가정 안 해도 됨

### 시스템 모델 (System Models)

분산 알고리즘 분석할 때 쓰는 가정들임

**타이밍 모델**
- **동기 모델**: 메시지 지연/처리 시간에 상한이 있음 → 현실적이지 않음
- **부분 동기 모델**: 대부분 동기지만 가끔 초과 → 현실과 가장 가까움
- **비동기 모델**: 어떤 타이밍도 가정 안 함 → 매우 제한적인 알고리즘만 가능

**노드 장애 모델**
- **충돌-정지**: 노드가 죽으면 영원히 죽음 (돌아오지 않음)
- **충돌-복구**: 죽었다가 돌아올 수 있음 (비휘발성 저장소의 상태는 유지)
- **비잔틴**: 노드가 어떤 방식으로든 이상 동작 가능

**알고리즘의 정확성**
- **안전성(Safety)**: "나쁜 일이 일어나지 않음" — 항상 유지해야 함
- **활성(Liveness)**: "좋은 일이 결국 일어남" — 일부 상황에서 일시적으로 어길 수 있음
- 예: "잘못된 데이터를 반환하지 않음(안전성)" vs "요청에 결국 응답함(활성)"

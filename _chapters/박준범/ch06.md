## 파티셔닝 (Partitioning)

- **파티셔닝**: 데이터를 여러 노드에 분할 저장 → **수평 확장(scale out)**
- 각 레코드는 정확히 하나의 파티션에 속함
- 보통 복제와 함께 사용 — 각 파티션의 복사본이 여러 노드에 존재
- 용어: HBase에서는 region, Bigtable에서는 tablet, Cassandra/Riak에서는 vnode, MongoDB에서는 shard

**파티셔닝의 목적**
- 한 노드에 다 담을 수 없는 데이터 저장
- 쿼리 처리량을 여러 노드에 분산 → 확장

**불균등 분할 (Skew)**
- 파티션 간 데이터/쿼리가 불균등하면 일부 파티션이 **핫스팟(hotspot)** 이 됨
- 모든 부하가 하나에 쏠리면 파티셔닝 의미 없음

## 1. 키-값 데이터 파티셔닝

### 키 범위 기반 파티셔닝 (Key Range Partitioning)

- 각 파티션에 연속된 키 범위 할당 (예: 백과사전 a-c, d-f, g-i…)
- 파티션 경계는 균등하게 분포하도록 관리자가 수동 설정하거나 자동 조정
- **장점**: 범위 쿼리 효율적 (파티션 하나에서 범위 스캔 가능)
- **단점**: 특정 패턴에서 핫스팟 발생
	- 예: 타임스탬프를 키로 사용 → 오늘 날짜 파티션에만 쓰기가 집중
	- 해결: 타임스탬프 앞에 센서명 등을 prefix로 붙여 여러 파티션에 분산 (단, 범위 쿼리 시 여러 파티션 조회 필요)
- 사용: HBase, RethinkDB, MongoDB(2.4 이전)

### 키 해시 기반 파티셔닝 (Hash Partitioning)

- 좋은 해시 함수를 통해 편향된 데이터를 균등하게 분산
- 파티션 범위를 해시값 기준으로 할당 (연속된 키 → 흩어짐)
- **장점**: 균등 분산, 핫스팟 완화
- **단점**: 범위 쿼리 비효율 (연속된 키가 여러 파티션에 흩어짐)
	- MongoDB: 해시 파티셔닝 시 범위 쿼리는 모든 파티션으로 전송
	- Cassandra: 복합 기본 키로 절충 — 첫 번째 컬럼은 해시로 파티션 결정, 나머지로 파티션 내 정렬
		- 예: (user_id, update_timestamp) → 특정 사용자의 모든 업데이트를 효율적으로 범위 조회 가능
- 사용: Cassandra, Riak, Voldemort

**핫스팟 해결의 한계**
- 해시도 완전하지 않음 — 유명인 SNS 계정에 쓰기가 집중되는 경우
- 해결: 키 앞뒤에 랜덤 숫자 추가 → 쓰기는 100개 파티션으로 분산, 읽기는 모든 파티션 집계 후 합산 (오버헤드 있음)

## 2. 파티셔닝과 보조 인덱스

### 문서 기반 보조 인덱스 (Document-partitioned)

- 각 파티션이 자신만의 보조 인덱스 유지 → **로컬 인덱스**
- 특정 필드로 검색 시 모든 파티션에 쿼리 전송 후 결과 합산 → **스캐터/게더(scatter/gather)**
- 예: `color:red` 차량 검색 → 모든 파티션에 질의 → 꽤 비쌈
- Elasticsearch, Solr, Riak, Cassandra, MongoDB, VoltDB 등

### 단어 기반 보조 인덱스 (Term-partitioned)

- 인덱스 자체를 파티셔닝 → **글로벌 인덱스**
- `color:red`는 색상 인덱스 파티션에, `color:yellow`는 다른 파티션에
- 파티션 키: 인덱스 단어(term) 자체 또는 해시값
- **장점**: 읽기 시 한 파티션에서만 조회 가능 → 효율적
- **단점**: 쓰기 시 여러 인덱스 파티션 갱신 → 복잡, 분산 트랜잭션 필요
- 실제로는 보통 **비동기 업데이트** → 인덱스가 실시간으로 최신이 아닐 수 있음
- 사용: DynamoDB, Riak의 검색 기능, Oracle의 글로벌 인덱스

## 3. 파티션 재균형화 (Rebalancing)

- 노드 추가/제거, 데이터 증가 시 파티션을 재분배해야 함
- 조건:
	- 재균형화 후 부하가 균등해야 함
	- 재균형화 중에도 읽기/쓰기 가능해야 함 (무중단)
	- 최소한의 데이터만 이동 (네트워크/디스크 부하 최소화)

### 재균형화 전략

**파티션 수 = 노드 수 (비권장)**
- 노드 추가 시 파티션 분할 → 반쪽을 새 노드로
- Riak, Elasticsearch, Couchbase, Voldemort 사용 (일부)
- 분할 포인트 결정 어렵고, 분할 자체도 비쌈

**고정 파티션 수 (Fixed number of partitions)**
- 처음부터 파티션을 많이 생성 → 노드 추가 시 파티션 몇 개를 새 노드로 이동
- 예: 10개 노드, 1000개 파티션 → 노드당 약 100개 파티션
	- 노드 추가 시 파티션 몇 개만 이동, 나머지는 그대로
- **파티션 수는 고정** → 처음 설정이 중요 (너무 적으면 나중에 문제, 너무 많으면 오버헤드)
- Riak, Elasticsearch, Couchbase, Voldemort 사용

**동적 파티셔닝 (Dynamic partitioning)**
- 파티션이 설정 크기(예: 10GB)를 초과하면 둘로 분할, 너무 작아지면 병합
- 파티션 수가 데이터에 비례 → 효율적
- 초기에는 파티션 하나 → 모든 쓰기가 한 노드 집중 (pre-splitting으로 초기 파티션 여러 개 설정 가능)
- HBase, RethinkDB, MongoDB

**노드 비례 파티셔닝 (Node-proportional)**
- 노드당 파티션 수 고정 → 노드 추가 시 파티션 분할
- 데이터 증가: 파티션 커짐 / 노드 추가: 파티션 분할해서 새 노드로
- 파티션 크기가 데이터/노드 수에 비례
- Cassandra, Ketama 사용

### 자동 vs 수동 재균형화

- **자동**: 편리하지만 예측 불가 → 특정 노드 느리면 과부하로 판단해 불필요한 재균형화 가능 → 연쇄 장애
- **수동(관리자 승인)**: 예측 가능, 의도치 않은 재균형화 방지
- **절충**: 자동 추천 + 관리자 승인으로 실행 (Couchbase, Riak, Voldemort)

## 4. 요청 라우팅 (Request Routing)

- 클라이언트가 "어떤 노드로 연결해야 하는가?"를 어떻게 아는가?

### 세 가지 방식

1. **임의 노드 접속 후 포워딩**: 클라이언트가 아무 노드에 연결 → 맞는 노드로 포워딩
2. **라우팅 티어(Routing Tier)**: 전용 파티션 인식 라우터가 올바른 노드로 전달 (클라이언트는 라우터만 알면 됨)
3. **클라이언트 인식**: 클라이언트가 직접 파티션-노드 매핑 알고 있음 → 직접 접속

**파티션 할당 정보는 어디서?**
- **ZooKeeper**: 파티션-노드 매핑을 중앙에서 관리 → 노드가 ZooKeeper에 등록, 라우터가 구독
	- HBase, SolrCloud, Kafka
- **Gossip 프로토콜**: 노드 간 직접 정보 전파 → ZooKeeper 없이도 동작
	- Cassandra, Riak

### 병렬 쿼리 실행 (Massively Parallel Processing, MPP)

- 지금까지는 단순 키-값 조회 중심
- 분석 DB (MPP): 복잡한 쿼리를 여러 파티션에서 병렬 실행
- 쿼리 옵티마이저가 여러 파티션에 실행 계획 분산 → 결과 취합
- Teradata, Vertica, Redshift 등이 MPP 아키텍처 사용
